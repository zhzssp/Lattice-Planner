# Part 1 · 三档自我介绍

## 30 秒版

> Lattice-Planner 是个人目标管理系统，我在里面做了内置的 Agent 运行时。
>
> 技术上没用 LangChain 或 Spring AI，手写了完整链路：ReAct 主循环、注解+反射的工具注册表、多轮上下文管理，以及双向 MCP 协议实现。
>
> 三个有意思的点：**一是让 Agent 通过本机回环真正走 MCP 协议访问自己的本地文件服务**；二是把检索质量做成运行时闭环而非提示词约束；三是参考 DeepSeek Harness 做了工具分层可见性与轮次收尾解耦——但刻意裁剪了不适配个人单机场景的部分。
>
> 最近在做**知识仓库**这条线：把「我不知道自己不知道什么」这个问题工程化——用 Git 管理语料、用检验闭环证明"真的会了"、用缺口台账攒盲区证据、用蒸馏把 PDF 变草稿。核心方法论一句话：**把靠人自觉的约定变成机器门禁**。

## 2 分钟版

> 背景是我需要一个能管目标/任务/笔记/复盘的工具，后来想让它"读我的资料帮我规划"，就演进成 Agent 系统。
>
> **最底层是 Agent 内核**——ReAct 循环、工具注册表、上下文管理。工具用 `@AgentTool` 注解声明，启动时反射扫描成注册表，导出 JSON Schema 给 LLM。我控制三个点：单轮步数上限防工具循环、按对话模式做工具 tag 隔离、工具确认策略。
>
> **中间是知识层**。笔记做 hybrid 检索——MySQL 全文索引 + 应用层向量 cosine，加权融合。之上加两层：CRAG 纠正式检索（检索完自评质量，低质就改写重检索，仍不行让 LLM 明示"基于通用知识"）；serving 化（语义查询缓存 + 异步预取）。
>
> **上层是编排层**。子代理机制让规划/复盘/检索三种角色在独立上下文跑各自 ReAct，只回压缩结论，避免长文档污染主对话。MCP 双向实现——既对外暴露 Server，也作为 Client 连接外部服务器。
>
> **最近吸收前沿做的是可控性**。参考 DeepSeek Harness 做了工具分层可见性（全局→模式→角色→会话四层遮蔽，能显式 deny + 执行层强制拦截）和轮次收尾解耦（收尾顾问 steer + 粘性降级标记），但刻意裁剪了不适配个人单机场景的插件化实现替换。
>
> **再往上走是知识仓库这条线**。用 Git 管理刻意整理的知识体系，四层索引；用「预测门禁 → 受限执行 → 判定」的检验闭环证明"真的会了"；把三类盲区信号（检索降级、当初跳过现在被问、验证失败）攒成缺口台账；再用蒸馏把 PDF 变草稿、定线算"现在该干什么"。贯穿的方法论一句话：**把靠人自觉的约定变成机器门禁**——示例必须入库、引用必须可达、改动必须审阅，每条都做成了执行层的拒绝或 CI 的报错，而不是 prompt 里的一句"请遵守"。
>
> **我认为最有价值的是 MCP loopback**：Agent 读本地文档时不走同进程直接调方法的捷径，而是作为 MCP Client 连接本机自己的 Server，完整走 SSE + JSON-RPC 握手。多一次本机回环 5ms 以内，换来协议栈完整复用——以后接任何外部 MCP 服务器是同一套代码路径。

## 5 分钟版结构（按序展开，别乱跳）

1. **问题**：让工具"读我资料帮我规划"，需要调用系统能力 + 读本地文档 + 检索知识库
2. **为什么自己写**：不是不知道有框架，是要的控制点被框架封装掉了
3. **内核**：ReAct + 工具注册表 + 上下文（可要白板）
4. **难点一**：上下文膨胀 → 子代理隔离
5. **难点二**：检索质量不可控 → CRAG 硬闭环
6. **难点三**：每轮重复构造 prompt → 前缀缓存 + 字节稳定化
7. **难点四**：工具权限边界 → 分层可见性 + Reflexion 封禁（两层治理）
8. **再往上**：知识仓库——把"学一个体系"工程化（检验闭环证明真会、缺口台账攒盲区、门禁替代自觉）
9. **工程完整性**：多用户隔离、可观测、降级、评测体系
10. **收尾**：踩坑（选 Part 5 坑 1）

# Part 3 · Agent 内核（技术面主战场）

## 3.1 ReAct 主循环：为什么手写

**先声明"我知道有现成的"**：

> function calling 和各类框架都能做工具调用。我手写是因为要在循环里插入三个控制点，而这些点框架要么封装掉、要么要 hack 才能改。

**骨架（能默写）**：

```java
for (int step = 0; step < maxSteps; step++) {
    var msgs = promptBuilder.assemble(prefix, memory.history(sid));   // ① 前缀复用
    String raw = llm.generateChat(msgs);
    ToolCall call = parser.parse(raw);

    if (call == null) {                          // 终态：自然语言
        if (finishOrSteer(sid, outcome)) continue;   // ⑤ 收尾顾问可 steer 继续
        return;
    }
    ToolDefinition def = registry.get(call.name());
    if (def == null) { 回灌 UNKNOWN_TOOL; continue; }      // ② 未知工具也回灌
    if (!toolView.contains(call.name())) { 回灌 TOOL_NOT_VISIBLE; continue; }  // ⑥ 可见性硬边界

    if (approvalPolicy.needsConfirm(user, def)) {          // ③ 授权切入点
        if (!confirmCoordinator.askUser(...).get()) { 回灌 USER_REJECTED; continue; }
    }
    try { result = registry.invoke(call.name(), call.arguments()); }
    catch (Throwable t) { result = {"error": t.getClass().getSimpleName(), ...}; }  // ④ 失败即 Reflexion
    appendToolTrace(sid, ...);                   // 回灌 history，进入下一步
}
```

**六个设计点**：

**① 步数上限 24**
防"工具循环"（LLM 反复调同一工具不收敛）。为什么不是 8？引入子代理和 MCP 后单轮需多跳（读文档→拆解→建目标→建 N 个任务），实测 8 步会在复杂规划中途截断。耗尽时明确提示"请拆分任务"而非静默失败。

**② 任何异常转结构化 JSON 回灌，不抛出**
这就是 Reflexion 的最小实现。关键细节：连 `UNKNOWN_TOOL`（LLM 编了不存在的工具名）也回灌，它下一步通常能自己改对。实测比"抛异常终止"体验好很多。

**③ 授权判断独立成策略层**
`requiresConfirm` 是工具**固有属性**（注解里，编译期固定），不能改——改了对所有用户生效，破坏安全默认值。用户的 auto-approve 是**运行时降权**，存在 `UserPreference`。所以判断式是 `requiresConfirm && !autoApproved(user, tool)`，抽成 `ToolApprovalPolicy.needsConfirm(user, def)`。**主循环和子代理共用同一策略，改授权只动一处。**

**④ 工具轨迹回灌格式**
```java
memory.append(sid, "assistant", {"tool":"task.create","arguments":{...}});
memory.append(sid, "user", "[tool_result task.create]\n" + truncate(json, 4000));
```
把结果伪装成 user 消息，因为 OpenAI 兼容接口的 `tool` role 在不同供应商行为不一致，user role 最稳。截断 4000 防单个结果撑爆上下文（截断发生时置粘性降级标记，见创新 8）。

**⑤ 收尾顾问（TurnStopping）**
终态不是直接 `return`，而是先问一圈顾问——顾问可返回 steer 消息让轮次继续。这样"什么时候算结束"从循环内部解耦到外部，加"还没完的理由"不用改主循环。失控防护：单轮 steer 上限由 Bus 强制，顾问绕不过。

**⑥ 可见性硬边界（执行层强制）**
`registry.get` 查的是全量注册表，而 LLM 只看到过滤后的 schema。若只靠 schema 过滤，模型凭记忆调不可见工具照样能调通。所以在 `def != null` 之后、执行之前再拦一道：工具存在但当前 scope 不可见 → 短路返回 `TOOL_NOT_VISIBLE`，不真正执行。

## 3.2 工具系统：注解 + 反射

```java
@AgentTool(name = "task.create", tags = {"task","write"}, requiresConfirm = false,
           description = "创建一个任务...")
public Map<String,Object> create(
    @ToolParam(value="title", desc="任务标题", required=true) String title,
    @ToolParam(value="dueDate", desc="截止日期 yyyy-MM-dd") String dueDate) { ... }
```

**启动扫描**（监听 `ApplicationReadyEvent`）：扫所有 bean 方法找 `@AgentTool`。**强制校验**：参数没打 `@ToolParam` 直接抛异常启动失败。

> 为什么这么严？Java 编译后参数名会丢（除非开 `-parameters`），没注解就无法生成正确 JSON Schema。**宁可启动失败，也不要运行时给 LLM 一个错的 schema。**

**为什么用 `ApplicationReadyEvent` 而非 `@PostConstruct`**：MCP 远程工具是客户端连上后才注册进来的，顺序上必须最后。

**统一入口**：

```java
public Object invoke(String name, JsonNode args) {
    ToolDefinition local = tools.get(name);
    if (local != null) return invokeLocal(local, args);           // 反射
    if (mcpTools.containsKey(name)) return invokeMcp(name, args); // MCP 代理
    throw new IllegalArgumentException("未知工具：" + name);
}
```

对 LLM 完全透明——它不知道背后是本地反射还是跨进程 JSON-RPC。**这是抽象设计的关键价值，一定要讲。**

## 3.3 上下文管理：三层记忆

| 层次 | 载体 | 生命周期 | 解决什么 |
|---|---|---|---|
| 短期 | `ConversationMemory`（内存，窗口 30） | 会话内 | 多轮连贯 |
| 长期 | 归档成 `note.type=AGENT_MEMO` | 跨会话 | "记住我的习惯" |
| 工作 | 子代理局部 `List<Map>` | 单次子任务 | 隔离长文档 |

**长期记忆**：会话空闲 30 分钟后由 `SessionArchiveScheduler` 触发，用 LLM 压缩成要点存为特殊类型笔记，下次构造 system prompt 时注入【用户长期记忆】段。

**值得讲的细节**：归档笔记复用 `note` 表而非新建表，用 `NoteType.AGENT_MEMO` 区分，`/note` 列表页主动过滤——**用户不该看到 Agent 的内部记忆**，但它该享受笔记的全部基础设施（向量索引、检索）。这是"复用 > 新建"的取舍。

## 3.4 多用户隔离：ThreadLocal + 跨线程显式传播

`AgentContext` 用 ThreadLocal 存 User + sessionId + depth：

```java
AgentContext.set(user, sid);
try { orchestrator.handleUserTurn(...); }
finally { AgentContext.clear(); }
```

所有工具入口第一行 `User u = AgentContext.requireUser()`，仓储查询带 userId 过滤。**越权读他人数据在架构上不可达**，不依赖每个工具自己记得校验。

**必被追问："子代理在别的线程，ThreadLocal 怎么传？"**

答：**显式传播**。

```java
CompletableFuture.supplyAsync(() -> {
    AgentContext.set(parentUser, parentSid);   // 手动重建
    AgentContext.enterSub();                    // depth++
    try { return runner.run(role, instruction); }
    finally { AgentContext.exitSub(); AgentContext.clear(); }
}, pool);
```

**不能用 `InheritableThreadLocal`**——用的是固定线程池，线程复用，继承语义会让上个任务的 User 泄漏到下个任务。必须每次显式 set + finally clear。

**这个回答能证明你真踩过并想清楚了并发问题。**

# Part 4 · 六大创新点

> 讲法公式：**问题 → 常规做法不足 → 我的方案 → 取舍代价 → 效果数据**。缺一环都显单薄。

## 创新 1 · MCP loopback：让 Agent 自己连自己（优先讲）

**演进过程（讲出来最有说服力）**：

| 版本 | 做法 | 为何放弃 |
|---|---|---|
| v1 | 复用已有本地文件服务代码 | 只是代码复用，没走协议 |
| v2 | 新加 `@AgentTool` 同进程直接调 | 走了捷径，**已有 MCP 骨架被架空** |
| **v3** | **Agent 作为 MCP Client 连本机自己的 Server** | 采用 |

**v3 调用链**：

```
LLM 决定调 mcp.loopback.local.read_document
  → ToolRegistry.invoke() 识别 mcp. 前缀
  → McpToolProxy 解析 serverName=loopback, tool=local.read_document
  → McpSseClient: POST localhost:8080/mcp/message?sid=xxx
     {"method":"tools/call","params":{"name":"local.read_document",...}}
  → [同一 JVM] McpSseEndpoint.handleMessage()
  → McpLocalFileService: 白名单校验 → 按扩展名选提取器 → 长文走摘要
  → 结果经 SseEmitter 沿 SSE 推回
```

**必被问："同进程为什么绕一次 HTTP？不是白加开销？"**（背下来）

> 确实多一次本机回环，实测 5ms 以内，相比文档解析和 LLM 摘要可忽略。换来三件事更值：
>
> **一、协议栈是真通的。** Server 和 Client 两套代码都在这条链路被真实验证——SSE 建连、initialize 握手、tools/list 发现、tools/call 调用全套跑通。走捷径的话这两套骨架只是摆设，真接外部服务器时才暴露问题。
>
> **二、扩展零成本。** 接第三方 MCP Server 只需配置里加一个 server 条目，代码路径完全一样，工具自动以 `mcp.<server>.<tool>` 出现在工具列表。
>
> **三、它暴露了真实的协议 bug。** 正因走真协议，我才发现服务端返回 endpoint 是相对路径而 Java HttpClient 不接受相对 URI。走捷径的话这 bug 会潜伏到接外部服务器那天。

**主动承认限制（加分）**：

> loopback 连接在启动时建立并长期复用，绑定的是 token 持有者身份，和"当前对话用户"是两个独立身份。对"读本机白名单目录"可接受，因为白名单本身是全局配置。多用户隔离部署需改成按对话用户动态签发临时 token——这个我在设计文档里标注了是后续增强。

## 创新 2 · Reflexion × CRAG 双闭环

**Agent 有两类失败，通常只处理了一类**：

| 失败类型 | 现象 | 机制 |
|---|---|---|
| 工具**坏了** | 抛异常/参数错/工具不存在 | **Reflexion**：错误 JSON 回灌自纠 |
| 工具**好了但没查到好东西** | 检索成功但命中质量差 | **CRAG**：改写重检索/降级明示 |

第二类的典型后果：**检索返回一堆低相关片段，LLM 拿着编出看似有据的错误答案**——比明确说"我不知道"危险得多。

**CRAG 状态机**：

```
检索 → gradeByScore(topHit 融合分数)
  score ≥ 0.6  → CORRECT    直接用
  0.4 ≤ s <0.6 → AMBIGUOUS  改写重检索，融合去重
  score < 0.4  → INCORRECT  改写重检索；仍不行 → degraded=true
```

**核心：把"提示词软约束"升级为"运行时硬闭环"**

原来提示里写"最高分低于 0.4 要说明未找到强相关笔记"——**软约束，LLM 可能不遵守**。

现在检索工具返回值第一项是结构化元信息：

```json
{
  "_meta": "crag",
  "grade": "INCORRECT",
  "degraded": true,
  "hitCount": 3,
  "usedQueries": ["原查询", "改写1", "改写2"],
  "message": "检索质量差：请在答复首句明示\"未找到强相关笔记，以下基于通用知识：\"，不要假装命中。"
}
```

**`message` 不是给人看的，是给 LLM 的行动指令**。质量评估在服务端确定性完成，LLM 只负责按指令措辞。

**取舍**：默认走零 LLM 成本的分数判级，LLM 判级留成可选开关。改写重检索**上限严格 1 次**防延迟放大，且只有低分分支才付出改写成本。

## 创新 3 · 场景驱动的语义查询缓存

**通用 RAG serving 的查询缓存命中率通常不高**，因为查询千变万化。

**我的观察**：个人知识库场景不同——**同一用户会反复问语义相同的问题**（"Kafka 消费者组是什么" / "跟我说说 Kafka 的消费者组"）。这个场景特性让语义缓存收益远高于通用场景。

```java
for (CachedQuery cq : userQueue) {
    if (EmbeddingClient.cosine(queryVec, cq.queryVec()) >= 0.93) {
        return Optional.of(cq.hits());   // 命中，跳过全表 cosine
    }
}
```

**必答追问："0.93 怎么定的？误命中怎么办？"**

> 0.93 是偏保守的取值。bge-m3 上同义改写通常 0.93~0.98，不同主题一般低于 0.85，中间地带主要是"相关但不同"的查询。我宁可漏命中（多查一次，只是慢点）也不要误命中（返回错结果，正确性问题）。
>
> 两层兜住风险：一是**写失效**——笔记更新时主动 invalidate 该用户整个查询缓存，内容变了旧结果就是脏的；二是 `expireAfterAccess` 30 分钟兜底。
>
> 更严谨该做离线评测：收集真实查询对、人工标注等价性、画 precision-recall 曲线选阈值。这个我没做，是工程欠账。

**最后这句"我没做"很重要**——证明你知道严谨做法，只是权衡了投入。比硬说"0.93 是调优出来的"安全得多。

## 创新 4 · 角色感知预取

**这是"私域信息"带来的优化，通用 serving 做不到。**

**洞察**：我知道"哪个子代理角色即将运行"。请求要委派给 RESEARCH 子代理时，我确定它接下来一定会做知识库检索。

```java
if (role == SubAgentRole.RESEARCH && instruction != null) {
    ragServing.prefetch(user, instruction);   // fire-and-forget，独立线程池
}
// 子代理真正检索时大概率命中语义缓存
```

**为什么通用系统做不到**：它不知道"谁在用、接下来要干什么"。而我有 Agent 的编排信息——**这是把 Agent 的结构信息反哺给检索层**。

**取舍**：fire-and-forget，失败只打 debug 日志绝不影响主链路。线程池有界队列 + CallerRuns 拒绝策略，最坏退化为同步执行，不会因预取把系统压垮。

## 创新 5 · 前缀字节稳定化 + 上游缓存闭环观测

**先划清边界（关键，否则容易被问穿）**：

> 要先说清楚，真正的 GPU KV-Cache 复用发生在**推理服务端**（vLLM / SGLang / DeepSeek context caching），应用侧做不到那个。我做的是两件应用侧能做的事。

**第一件：turn 级前缀复用（省 CPU）**

原来每步 ReAct 都要 `exportSchemas()` + JSON 序列化 + format 整个 system prompt，一轮走 10 步就做 10 次。

改成拆分 `buildPrefix()` / `assemble()`，前缀 turn 开始时构造一次，10 步复用。跨 turn 有 Caffeine 缓存，key 是四元组：

```java
PrefixKey(mode, toolsetHash, memoHash, dateBucket)
```

- `mode` 变 → 工具集不同必须重建
- `toolsetHash` 变 → 工具增减（如 MCP 重连后）自动失效
- `memoHash` 变 → 长期记忆更新
- `dateBucket` → **天级**而非精确时间

**第二件：字节稳定化（让上游缓存能命中）**

上游 automatic prefix caching 按**前缀字节完全一致**命中。两处修正：

1. **`LocalDate.now()` → `dateBucket()`**：原来嵌了当前日期，精度到秒的话每次请求前缀都不同，上游永远无法命中
2. **`exportSchemas()` 输出排序**：原来遍历 `ConcurrentHashMap.values()`，**迭代顺序不保证**——同样工具集两次序列化可能产出不同字节序！加了一行按名排序

> 第二点是我 review 时发现的隐蔽问题。ConcurrentHashMap 迭代顺序实践中通常稳定但规范上不保证，重哈希后可能变。**这种"大部分时候没问题"的 bug 最难查。**

**第三件：闭环验证（最能体现工程素养）**

做了优化就要能证明有效。解析响应 `usage`：

```java
long hit  = usage.path("prompt_cache_hit_tokens").asLong(-1);      // DeepSeek 风格
long miss = usage.path("prompt_cache_miss_tokens").asLong(-1);
long cached = usage.path("prompt_tokens_details").path("cached_tokens").asLong(-1);  // OpenAI 风格回退
```

暴露成端点：

```
GET /api/agent/prefix-cache/stats
{
  "metrics": {
    "prefixCacheHit": 18, "prefixCacheMiss": 3, "prefixCacheHitRate": 0.857,
    "prefixBuildCount": 3, "avgBuildMs": 3.2,
    "estimatedBuildTimeSavedMs": 57,
    "upstreamPromptCache": {
      "promptCacheHitTokens": 8460,
      "promptCacheHitRate": 0.7255      ← 直接证明字节稳定化生效
    }
  }
}
```

**`promptCacheHitTokens > 0` 是唯一能证明"前缀字节稳定化真让服务端缓存命中"的客观证据。** 被问"怎么知道有效"就给这个数。

## 创新 6 · 上下文隔离的子代理

**问题**：主对话上下文是稀缺资源。Agent 读了 50 页 PDF，原文全进历史，后续几轮就被挤爆。

**方案**：Orchestrator-Worker。三角色各自在**独立上下文**跑完整 ReAct，只回压缩结论。

| 角色 | 工具 tag 子集 | 产出约定 |
|---|---|---|
| 规划专家 | mcp, kb, planner, task, goal | 3~6 行"建了什么目标、拆了几个任务" |
| 复盘专家 | insight, task, goal, note, kb | 【亮点】【问题】【下一步建议】 |
| 检索专家 | kb, note, mcp | 有出处的综合答案 |

**关键约束**：
- 结论截断 `result-max-chars=4000`
- **子代理不能再委派子代理**：`guardTopLevel()` 检查 `depth() > 0` 抛异常，防指数级放大
- 每角色 `maxSteps=6`，独立于主循环的 24
- 工具 tag 是**最小必要子集**——tag 过滤是 OR 语义，所以只声明领域 tag（task/goal/kb），不放通用的 read/write，否则会命中所有工具，隔离失去意义

**并行 fan-out**：`subagent.parallel_research` 把问题拆成多个子问题并发研究，`allOf().orTimeout()`，超时未完成的 worker 汇总时标注降级，**不整体失败**。

## 创新 7 · 工具运行时可见性：分层遮蔽（参考 DeepSeek Harness）

**问题**（个人场景的真实痛点）：

> 个人场景有个特点：同一个用户在不同思维模式下，Agent 的权限**应该**不同。学习模式只想让它帮我查笔记，不希望它顺手改任务；执行模式又必须能写。

原来的做法是给工具打 tag 按模式过滤，但我发现两个问题：

1. **tag 过滤是 OR 语义的并集放行，只能"放行"不能"禁止"**。`note.create` 同时带 `note` 和 `write` 两个 tag，learn 模式放行了 `note`，它照样能写笔记——这是个真实的 bug，潜伏了很久。
2. **更严重的是，过滤只影响给 LLM 的 schema 列表，不影响执行**。模型如果从上下文记得 `task.create` 这个名字，直接调用是能调通的，因为 `registry.get()` 查的是全量注册表。**所以它是提示层约束，不是执行层约束**。

**方案**：四层 scope 链

```
GLOBAL（全量）→ MODE（模式）→ ROLE（子代理角色）→ SESSION（会话）
```

运行时实时算出"当前能看到哪些工具"，支持**显式 deny**（禁止）和**显式 pin**（破例），每个工具都能给出可解释的决策链。

**执行层强制**（最关键的一环）：

> 工具存在但当前不可见 → 短路返回 `TOOL_NOT_VISIBLE`，不真正执行。这和我之前做的 Reflexion 封禁刚好组成**两层权限治理**——可见性决定"你本来能碰什么"，Reflexion 封禁决定"你这轮已经把什么碰坏了"。

**必讲的取舍（体现不是照搬）**：

> 我参考了 DeepSeek Harness 的分层遮蔽，但它其实解决两件事：插件化实现替换、可见性收窄。我只需要后者——我的工具是注解扫描的，一个名字唯一实现，"替换实现"在我这没有落点，硬做就是过度设计。所以我刻意裁剪掉了它。

**连带修掉两个隐患**：

- **幻觉率被高估**：原来"工具不存在"和"工具存在但越界"混算进 `hallucinationRate`，现在分开埋点（`notVisibleBlocked` vs `unknownTools`）。
- **同名遮蔽**：本地工具和 MCP 工具可能同名，原来 `get()` 本地优先但 `exportSchemas()` 两个都导出，LLM 看到两个同名条目。现在显式化成"本地优先、MCP 不重复导出"。

**子代理继承**：learn 模式委派 PLANNER 子代理，写工具仍不可见——模式边界不能被子代理绕过。子代理的 `subagent.*` 工具是**结构性保留**，无条件不可见（从 prompt 软约束升级为可见性硬边界）。

## 创新 8 · 轮次收尾解耦：TurnStopping + 粘性降级标记

**问题一：收尾时机硬编码**。ReAct 循环里"什么时候算结束"是写死的——模型没输出工具调用就 `sendDone` 返回。想加任何"还没完"的理由，都得改主循环。

**问题二：信息丢失是静默的**。工具结果超过 4000 字符就硬截断，切掉了 LLM 不知道、用户更不知道。

**方案**：两个机制

**① 收尾顾问（TurnStoppingAdvisor）**：

> 轮次真正关闭前广播一次，顾问可以返回一条 steer 消息让循环继续。这样"还没完的理由"变成可插拔的，主循环不需要预先知道有多少种。
>
> 我落了两个顾问：**降级明示**——本轮发生过截断/降级但答复没说明，强制补一句诚实声明；**主动衔接**——复盘收尾前检查明日待办，够多就追问"要不要帮你排期"。
>
> 失控防护是重点：steer 会让循环 continue，最大风险是无限循环 + 无限烧钱。我把单轮 steer 上限做在 Bus 里强制执行，顾问绕不过去，还专门写了"每次都返回非空"的恶意顾问测试桩验证。

**② 粘性降级标记（TurnOutcome）**：

> 参考 DSH 的"max-tokens 状态粘性"：本轮只要发生过截断、CRAG 降级、子代理截断、工具封禁，就置一个**只能置位不能清除**的 degraded 标记。后面正常收敛不得把轮次洗白。
>
> 这顺带修正了一个偏乐观的指标：原来的收敛率把"中途丢过数据但最后蒙对了"也算正常收敛。现在多了 `cleanConvergenceRate`，差值就是被高估的部分。

**价值一句话**：

> 在还没能力"不丢信息"之前，先做到"不隐瞒信息丢失"。

**保守化改造（体现判断力）**：

> DSH 还有个 `concludesTurn` 工具提前收尾特性，能省一次 LLM 调用。我实现了但**默认关闭**。原因是收益/风险比不同：DSH 是 coding agent，工具调用密度高；我这是个人规划助手，一轮通常 2~5 步，省一次调用的收益远小于"用户说'先复盘，再把没做完的顺延到下周'时把第二个意图吞掉"的代价。**同一个特性，场景不同默认值就该不同**。

## 创新 9 · 知识仓库：把「靠自觉的约定」变成「机器门禁」

> 这是最近五期（V4 Codex P0~P4）在做的主线，讲法公式照旧：**问题 → 常规做法不足 → 我的方案 → 取舍代价**。

**问题**：一个人怎么管理"学习一个体系"这件事？三个真实痛点——

1. **我不知道自己不知道什么**：人能列出"待学清单"，但列得出来的已经不是盲区了。
2. **"我懂了"是假的**：看懂了 ≠ 能改能跑。以为懂但不懂，是最危险的一类假掌握。
3. **机器会弄坏我的语料**：让 LLM 帮我整理/产出知识，它一次幻觉就能覆盖我几个月手写的内容。

**我的方案分五期，每一期都有一个"用结构替代自觉"的核心决定**：

| 期 | 能力 | 一个可讲的取舍 |
|---|---|---|
| P0 | Git 仓库四级索引 | **MySQL 是可丢弃的派生索引，Git 是权威源**——重装就能重建，不引入"第二个真相源" |
| P1 | 验证闭环（checkpoint） | **预测门禁**：动手前必须先写预测，因为"改完再解释"人会自动为结果编理由，永远发现不了自己原本想错了 |
| P2 | 沉淀 + PR + 知识 CI | **写入白名单只含 `docs/notes/`**：改既有 guide 在结构上不可能，不是靠 prompt 里写"请别改无关章节" |
| P3 | 缺口三源合流 | **缺口只能来自行为证据**：CRAG 降级 / 当初标了"先跳过"现在被反复问 / 验证失败。刻意不提供 `gap.create` 工具 |
| P4 | 蒸馏 + 定线 | **先看后写**：蒸馏产物先不落盘，用户看完草稿才写入；定线一次 LLM 都不调 |

**最想展开讲的三个决定**（背下来）：

**① 示例门禁是执行层拒绝，不是提示词请求**。沉淀笔记时，如果问答原文里有代码块、而模型把笔记压缩成"见原文示例"，我直接拒绝写入。理由很具体：模型天然倾向于把内容压缩得更"整洁"，被压掉的恰恰是半年后还能重新看懂的部分。**而且这个门禁有指标**——`exampleGateRejections` 一旦不为 0，就直接证明了"只靠 prompt 提醒是不够的"。

**② "先跳过"的止损线必须能被真实解析器抽出，而不是"有那个小节就行"**。止损线是用户写的"遇到再学"清单。我让它的召回依赖一个术语解析器——如果一篇新产的 guide 有小节但抽不出具体术语，它在系统里是**静默失效**的（永远不会触发提醒），从文件本身完全看不出来。所以门禁判据是"解析器真能抽出"而非"看起来有"。

**③ 定线（"我现在该干什么"）一次 LLM 都不调**。因为"投入 60% 学 LLVM"是用户对自己时间的主观分配，机器没有依据去改它；让 LLM 生成一份"建议的阶段表"只会产出一份看起来合理但无法核对的东西，最终被忽略。我做的是**纯计算**——checkpoint 状态、缺口次数、草稿核对状态全在库里，每条建议都附它依据的那条记录。**可核对比更聪明重要。**

**贯穿五期的一条方法论**（这是我最想传递的）：

> 我反复在做一个动作——**把"靠人自觉"的约定升级成"机器强制"的门禁**。笔记必须回挂、示例必须入库、引用必须可达、改动必须审阅、止损线必须可召回……每条原本都是文档里的一句"请遵守"，我逐条做成了执行层的拒绝或 CI 的报错。因为我的经验是：**prompt 提醒失效时是静默的，而门禁失效时会大声拒绝**——前者会让你在很久以后才发现内容坏了，后者当场就拦住了。

# Part 5 · 真实踩坑四则（最有说服力）

> "遇到最难的 bug 是什么"这类问题面试官格外看重，因为**编不出来**。按推荐讲述顺序排列。

## 坑 1 · MCP loopback 永远连不上：相对 URI（首推）

**现象**：Agent 说"无法读取本地文件"。但配置全对——`local-files-enabled=true`、白名单默认整个用户主目录、Server 端手工 curl 测过完全正常。

**排查路径**：
1. curl 直连 `/sse` → 正常返回 endpoint 事件
2. curl 手工发 `tools/list` → 正常返回，`local.read_document` 在列表里
3. 说明 **Server 端没问题，问题在 Client 端**
4. 翻启动日志，发现一行被淹没的 warn：`Server loopback 启动时连接失败，将在健康检查时重试`
5. 30 秒一次的健康检查也在重试失败 → **loopback 从来就没连上过**

**根因**：服务端发 endpoint 事件给的是**相对路径**：

```java
.data(messagePath + "?sid=" + sid)   // "/mcp/message?sid=xxx"
```

客户端直接拿它建请求：

```java
.uri(URI.create(messageEndpoint))    // 相对 URI
```

**Java `HttpClient` 不接受相对 URI**，抛异常 → `initialize` 握手失败 → 连接标记失败 → 工具永不注册 → LLM 调用时得到"未知工具"。

**修复**：客户端收到 endpoint 时用 SSE 的 base URL 补全：

```java
private String resolveAbsoluteUrl(String raw) {
    URI uri = new URI(raw);
    return uri.isAbsolute() ? raw : baseUrl + raw;   // baseUrl = scheme + authority
}
```

**这坑能讲出三层价值**：
1. **分治定位**：先用 curl 隔离是 Server 还是 Client 的问题，避免两头乱猜
2. **日志级别的教训**：连接失败只打 warn 且措辞是"将重试"，看起来像暂时性问题，实际是永久失败。**这种"看起来会自愈但其实不会"的日志最容易漏**，应在重试 N 次后升级为 error
3. **回到设计**：正因坚持走真 MCP 协议才提前暴露这 bug，走捷径会潜伏到接第一个外部服务器那天

## 坑 2 · Self-RAG 链路"看起来通了其实断了"

**现象**：CRAG 三个组件都实现了、单独测都对，但 Agent 在检索质量差时**还是假装命中**，编造有据的答案。

**根因**：元信息只在零命中时返回。

```java
if (out.isEmpty()) {          // ← 只有空结果才附加 grade/degraded
    meta.put("grade", ...);
    meta.put("degraded", ...);
}
```

而"**有命中但质量差**"恰恰是最需要降级信号的场景——此时 `hits` 非空走不进这个分支，`grade`/`degraded` 被丢弃。`CorrectiveRetriever` 明明算出来了，就是没传给 LLM。

**修复**：改为无条件返回并置于数组首位。

**这坑揭示一类问题**：

> 每个组件单测都通过，但**组件间的信息传递断了**。这类"集成层缺陷"是单元测试的盲区——需要端到端验证"信号真的到达了消费方"。我后来写验收文档时专门加了一条断言：即使 hitCount>0，grade 和 degraded 也必须存在。

## 坑 3 · 子代理的工具 tag 指向了已下线的工具

**现象**：子代理浪费推理步数，日志里全是 `UNKNOWN_TOOL`。

**根因**：本地文件访问从 Electron 桥迁移到 MCP 后端直读后，旧的 `local.*` 工具被下线（承载类变成空文件）。但子代理角色的 `toolTags` 里还留着 `local`，且 system prompt 明确引导它调 `local.read_file`。同时 `toolTags` 不含 `mcp`，所以它也看不到新的 `mcp.loopback.local.read_document`。

**结果**：子代理按 prompt 指引调一个不存在的工具，必然失败。而主 Agent 的提示里已经明令"严禁调用不含 mcp. 前缀的 local.* 工具"——**两处提示互相矛盾**。

**修复**：`toolTags` 的 `local` 换成 `mcp`，prompt 里工具名同步更新。

**教训**：

> 这是重构留下的"悬空引用"。工具是**用注解+字符串 tag 弱关联**的，编译器查不出来——tag 写错、工具下线，都不会编译报错。这类弱类型关联是灵活性的代价。如果重来，我会加一条启动自检：校验每个角色的 toolTags 至少能命中一个已注册工具，否则启动告警。

## 坑 4 · 指标恒为 0：埋了计数器却没调用

**现象**：写验收文档时想验证"rerank 是否在静默降级"，发现 `RagServingMetrics` 里 6 个计数器有 4 个永远是 0。

**根因**：计数器方法定义了，但**从来没有任何地方调用**。`recordSearch()` / `recordPrefetch()` / `recordRerank()` / `recordRerankFallback()` 全是死方法。

**为什么会这样**：写 metrics 类时是"先把接口定义好"，结果实现业务逻辑时忘了回来接线。而且**没有任何测试或端点消费这些指标，所以恒为 0 也不会被发现**。

**修复**：补齐埋点。同时意识到 `Reranker` 的成功/回退只有它自己知道，所以让它自己注入 metrics 记录，而不是在调用方猜。

**教训**：

> 可观测性不能只是"定义了指标"，必须有消费方。我后来补了 stats 端点，正是因为要在端点上把数字显示出来，才发现它们恒为 0。**没有消费方的指标等于没有指标**——这也是我现在做 metrics 一定同时做暴露端点的原因。

## 坑 5 · 放宽一处白名单，漏掉了一条更早存在的写入路径

**现象**：V4 P4 我新增了 `create-only` 白名单（蒸馏产物目录"只能新建、不能覆盖"），单独测是好的。但回头审代码时发现——**P2 的沉淀服务只校验了路径合法性，没校验覆盖权**，于是 `doc.write(path=蒸馏目录/已有文件, mode=REPLACE)` 能覆盖掉用户手写的论文精读。

**根因**：新增目录进了 `create-only` 白名单后，`checkPath` 开始对它放行；而 P2 的 `SedimentService` 早就用 `TRUNCATE_EXISTING` 写盘、且**只调了 `checkPath`**。新加的目录会记得校验，旧路径不会自己变严。

**教训**：

> 放宽任何一处白名单，必须回头把所有"只做过路径校验"的写入路径都补上覆盖权校验。安全边界不是"加一道新闸门"就完了，而是**每次放宽都要重审所有既有入口**——因为漏洞总是从你最没想到的旧路径漏出来。

# Part 6 · 高频追问与应答

## 关于技术选型

**Q：为什么不用 LangChain / Spring AI？**

> 不是不知道。核心原因是我需要几个控制点，框架要么封装掉、要么要 hack：
> 1. **步数上限与耗尽后的降级措辞**——我要给用户"请拆分任务"的具体指引，不是抛异常
> 2. **工具的分层可见性**——learn 模式不该看到写工具，且要能显式 deny、会话级屏蔽，这是我的业务语义
> 3. **确认策略要能被用户运行时降权**——auto-approve 是用户级配置，不是工具级
>
> 另外这是学习项目，手写一遍 ReAct、工具注册、MCP 协议，收获比调框架大得多。如果是生产项目、团队协作、要快速交付，我会选框架。

**Q：MCP 是什么？为什么用它？**

> Model Context Protocol，Anthropic 提出的标准，让 LLM 应用以统一方式接入外部工具和数据源。传输走 SSE + JSON-RPC 2.0，核心是 `tools/list`、`tools/call`、`resources/list`、`resources/read` 几个方法。
>
> 用它的价值是**双向**的：对外我把系统能力（任务、目标、笔记）暴露成 MCP Server，Claude Desktop 这类客户端可以直接接入我的系统；对内我作为 MCP Client 可以接任何第三方 MCP Server 扩展能力。这比自己定协议更有生态价值。

## 关于并发与正确性

**Q：多用户并发时上下文会串吗？**

> 不会。`AgentContext` 是 ThreadLocal，WebSocket handler 为每次用户输入派生 worker 线程，进入时 set、finally clear。所有工具第一行取 `requireUser()`，仓储查询带 userId 过滤。
>
> 唯一需要特别处理的是子代理——它在线程池里跑，ThreadLocal 不自动传递。我用显式 set + finally clear，**不能用 InheritableThreadLocal**，因为固定线程池会复用线程，继承语义会让上个任务的用户身份泄漏。

**Q：LLM 输出不稳定，工具调用解析失败怎么办？**

> 三层处理：
> 1. **解析层容错**：`ToolCallParser` 剥离 `<think>` 推理段（reasoner 模型会输出）、兼容 Markdown 围栏、从文本里提取第一个合法 JSON 对象
> 2. **协议约束**：system prompt 明确要求"调工具时只输出一个 JSON 对象，不要解释不要围栏"
> 3. **兜底**：解析不出工具调用就当成终态自然语言回复。宁可多说一句话，也不要卡死
>
> 另外最终答复展示前会用 `cleanForDisplay` 再清一遍，防止残留的 tool-call JSON 泄漏给用户。

## 关于性能与成本

**Q：一次对话要调几次 LLM？成本怎么控？**

> ReAct 每步一次，上限 24 步，但实际大多在 2~5 步。控成本的手段：
> - **前缀缓存**：省本地 CPU；**字节稳定化**：让上游 prompt cache 命中，直接降 token 成本（实测命中 token 占比 72%）
> - **语义查询缓存**：命中就完全跳过 embedding 调用和全表 cosine
> - **子代理压缩回灌**：结论上限 4000 字符，防长文档反复进主上下文
> - **rerank 默认关闭**：它要额外一次 LLM 调用，收益不确定时不开
>
> 还有一点：**LLM 判级、LLM rerank、查询改写这些"用 LLM 做辅助决策"的能力我都做成了可选开关**，默认走零成本路径。

**Q：向量检索用全表 cosine，数据量大了怎么办？**

> 现在是万级 chunk × 1024 维，实测约 10ms，够用。我做的优化是用 Caffeine 缓存**反序列化后的 float[]**——因为真正的瓶颈不是 cosine 计算，而是从 MySQL 取出 JSON 再反序列化。
>
> 但我清楚这个方案的天花板：**十万级以上必须换专用向量库**（pgvector / Milvus / Qdrant）。我没引入是因为当前规模不需要，而且引入向量库会带来运维成本和数据一致性问题。这是有意识的技术债，不是不知道。

## 关于设计取舍

**Q：为什么本地文档摄取功能被禁用了？**

> 这是个主动的设计决策。本地文件访问原来走 Electron 桥（渲染进程 IPC），后来迁移到 MCP 后端直读。摄取功能依赖的取文通道随之失效，我选择**先降级为只读**，而不是仓促改一版。
>
> 底层能力其实完整保留——`rebuildForLocalDoc` 可用、表结构支持 `source='LOCAL_DOC'`、检索链路原生支持。恢复只需把取文换成后端直读。我把原实现以注释保留并写了恢复步骤。
>
> **在能力不完整时明确禁用并返回 `WRITE_DISABLED`，比留一个半通的功能让用户踩坑更负责。**

**Q：如果让你重做，会改什么？**

> 三个（后两个已经补上了）：
> 1. **测试先行**。早期几乎没有单测，坑 2 那类"组件间信息传递断了"的问题，有端到端测试能提前发现。后来补了轨迹回放评测体系 + 60 多个单元测试
> 2. **可观测性和功能同时做**。坑 4 就是先写了功能后补指标，导致指标恒为 0 好久没发现
> 3. **工具与角色的关联加启动自检**。tag 是字符串弱关联，编译器查不出悬空引用——现在工具可见性 resolver 已经加了启动自检（引用不存在的 tag 会告警）

## 关于工具可见性与收尾解耦（K/L）

**Q：工具的可见性你是怎么做的？和简单的 tag 过滤有什么不同？**

> 我做了四层 scope 链：全局 → 模式 → 角色 → 会话。关键差异有两个：
> 1. **从"只能放行"到"能显式禁止"**。tag 过滤是 OR 语义，`note.create` 同时带 note 和 write 两个 tag，learn 模式放行 note 后它照样能写笔记——我踩过这个真实的 bug。改成 deny 语义后才能精确禁止 write。
> 2. **从"提示层约束"到"执行层约束"**。过滤只影响给 LLM 的列表，不影响执行——模型凭记忆调不可见工具照样能调通。所以我在执行前再拦一道，返回 `TOOL_NOT_VISIBLE`，不真正执行。

**Q：你参考了 DeepSeek Harness，为什么不直接照搬？**

> DSH 的分层遮蔽其实解决两件事：插件化的实现替换、可见性收窄。我只需要后者——我的工具是注解扫描的，一个名字只有唯一实现，"替换实现"在我这没有落点，硬做就是过度设计。所以我刻意裁剪掉了它，只保留收窄 + deny。这是"吸收而非照搬"的关键。

**Q：steer 机制会不会导致无限循环？**

> 会，所以我把防护做在基础设施层而非指望顾问自律。单轮 steer 次数上限由 `TurnStoppingBus` 强制，顾问绕不过；还加了一道剩余步数保护，避免在最后一步 steer 导致用户什么都拿不到。我专门写了一个"每次都返回非空"的恶意顾问测试桩来验证这个上限真的生效。

**Q：截断信息丢了，为什么不直接放大上限？**

> 因为"丢信息"的根因不是上限太小，而是"丢了没人知道"。放大上限只是推迟问题，且会挤爆上下文。我做的两件事更有价值：一是让截断成为**粘性降级标记**（丢过就是丢过，不能洗白）；二是收尾时若答复没提，强制补一句诚实声明。**在没能力不丢信息之前，先做到不隐瞒。**

# Part 7 · 必须划清的边界（防被问穿）

> **这部分比创新点更重要。** 面试官最反感的是夸大——一旦发现你把"读了 usage 字段"说成"实现了 KV-Cache"，整场信任就崩了。

| 我做的 | 我**没有**做的 | 被问到时怎么说 |
|---|---|---|
| 应用层前缀复用 + 字节稳定化 + 读 usage 观测 | **GPU KV-Cache 复用**（在 vLLM/SGLang 侧） | "真正的 KV-Cache 在推理服务端，应用侧只能保证前缀稳定让它能命中，并读 usage 验证" |
| MySQL 全文索引 + 应用层 cosine + 加权融合 | **专用向量数据库 / ANN 索引** | "万级规模全表 cosine 够用，十万级以上必须换 pgvector 或 Milvus" |
| LLM-as-Ranker（可选，默认关） | **cross-encoder 精排模型** | "不引入新模型依赖，复用已有 LLM 通道实现二阶段精排" |
| 基于分数阈值的检索质量分级 | **训练过的评估模型 / 离线评测集** | "零成本启发式判级。严谨做法是标注评测集调阈值，我没做" |
| 单进程内的 ReAct + 子代理 | **分布式 Agent / 持久化工作流引擎** | "单机单进程，会话状态在内存，重启丢失。生产要用 Temporal 之类的工作流引擎" |
| 语义查询缓存（阈值 0.93） | **阈值的离线评测验证** | "保守取值 + 写失效兜底。没做 precision-recall 曲线，是工程欠账" |
| 分层工具可见性（deny/pin + 决策链） | **工具实现的运行时热替换** | "DSH 那套可逆副作用需要 Cordis 插件运行时 + TS 原型系统，Java 静态类型做不到，而我的场景也不需要" |
| 粘性降级标记 + 降级明示顾问 | **自动补全/恢复被截断的内容** | "我只保证'诚实告知'，不保证'找回丢失的信息'——后者是上下文工程要解决的，用 token 预算 + 滚动摘要" |
| 收尾顾问 steer 机制 | **多顾问并行协商 / 异步事件流** | "顾问是同步的、首个非空胜出，因为 steer 要影响控制流，异步语义会引入竞态" |
| 把约定做成门禁（示例/止损线/覆盖权） | **保证产物内容正确** | "门禁只能挡住'结构不合格'和'写空'，挡不住'写得通顺但内容错'。所以蒸馏产物一律 draft 且必须人工核对——门禁保证产物**值得被核对**，不保证产物正确" |
| 知识仓库索引（四级） | **替代 Git 成为第二真相源** | "MySQL 是可丢弃的派生索引，Git 是权威源；索引坏了重跑一次就重建，这跟'改动必须走 Git 审阅'是同一套立场" |
| 机器出题（EXAMINER） | **把人手写的题也交给机器判** | "机器出的题标 `AGENT_DRAFT`，通过率与人手写的题**分开统计、永不合并**——混在一起会让'通过率'这个无法造假的指标失去意义" |

**三条铁律**：

1. **不确定的数字不要说**。说"实测约 10ms"可以，说"性能提升 300%"就会被追问怎么测的
2. **主动说限制比被问出来好**。"这个方案在 X 场景会失效，我的应对是 Y"——这是成熟度信号
3. **"我没做"是完整答案的一部分**。"严谨做法是 A，我用了简化的 B，因为 C"，这个句式非常有力

# Part 8 · 收尾话术

**如果对方问"这个项目你最大的收获是什么"**：

> 两点。
>
> 第一，**Agent 系统的难点不在"能不能调用工具"，而在"上下文、质量、可控性"这三件事上**。调用工具是最容易的部分。真正花时间的是：上下文怎么不被污染（子代理隔离）、检索质量差时怎么不让 LLM 编造（CRAG 硬闭环）、工具的权限边界怎么治理（分层可见性 + Reflexion 封禁）。
>
> 第二，**做了优化必须能证明有效**。我踩过一个坑：埋了指标却没接线，恒为 0 很久没发现。现在我做任何优化都会同时想清楚"用什么数据证明它生效了"——比如前缀字节稳定化，如果没有 `promptCacheHitTokens` 这个数，我根本不知道它到底有没有用；比如执行层强制拦截，如果没有 `notVisibleBlocked` 这个数，我也不知道"只做提示层"到底够不够。

> 如果您对某一块感兴趣我可以展开——MCP 双向协议的实现细节、CRAG 状态机的取舍、工具分层可见性的遮蔽算法、还是轮次收尾解耦的 steer 机制？
