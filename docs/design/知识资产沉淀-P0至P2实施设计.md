# 一、三个阻塞性前提（必须先修，否则 P0 交付即残废）

## P0-BLOCKER-1 · 切片上限会静默吃掉 2/3 主干内容

```12:12:src/main/java/org/zhzssp/memorandum/feature/pkm/service/NoteIndexService.java
static final int MAX_CHUNKS_PER_NOTE = 64;
```

`64 × 600 = 38,400` 字符上限。`iree-learning-guide.md` 有 107,153 字符 → **只索引前 36%，后 64% 直接消失**，且 `chunk()` 是 `return out` 静默返回，**不记日志、不报警**。

后果极其严重：Agent 会说"我检索了你的知识库"，但 HAL 对象模型、timeline semaphore 那些核心内容根本不在索引里。**这比没有检索更糟——它会让你误以为库里没有。**

### 修法

不是简单调大上限（那会让单篇 178 个 chunk 挤爆检索结果，且 embedding 成本失控）。三层处理：

```
① 分层切片：Git 文档按 ## / ### 标题先切 section，再在 section 内切 chunk
   → 每个 chunk 天然带 heading 路径，检索命中可精确定位到章节 anchor
   → 107K 的 iree guide 按 ## 切约 12 段，每段再切 → 结构化而非平铺

② 上限提到「文档级」而非「笔记级」：
   pkm.rag.chunk.max-per-document=400   （Git 文档，默认 400）
   MAX_CHUNKS_PER_NOTE=64 保持不变      （手写笔记，不影响现状）

③ 触顶必须告警（这是本次真正的修复）：
   触顶时写 WARN + 落 kb_document.truncated=true + 仪表盘红标
   → 延续项目「截断不可静默」原则（方案 L 的粘性降级同一立场）
```

`chunk()` 方法改为**接受 `maxChunks` 参数**，不改默认行为。这样手写笔记路径逐字节不变，Git 文档走新参数。

## P0-BLOCKER-2 · 向量缓存是「全用户 List + 全表 cosine」，加 2900 chunk 会打崩

```91:110:src/main/java/org/zhzssp/memorandum/feature/pkm/service/EmbeddingVectorCache.java
private List<Entry> doLoad(Long userId) {
    List<NoteEmbedding> rows = embeddingRepository.findByUserId(userId);
```

现状：`findByUserId` 取该用户**全部**向量 → 反序列化成 `List<Entry>` → `RagSearchService` 对**整个 List** 做 cosine。

注释里写「单用户万级 chunk × 1024dim 全表 cosine ~10ms」。但那是笔记场景（几百 chunk）。接入一个仓库后：

- 2,900 chunk × 1024 float = **约 11.9 MB 常驻**（float[] + 对象头）
- 接两个仓库（学习 + 工作）→ ~24 MB / 用户
- `maximumSize(32)` 用户 → **最坏 760 MB**，JVM 默认堆直接 OOM

而且现有 `Entry` record **没有 repoId / documentId 字段**，无法按仓库过滤——查一个仓库要扫全部。

### 修法（分两步，不做过度设计）

```
P0 必做（够用）：
  ① Entry 增加 sourceRef（repoId + documentId），支持按仓库/文档过滤
  ② 缓存 key 从 userId 改为 (userId, scopeKey)，scopeKey = "repo:7" | "note"
     → 查仓库文档只扫该仓库的向量，不碰笔记
  ③ maximumWeight 替代 maximumSize，按 chunk 数计权
     pkm.rag.cache.max-vectors=20000（约 80MB 上限，可配）
  ④ 加载失败/超限时降级为「直读 DB + 不缓存」，不是抛错

P4 再考虑（现在不做）：
  倒排 + 向量两级召回、量化压缩（float→int8）。
  2900 chunk 的全表 cosine 实测约 3~5ms，远未到瓶颈。过早优化。
```

**判断依据**：瓶颈是**内存**不是**算力**。所以先解决"别把整个库都装进内存"，而不是优化 cosine。

## P0-BLOCKER-3 · `NoteEmbedding` 的 `noteId NOT NULL` 与 Git 文档语义冲突

```34:35:src/main/java/org/zhzssp/memorandum/entity/NoteEmbedding.java
@Column(name = "note_id", nullable = false)
private Long noteId;
```

现状 `LOCAL_DOC` 用 `noteId=0` 占位（见 `NoteIndexService:185`）。Git 文档若沿用这个 hack，就无法从向量行反查「属于哪个仓库的哪篇文档的哪个章节」——而这是**引用定位**的前提（用户要能点击跳到 `iree-learning-guide.md#46-timeline-semaphore`）。

### 修法

**不改 `NoteEmbedding`**（避免动现有笔记与 LOCAL_DOC 路径），改为**新增独立表 `kb_chunk`**：

| | `note_embedding`（保留不动） | `kb_chunk`（新增） |
|---|---|---|
| 服务对象 | 手写笔记 + LOCAL_DOC 摄取 | Git 仓库文档 |
| 定位能力 | noteId / sourcePath | repoId + documentId + sectionId + anchor |
| 增量判定 | 无（全量重建） | **blobHash**（跳过未变文件） |

`RagSearchService` 增加**第三条通路**（Git 通路），与现有两路并列融合。这样：
- 现有笔记检索**逐字节不变**（评测录制不被破坏，这是硬约束）
- Git 通路可独立开关 `pkm.rag.git.enabled`
- 任一路失败不影响其他（延续现有 try/catch 降级设计）

> **为什么不复用 `note_embedding` 加字段**：它的 `idx_user_source` 索引与 `findByUserId` 全量加载语义已被现有代码依赖，加 repoId 后所有查询都要改，且会让笔记与文档共用一个 LRU 桶（正是 BLOCKER-2 的根因）。分表是更小的改动面。

## 2.5 Git 客户端选型：JGit vs 调系统 git

| | JGit（`org.eclipse.jgit`） | 调系统 `git`（子进程） |
|---|---|---|
| 依赖 | +1 依赖（~3MB） | 0 依赖 |
| 用户环境要求 | 无 | **需装 git**（你已装） |
| 行为一致性 | 自成一套，与 CLI 有细微差异 | 与用户手动操作**完全一致** ★ |
| CRLF / .gitattributes | 需自己配 | 天然一致 ★ |
| 凭证 | 自己管 | 复用系统 credential helper ★ |
| 大仓库性能 | 一般 | 更好 |
| 可测试性 | 可内存仓库 | 需真实 git（可接受，本就要真仓库验收） |

**选调系统 git。** 决定性理由是**行为一致性**：用户会在 IDE 里手动操作同一个仓库，两套 git 实现对 CRLF、ignore、credential 的处理若有差异，会产生极难排查的"软件看到的和我看到的不一样"。

> 实测你的 `core.autocrlf` **未设置**（输出为空）。Windows 下这意味着不做转换——`blobHash` 计算必须用 `git hash-object` 而非自己读文件算 SHA，否则跨平台会不一致。**这是选系统 git 的又一个具体收益。**

风险与对策：
- git 不存在 → 启动自检，`sync_status=ERROR` + 明确提示，**不影响其余功能**（可降级原则）
- 命令注入 → 所有参数走 `ProcessBuilder` 数组形式，**永不拼接 shell 字符串**；路径经白名单校验
- 超时 → 每条命令独立 timeout，默认 60s（clone 300s）

  ├─ 读 repo.yml 的 agent_conventions 声明的文件

## 3.3 受限执行安全设计（本方案风险最高的一环）

我把它做成**五道闸门串联**，任一不过即拒绝：

```
闸门 1｜Mode 隔离
  exec 类工具仅在 AgentMode.VERIFY 可见（复用方案 K 的 ToolView + 执行层强制）
  → 其余 mode 下调用直接返回 TOOL_NOT_VISIBLE，工具不执行

闸门 2｜命令白名单（不是黑名单）
  只允许两种形态：
    a) bash <repo内相对路径>.sh
    b) 白名单可执行文件 + 参数：{git, python, cmake, ninja, mlir-opt,
       iree-compile, iree-run-module, opt, llc, clang, pytest, gradle}
  禁止：管道 | 重定向 > 反引号 $() && || ; 换行
  → 出现任一即 REJECT_UNSAFE_COMMAND（不尝试转义，直接拒）

闸门 3｜路径沙箱
  cwd 必须在 knowledge_repo.local_path 之内（realpath 解析后再比对，防 ../ 与符号链接）
  脚本文件必须存在且在仓库内且被 git 跟踪（未跟踪的脚本 = 不可信）

闸门 4｜人工确认
  requiresConfirm=true，复用 ToolConfirmCoordinator（60s 超时按拒绝）
  确认弹窗必须原文展示：完整命令 + cwd + timeout
  ★ checkpoint.run 不允许加入 auto-approve 白名单（ToolApprovalPolicy 加硬编码例外）

闸门 5｜运行时限制
  timeout（默认 600s，上限 1800s）+ 强制 destroyForcibly
  stdout/stderr 各限 8KB（超出截断并标记，不静默）
  ProcessBuilder 数组形式，不经 shell
  环境变量白名单传递（不透传全部 env，防泄漏 API key）
  并发上限 1（单用户同时只能跑一个 checkpoint）
```

**审计**：每次执行落 `kb_checkpoint_run`，含 `cmd_executed` 与 `approved_by_user`。

**为什么不用容器**：个人单机软件引入 Docker 依赖不现实，且你的 lab 脚本依赖本机 conda 环境（`setup.sh` 装的），容器内跑不通。**如实说明这一点比假装隔离更好**——这是"在用户自己机器上、经用户逐次确认、跑用户自己仓库里被 git 跟踪的脚本"，风险模型接近"用户自己在终端敲这条命令"。

## 3.4 预测门禁的实现

```
checkpoint.run 被调用
  ↓
if (predict_required && status != PREDICTED)
    return {error: "PREDICTION_REQUIRED",
            hint: "该检验要求先写下预测。请让用户在 Checkpoint 面板填写
                   『你认为会发生什么』后再运行。Agent 不得代替用户预测。"}
```

★ **两个反作弊设计**：

1. **Agent 不得代填预测**：`checkpoint.predict` 工具**不存在**。预测只能由用户通过 HTTP 接口（UI 表单）提交，Agent 无工具可用。否则 Agent 会"贴心地"帮你预测，整个机制立刻失效。

2. **预测不可事后修改**：`predicted_at` 一旦写入即冻结，UI 变只读。判定"预测对不对"时对比的是冻结版本。

## 3.5 「通过但预测错」的判定

这是全方案最有价值的信号，但它**无法完全自动判定**（预测是自然语言）。设计为**半自动**：

```
run 结束 → passed=true
  ↓
LLM 判定：把 prediction 与 (expect_result + stdout 摘要) 一起喂给模型
  输出结构化：{consistent: true|false|unclear, divergence: "预测说X，实际Y"}
  ↓
consistent=false → 写 prediction_correct=0
                 → 生成 Gap（source=CP_MISPREDICT）
                 → 建议沉淀 note：「我原以为…实际…」（P2 的 SEDIMENTER 接手）
consistent=unclear → 挂起，UI 让用户自判（一次点击）
```

**如实标注局限**：LLM 判定预测一致性会有误判。所以 `prediction_correct` 允许用户覆盖，且 UI 显示"AI 判定"或"我判定"。**指标口径要写清楚，不能把 AI 判定的准确率说成客观数字。**

## 5.1 三个新 AgentMode（枚举扩充）

```java

## 5.3 检索融合：Git 通路怎么并进去

`RagSearchService` 现有两路 + 新增第三路，**融合逻辑复用现有 merge**：

```

`Hit` record 需要扩字段承载定位信息。**为不破坏现有 record 的位置参数**，加一个可选的 `locator` 字段（`source=GIT_DOC` 时填 `path#anchor`，其余为 null），并把 `Hit` 的构造改为静态工厂 + 保留原 7 参构造。

★ **CRAG 影响**：`kb.semantic_search` 的返回会多出 GIT_DOC 类型命中。`CorrectiveRetriever` 的评级逻辑不变，但 `KnowledgeTools.semanticSearch` 需要在 row 里加 `path` 与 `heading`，让 LLM 能给出精确引用。这会改变工具返回格式 → **必须重录该工具相关的 cassette**，或用新工具名 `doc.search` 承载 Git 检索、`kb.semantic_search` 保持不变。**推荐后者**：零回归，且语义更清晰（kb=笔记，doc=仓库）。

# 九、风险登记（新增/更新）

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | **受限执行破坏用户仓库** | **高** | 五闸门 + 全审计 + 单并发 + 明确告知"等价于你自己敲这条命令" |
| 2 | **改动破坏评测录制** | **高** | 新工具不进既有 mode（只加 deny）；`kb.semantic_search` 返回格式不动，Git 检索走新工具名；每期收尾必跑 `agentEval` |
| 3 | 索引内存膨胀 | 中高 | `max-vectors` 权重上限 + 按 scopeKey 分桶 + 超限降级直读 |
| 4 | embedding 成本 | 中 | 2873 chunk 首次全量约 2873 次（可批量 32 → ~90 请求）；之后 blobHash 增量近零。首次索引前 UI 明示预估量并需确认 |
| 5 | LLM 判定预测一致性误判 | 中 | 允许用户覆盖 + UI 标注判定来源 + 指标口径写清 |
| 6 | 大文件解析 OOM | 中 | 107K 单文件流式读 + 单文档 chunk 上限 + 全局字符上限 |
| 7 | Windows 路径与 CRLF | 中 | 统一正斜杠存储；`blobHash` 用 `git hash-object` 而非自算 SHA（实测 `core.autocrlf` 未设） |
| 8 | **过度自动化掏空方法论** | **高** | 三条硬线：Agent 无预测工具、Agent 不能写 `maturity≥reviewed`、Agent 不能直推 main。**产品文案与代码双重保证** |

风险 2 值得强调：这个项目已有可观的评测资产（cassette + 47 个用例），**任何改动若让 `agentEval` 变红，等于砸掉最有价值的工程资产**。所以本设计里"新工具走新 mode / 新工具名"不是洁癖，是保护既有投资的必要手段。
