# Agent 量化评测体系 —— 工业界方案对标与引入设计

> 起因：2026-09-01 的覆盖度核查发现现有评测**验证的是链路能跑通，不是模型决策正确**。
> 9 个录制盒全部手工编写，收敛率 100% / 幻觉率 0% 这两个数字目前不承载字面含义。
>
> 本文对标 2026 年工业界的 agent 评测实践，给出**可落地到本仓库的分期改造方案**。
> 现状核查详见 `docs/Agent评测体系使用指南.md` §6，本文只讲"接下来怎么做"。

---

## 1. 现状定位：我们在成熟度模型的哪一级

Mastra 的评测成熟度模型分四级，对照下来本项目处在 **Stage 2 的前半段**：

| 级别 | 标志 | 本项目 |
|---|---|---|
| Stage 1 · 手工测试 | 发版前人工点一遍 | 已越过 |
| **Stage 2 · 结构化离线评测** | 固定任务集 + 自动判分 + 能检出回归 | **部分达成**：有任务集和 harness，但判分粒度不足，且录制盒是手写的 |
| Stage 3 · CI 自动化 + 线上监控 | 每次改动跑评测、能力集与回归集分离 | 未达成 |
| Stage 4 · 持续改进 + 治理 | 评测驱动开发、可审计记录 | 未达成 |

**卡住我们的不是工具，是判分粒度。** 现有断言 `calledTool("task.create")` 只问了"模型选对工具没有"，没问"这次调用真的成功了没有"——这正是评测假绿的根因。

---

## 2. 工业界的四个核心思想（及它们各自解决什么）

### 2.1 端状态验证（End-State Verification）—— τ-bench 的核心

> "A benchmark that only checks tool-call syntax or final text would pass agents that look right and do the wrong thing. Verify the end state, not the last message."

τ-bench / τ²-bench 的判分不看模型说了什么，也不严格要求走某条路径，而是：把**参考轨迹**在一个干净的"gold 环境"上重放，得到目标 DB 末态，再和 agent 实际跑出来的 DB 末态**做哈希比对**。任何能产生等价末态的路径都算通过。

SWE-bench 是同一思想的另一种形态——跑仓库的测试套件，而不是比对 diff 文本。

**为什么这对我们特别重要**：这条正好是我们假绿的解药，而且**实现成本几乎为零**——评测已经跑在 H2 上，`task.create` 本来就在写库，我们只是从来没去查过写进去了什么。

### 2.2 pass^k —— 把"能做到"和"稳定做到"分开

| 指标 | 含义 | 用在哪 |
|---|---|---|
| `pass@k` | k 次里**至少一次**成功 → 能力上限 | 代码生成这类"有一个对的就行"的场景 |
| `pass^k` | k 次**每次都**成功 → 可靠性 | 面向用户的 agent |

关键直觉：**单次成功率 75% 的 agent，`pass@3` 看起来是 98.4%，`pass^3` 只有 42%。** 生产风险就活在这个差值里。

我们现在连 `pass^1` 都算不上——回放模式下路径由录制盒固定，跑 100 次结果完全一样，方差为 0 是假象。

### 2.3 轨迹指标的分解 —— 不是"调了没有"而是三个维度

工业界把工具使用拆成三个独立维度，任何一个坏了症状都不同：

| 维度 | 问什么 | 我们现在 |
|---|---|---|
| **调用决策**（invocation） | 该调工具时调了吗？不该调时忍住了吗？ | 部分有（`no_tool_hallucination`） |
| **选择准确率**（selection） | 选对工具了吗？有没有多余调用？ | 只有"调过某工具"的存在性断言 |
| **参数准确率**（parameter） | 参数对吗？隐含参数推断对吗？ | **完全没有** |

> "Parameter extraction mistakes: the agent selects the right tool but passes incorrect or incomplete arguments." —— 这是生产里最常见的**静默失败**来源。我们的 `task.create` 就算把 deadline 解析错了，现在的断言照样通过。

### 2.4 分层判分器：确定性 → LLM 裁判 → 人工

| 判分器 | 适用 | 局限 |
|---|---|---|
| 代码判分 | 客观、可复现的检查 | 对合理的表述变体太脆 |
| LLM-as-judge | 主观维度、开放式输出 | 非确定，**必须对人工标注做校准** |
| 人工 | 校准 LLM 裁判的金标准 | 贵、慢 |

重要提醒（来自 morphllm 的实践总结）：**LLM 裁判适合离线抽样打分，不适合每一轮的在线判定**——后者需要确定性、廉价的标签，那是分类问题，该用分类器而不是裁判。

我们现在 `finalAnswerContainsAny("未找到", "通用知识", ...)` 属于代码判分里最脆的一类字符串匹配：模型换成"你的笔记里没有相关记录"就误报。这一维度应该升级成带 rubric 的裁判。

## 3. 刻意不引入的部分（和裁剪 DSH 是同一套判断）

工业界方案里有相当一部分不适配个人单机项目，硬做就是过度设计：

| 不做 | 原因 |
|---|---|
| 线上 A/B 分流实验 | 单用户，没有能达到统计显著的流量 |
| 人工标注团队 / 标注员间一致性 | 只有我一个人。改为**我自己标 30 条做裁判校准**，并如实报告样本量 |
| 接入 LangSmith / Braintrust / Phoenix | 引入 SaaS 依赖与数据外传；本项目已有自己的 trace 埋点，缺的是判分而非可观测 |
| RAGAS 全家桶（8 个指标） | Python 生态，本仓是 Java。**移植思想不移植依赖**——只自实现 faithfulness 与 context recall 两个最有信息量的 |
| 分布式 / 大规模基准（SWE-bench 量级） | 任务集 20~50 条即可检出大效应量，这是工业界对起步阶段的一致建议 |

## 4. 分期改造方案

### P0 · 端状态验证（不需要 API Key，成本最低，收益最大）

**目标**：把断言从"工具被调用过"升级为"世界被正确改变了"。

**改造点**：

`TrajectoryAssert` 增加端状态断言，背后走已有的 `JdbcTemplate`：

```java
assertThat(trace)
    .calledTool("task.create")
    .endState(db -> db.taskExists(t -> t.title().contains("验收文档")
                                     && t.dueDate().equals(LocalDate.of(2026, 9, 4))));
```

新增一个 `EvalDbProbe`（薄封装，只读）：

```java
public record EvalDbProbe(JdbcTemplate jdbc) {
    List<TaskRow> tasks();          // select * from task where user_id = 1
    List<GoalRow> goals();
    boolean taskExists(Predicate<TaskRow> p);
    int countTasks();
}
```

**同时补一条全局不变量**（这条本身就能防住假绿复发）：

```java
// AgentEvalBase.tearDown 中无条件执行
if (!expectedToolFailures.contains(caseId)) {
    assertThat(trace.failedTools())
        .as("工具执行失败但用例没声明预期失败 —— 极可能是环境/DB 问题而非模型问题")
        .isEmpty();
}
```

**为什么先做这个**：它是唯一一个**不依赖真实 LLM 就能提升信息量**的改造。参数准确率也顺带被覆盖了——deadline 解析错了，DB 里的 `due_date` 就不对。

**工作量**：`EvalDbProbe` + `TrajectoryAssert` 扩展 + 9 个用例补断言，约半天。

---

### P1 · 真实录制 + 多次采样（需要 API Key，一次性成本极低）

**目标**：让收敛率、幻觉率恢复字面含义，并首次获得**可靠性**指标。

**步骤**：

1. `gradlew agentEval -Dagent.eval.mode=record` 用真模型录一遍，覆盖 9 个手写盒
2. 引入**多试次录制**：同一任务录 k 次（k=3 起步），录制盒结构从 `interactions[]` 扩成 `trials[trial][interactions]`
3. `EvalReport` 增加两个指标：

```
pass@k  = (至少一次通过的任务数) / 总任务数     ← 能力
pass^k  = (k 次全部通过的任务数) / 总任务数     ← 可靠性
```

**报告里必须同时列出两个数**，差值就是不稳定度。只报 `pass@k` 是在粉饰。

**注意事项**：录制时 `temperature` 不要设 0。设 0 会人为压掉方差，`pass^k` 就退化成 `pass^1`，指标失去意义。要测的就是真实采样下的稳定性。

**工作量**：录制盒结构改造 + 报告指标，约一天；LLM 调用成本约 27 次（9 任务 × 3 试次），可忽略。

---

### P2 · 轨迹指标分解

**目标**：从"调过某工具"升级到可量化的选择/顺序质量。

在 `GoldenTask` 里声明参考轨迹（借鉴 τ-bench：**它是一条参考路径，不是唯一正确路径**）：

```java
new GoldenTask("create_task_with_deadline")
    .instruction("帮我建一个任务：周五前写完验收文档")
    .referenceTools("task.create")           // 期望集合
    .forbiddenTools("goal.create")           // 明确不该调的
    .maxRedundantCalls(1)
    .endState(db -> ...);
```

计算三个指标：

```
工具选择精确率 = |实际调用 ∩ 期望| / |实际调用|      ← 惩罚多余调用
工具选择召回率 = |实际调用 ∩ 期望| / |期望|          ← 惩罚漏调
顺序一致性     = Kendall's τ(实际子序列, 期望序列)   ← 仅对有依赖的任务启用
```

`Kendall's τ` 用在有强依赖的任务上（如 `goal.create` 必须先于 `task.create`），业界建议以 `τ ≥ 0.85` 作为门禁。本项目大多数任务是单步的，这条**只对多步任务启用**，不要一刀切。

**类别平衡是重点**：工业界反复强调不要只测"该调工具时调了"，否则会训出一个"什么都要调工具"的 agent。任务集里必须有**明确不该调工具**的负例——我们已有 `no_tool_hallucination` 和 `mode_isolation_learn`，需要再补几条。

---

### P3 · LLM-as-judge（带校准，这是可信度的关键）

**目标**：替换脆弱的字符串匹配，量化"诚实性"这类主观维度。

**唯一真正需要裁判的维度是「降级明示」**——这恰好是本项目最重要的那条底线断言：

```
rubric: 检索质量差时，答复是否明确告知用户"未找到相关笔记/以下基于通用知识"？
  2 = 明确告知，且没有把通用知识伪装成用户的笔记
  1 = 隐晦提及，用户可能看不出来
  0 = 完全没提，或假装命中
  U = 无法判断（逃生舱）
```

**三条必须遵守的纪律**：

1. **给裁判一个 `Unknown` 逃生舱**。不给的话它会为了填格子而编分数。
2. **必须对人工标注做校准，并把一致率写进报告**。我自己标 30 条，报告里写明"裁判-人工一致率 0.87（n=30，单标注者）"。样本量和单标注者这两个限制要如实说——这比假装有标注团队诚实得多。
3. **裁判只跑离线抽样，不进 CI 每次跑**。成本与方差都不可控。

**判分器分层的最终形态**：

| 维度 | 判分器 | 跑在哪 |
|---|---|---|
| 端状态正确 | 代码（DB 断言） | 每次 CI |
| 工具选择/顺序 | 代码（集合与序列运算） | 每次 CI |
| 不泄漏内部表示 | 代码（正则） | 每次 CI |
| **降级明示诚实度** | **LLM 裁判 + rubric** | 夜间 / 发版前 |
| 答复有用性 | LLM 裁判（可选） | 发版前 |

---

### P4 · RAG 质量单独度量（移植 RAGAS 思想，不引依赖）

**核心原则**（这条最值得讲）：**检索质量与生成质量必须分开报告，一个混合数字是陷阱。**

只自实现两个最有信息量的指标：

| 指标 | 需要参考答案吗 | 怎么算 | 抓什么失败 |
|---|---|---|---|
| **faithfulness**（忠实度） | 否 | 把答复拆成若干 claim，逐条问裁判"这条能否由检索到的 context 推出" | **幻觉**——拿低相关片段编出有据的答案 |
| **context recall**（上下文召回） | 是 | 参考答案的每个要点，是否都能在检索到的 context 里找到 | **检索漏召**——右文档到了但关键那句没到 |

分工正好对应两种运行时机：
- faithfulness **无需参考答案**，可以在真实对话上持续跑
- context recall **需要金标集**，只在 CI 对金标集跑

**金标集规模**：工业界建议 RAG 场景 100~200 条起步。本项目是个人知识库，语料规模小得多，**先做 30~50 条**，但必须覆盖三类问题：

1. 单跳（库里有直接答案）
2. 多跳（要综合多条笔记）
3. **不可回答 / 越界**（库里根本没有）← 最重要，测的是拒答行为

第三类正是本项目 `kb_search_degraded` 守的那条线，工业界同样把它列为"最容易被忘掉的两类问题之一"。

---

### P5 · 效率与成本纳入门禁

> "Agents that solve tasks correctly but consume 10x more tokens than necessary are not production-viable."

`CollectingTraceListener` 已经能拿到 usage，只需汇总进报告：

| 指标 | 门禁建议 |
|---|---|
| 每任务 LLM 调用数 | 回归集不得较基线上升 > 20% |
| 每任务 token 数（prompt / completion 分列） | 同上 |
| 每任务预估成本 | 记录，暂不设门禁 |
| 端到端延迟 P50/P95 | 记录，暂不设门禁 |

**并把评测自身的成本也记为一个指标**——裁判调用是要花钱的，别让评测比被测系统还贵。

## 5. 两套任务集：能力集 vs 回归集

工业界的一条重要实践，我们目前只有一套混在一起：

| 套件 | 目标通过率 | 作用 | 何时跑 |
|---|---|---|---|
| **回归集** | 接近 100% | 防止倒退，**通过率掉了就是 bug** | 每次 PR |
| **能力集** | 低通过率（30~60%） | 给自己一座要爬的山，**通过率高了才有进步空间** | 夜间 / 发版前 |

**流转规则**：能力集里稳定通过的任务**毕业**进回归集；回归集里连续多月 100% 且不再变化的任务**退休**（避免评测饱和——一个全绿的套件能追踪回归，但对改进没有任何信号）。

对本项目，能力集应该放这些现在**做不到或不稳定**的场景：
- 多步规划（读文档 → 拆目标 → 建 N 个任务）的端状态正确性
- 长对话（30+ 轮）后早期约束仍被遵守 ← 直接复用上下文工程基准的场景
- 委派子代理后结论回灌的完整性
- 中途改变意图（"算了，先别建任务，先帮我查笔记"）

══════════════════════════════════════════════════════════════
  端状态正确      回归 18/18 (100%)   能力 5/12 (41.7%)
  pass@3          回归 100%           能力 58.3%

  参数准确率      0.89    （端状态比对推导）

## 7. 落地顺序与优先级

| 期 | 内容 | 依赖 | 工作量 | 收益 |
|---|---|---|---|---|
| **P0** | 端状态验证 + failedTools 全局不变量 | 无 | 半天 | **最高**：直接消灭假绿，不需要 API Key |
| **P1** | 真实录制 + pass@k/pass^k | API Key | 一天 | **高**：让现有指标恢复含义，首次获得可靠性数 |
| **P2** | 轨迹指标分解 + 负例补齐 | P1 | 一天 | 中高：定位"为什么不对" |
| **P3** | LLM 裁判 + 人工校准 | P1 | 两天 | 中：替换脆弱字符串匹配 |
| **P4** | RAG faithfulness / context recall + 金标集 | P3 | 三天 | 中：检索与生成分开归因 |
| **P5** | 成本延迟门禁 + 能力/回归分离 | P2 | 半天 | 中：防止"对但太贵" |

**强烈建议先做 P0 再做别的**：它不花钱、不依赖外部，而且做完之后现有的 9 个用例信息量立刻翻倍。

## 8. 引入后能诚实宣称什么

改造完成后，下面这些话才站得住：

- "我的 agent 在 30 个任务上 `pass^3` 是 X%"——**可靠性**，不是单次运气
- "工具选择精确率 0.94，多余调用主要集中在 kb.semantic_search"——**可定位**
- "检索 context recall 0.78，说明漏召是主要瓶颈，不是生成幻觉"——**检索与生成分开归因**
- "降级明示诚实度 1.87/2，裁判与我的人工标注一致率 0.87（n=30，单标注者）"——**带校准和样本量限制**

同时**仍然不能宣称**：

- 线上真实用户的效果（没有流量做 A/B）
- 裁判的判断等同人类共识（只有单标注者校准）
- 覆盖了 MCP loopback / 语义缓存 / 子代理（除非单独补，见覆盖度核查）
