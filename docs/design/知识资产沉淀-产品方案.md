# Lattice Codex · 知识资产沉淀产品方案

> 目标：把 Lattice-Planner 从「目标/任务/笔记管理 + Agent 规划」升级为
> **以工作流为原料的个人知识资产流水线**（Personal Knowledge Ops）。
>
> 本文只做产品方案与架构设计，不含代码实现。**请在文末「决策表」勾选分期，我再出实施计划。**

---

# 一、判断：为什么不是「再加一个 Wiki」

## 1.1 大厂知识资产沉淀的真实精髓

先说清参照物。互联网大厂每个组都在做「知识资产沉淀」，但真正起作用的**从来不是"有一个 wiki 空间"**——那东西每个公司都有，且大部分是坟场。真正有效的机制是这六条：

| 机制 | 具体形态 | 失效时的表现 |
|---|---|---|
| **沉淀嵌进工作流** | 需求上线/故障复盘/技术评审**结束时强制产出**文档，不是"有空再写" | 写文档变成额外负担 → 没人写 |
| **模板化结构** | COE 必须有「现象-根因-止损-改进项」；SOP 必须有「前置条件-步骤-回滚」 | 一堆散文随笔 → 无法检索复用 |
| **Owner + 生命周期** | 每篇有 owner，有 review 周期，过期打「待更新」，废弃走 deprecated | 文档腐化 → 读到过期内容比没文档更糟 |
| **结构化组织** | 知识地图 / 领域树 / 新人上手路径，而不是平铺列表 | 只有仓库没有体系 → 新人不知道从哪读 |
| **复用闭环** | 遇到问题**先搜历史**，命中即复用；没命中就沉淀一篇新的 | 同一个坑踩 5 次 |
| **可度量** | 覆盖率、腐化率、**被引用次数** | 无法判断哪些资产值钱 |

**结论：知识沉淀的难点不在存储，在于「沉淀动力」与「保鲜维护」。** 这两件事恰好是 LLM Agent 最能发力的地方，也是本项目相对 Notion/Obsidian/飞书知识库的**唯一可赢的切口**。

## 1.2 本项目独有的杠杆（差异化定位）

通用知识库软件的死穴：**它不知道你在干什么**。用户必须自己判断"这件事值得沉淀"、自己起草、自己归档。

Lattice 不一样——它手里握着别人没有的东西：

```
已有资产                          可转化为
────────────────────────────────────────────────────
Task 执行轨迹（完成/搁置/超期）  →  "这类事情怎么做" 的 SOP 原料
Goal 推进过程 + 里程碑           →  "这个方向的全景" 的综述原料
RETROSPECTIVE 复盘笔记           →  "踩过什么坑" 的 Pitfall 原料
Agent 对话历史 + 工具轨迹        →  "怎么解决 X 问题" 的 Solution 原料
CRAG degraded 信号 ★             →  "我不知道什么" 的知识缺口清单
本地文档摄取（MCP 直读）         →  外部资料的结构化吸收
insight 得分体系                 →  知识体系完整度的度量载体
```

★ 这一行是整个方案里我最看重的连接点：**现有 CRAG 已经在判定"检索质量差"，但这个信号目前只用来让 Agent 降级措辞，用完就丢。它其实是一份免费的、真实的、按频次排序的个人知识缺口台账。**

所以定位是：

> **不做"笔记软件 + AI"，做"从执行轨迹自动炼制知识资产、并主动维护知识体系健康度的个人知识运营系统"。**
>
> 一句话卖点：**沉淀成本趋近于零，因为原料是你本来就在产生的工作流数据。**

版本叙事：`V1 任务管理 → V2 目标/洞察 → V3 Agent 助手 → V4 知识资产操作系统`

模块命名建议 **Codex**：Lattice（晶格）的知识层——域树是晶格骨架，资产是格点，关联是键。与项目名同源。

# 二、核心概念模型

## 2.1 最关键的一刀：原料 / 成品二分

这是整个方案的骨架，**其他所有设计都从这一刀派生**。

| | **Note（原料层，已有，不改）** | **Asset 知识资产（成品层，新增）** |
|---|---|---|
| 心智 | 收集箱、草稿、摘录、随手记 | 组 wiki 里的正式文档 |
| 质量要求 | 无。想到就写 | 有模板、有结构、有出处 |
| 生命周期 | 无。写完就躺着 | owner + review 周期 + 版本 + 废弃 |
| 组织方式 | tags + `[[双链]]` | **挂在知识域树下** + 关联图 |
| 数量级 | 多而杂 | 少而精（10 篇 Note 炼 1 篇 Asset） |
| 谁来写 | 人 | **Agent 起草 → 人采纳** |

> **为什么不直接给 Note 加字段？**
> Asset 需要 10+ 个 Note 完全不需要的字段（maturity / owner / reviewDueAt / version / staleness / reuseCount / domainId / templateType）。塞进 Note 会把它变成上帝表，且污染现有笔记列表语义。
> 但**检索与渲染管道必须共用**：`note_embedding.source` 字段本来就是为多源设计的（已有 `NOTE` / `LOCAL_DOC`），加一个 `ASSET` 正是它的设计初衷 —— 于是 Hybrid 检索、CRAG、MarkdownRenderer、`[[双链]]` 解析**全部零成本复用**。
> **新建表 + 共用管道**，这是架构红利最大化的取法。

## 2.2 六个一等公民

### ① Asset（知识资产）

模板类型 `AssetType`（决定 required sections，是 Agent 能自动填槽的前提）：

| 类型 | 回答什么问题 | 模板槽位 | 大厂对应 |
|---|---|---|---|
| `SOP` | 「怎么做 X」 | 适用场景 / 前置条件 / 步骤 / 校验 / 回滚 | 操作手册、Runbook |
| `SOLUTION` | 「X 我是怎么解决的」 | 问题 / 约束 / 方案 / 权衡 / 结果 | 技术方案文档 |
| `PITFALL` | 「X 有什么坑」 | 现象 / 根因 / 规避 / 触发条件 | 踩坑库、FAQ（**复用率最高**）|
| `POSTMORTEM` | 「X 为什么失败」 | 时间线 / 根因 / 影响 / 改进项 | COE / 故障复盘 |
| `CONCEPT` | 「X 是什么」 | 定义 / 要点 / 常见误区 / 关联概念 | 概念卡（**学习场景主力**）|
| `DIGEST` | 「X 领域全景」 | 脉络 / 子主题 / 推荐路径 / 关键资产索引 | 领域综述、新人地图 |
| `CHECKLIST` | 「X 别漏了什么」 | 检查项 + 判定标准 | 上线检查单 |

成熟度 `Maturity`（**沉淀是渐进的，不能只有"有/没有"两态**）：

```
SEED（种子：一句话/一个链接，Agent 自动产出）
  → DRAFT（草稿：结构齐了但未校核）
  → REVIEWED（已核：人工确认过内容正确）
  → STABLE（稳定：可放心复用，进推荐池）
  → DEPRECATED（废弃：保留可查，检索降权）
```

关键约束：**Agent 只能产出 SEED / DRAFT，`REVIEWED` 及以上必须人工推进。** 这既是防幻觉的护栏，也延续项目既有的 `requiresConfirm` 哲学。

### ② Domain（知识域树）

资产必须挂域，这是「仓库 → 体系」的分界线。
- 工作场景 = 系统/模块树（如 `后端/Spring/事务`）
- 学习场景 = 学科树（如 `AI/Agent/上下文工程`）
- 每个域可挂一份 **Outline（标准大纲）**：Agent 生成的"这个域应该掌握哪些主题" → 与已有资产比对即得**覆盖率**。

> **「构筑完整知识体系」的可操作定义 = 域树 × Outline 覆盖率 × 关联密度。** 没有这个定义，"体系"就只是形容词。

### ③ Provenance（溯源）

资产的每个结论挂来源：`(sourceType, sourceId, locator, excerpt)`，来源可为 `TASK / GOAL / NOTE / LOCAL_DOC / CHAT_SESSION / EXTERNAL_URL`。

不复用 `Link` 表，因为需要 `locator`（chunk 下标/行号/时间戳）与 `excerpt`（原文片段快照）。

三个作用：抗幻觉可核对、原始来源变更时能算腐化、资产详情页可展示"这句话哪来的"。

### ④ Gap（知识缺口）

`(question, hitGrade, askCount, firstAsked, lastAsked, status, domainId, closedByAssetId)`

写入时机（**全部是现成信号，无需用户额外操作**）：
- `kb.semantic_search` 返回 `grade=INCORRECT` 或 `degraded=true`
- 同一语义问题反复问（向量聚类合并 askCount）
- Outline 里存在但无资产覆盖的主题
- 用户显式标记「这个我不会」

### ⑤ Mastery（掌握度，仅 CONCEPT/SOP 类）

`(assetId, level, lastExaminedAt, nextReviewAt)` + SM-2 间隔重复。让学习场景形成「学 → 检验 → 复习 → 巩固」闭环，而非只是收藏。

### ⑥ Revision（版本）

全量存历史正文。个人量级下全量最简单可靠，无需 diff 存储。

# 三、四个闭环（方案的真正主体）

概念模型只是名词，**产品价值全在这四个闭环里**。它们合起来构成飞轮。

```
                 ┌─────────────────────────────────────┐
                 │                                     │
      ①收割 Harvest                              ④复用 Reuse
   执行完成 → 自动起草资产                  新任务 → 主动推送历史资产
                 │                                     │
                 ↓                                     ↑
            ┌──────────────────────────────────────────┐
            │        知识资产库（域树 + 资产 + 关联）      │
            └──────────────────────────────────────────┘
                 ↑                                     │
                 │                                     ↓
      ③策展 Curate                               ②缺口 Gap
   定期巡检：腐化/重复/孤岛/空洞          问不出来 → 记缺口 → 转学习计划
                 │                                     │
                 └─────────────────────────────────────┘
```

## 闭环 ① Harvest：执行 → 沉淀（**产品的心脏**）

**解决的是"沉淀动力"问题——大厂 wiki 死掉的第一原因。**

```
触发（复用已有事件总线，core 层零改动）
  TaskCompletedEvent / TaskArchivedEvent / Goal 里程碑达成
  / RETROSPECTIVE 笔记落库 / 会话归档（SessionArchiveScheduler）
        ↓
【收割价值判定】（先规则后 LLM，省钢）
  规则预筛：任务跨度 ≥ N 天 / 关联笔记 ≥ 2 篇 / 曾被搁置（说明有阻塞=有坑）
           / 会话内工具失败后成功（说明有解法）
        ↓ 通过预筛的才喂 LLM
  HARVESTER 子代理：判断类型（SOP? PITFALL? SOLUTION?）+ 按模板填槽 + 挂溯源
        ↓
【收割收集箱 Harvest Inbox】—— 日常主入口
  草稿卡片流：标题 + 类型 + 3 行摘要 + 溯源 + 建议归属域
  用户三选一：✅采纳(→DRAFT) / ✏️编辑后采纳 / ❌丢弃(记负反馈)
```

**设计红线：Agent 绝不直接写入正式资产。** 理由不是保守，是产品生死线——知识库一旦被 AI 幻觉污染，用户会**永久失去对整个库的信任**，此后所有检索结果都要人工复核，产品价值归零。草稿态 + 一键采纳是唯一可持续的形态。

**成本红线：单张卡片的决策成本必须 ≤ 3 秒。** 卡片必须默认折叠正文、必须预填归属域、必须支持批量采纳。若用户需要读完全文才能决定，收集箱会在一周内被放弃。

## 闭环 ② Gap：提问 → 缺口 → 学习（**学习场景主线**）

```
kb.semantic_search 判 degraded/INCORRECT
        ↓ （现有信号，目前用完即丢）
写入 knowledge_gap（同语义问题按向量聚类合并 askCount）
        ↓
周期聚合（复用晨报/晚报通道）：
  "本周你 4 次问到「Agent 上下文压缩」，知识库都没答上"
        ↓
一键 gap.to_learning_plan
  → 复用已有 PlannerAgentService 生成学习目标 + 任务
  → 复用已有 Goal/Task 体系执行
        ↓
学完产出 CONCEPT 资产 → gap.status = CLOSED（closedByAssetId 回填）
        ↓
下次问同一问题 → 命中自有资产（grade=CORRECT）→ degraded 率下降
```

**这是全方案闭环最漂亮的一环**：把"检索失败"从一个负面事件转化为产品的驱动燃料，且**首尾都能被现有指标量化**（`degraded` 率下降 = 知识体系真的在长）。

## 闭环 ③ Curate：维护 → 保鲜（**决定库是否活着**）

CURATOR 子代理定期巡检（复用现有调度器），五类问题：

| 检测项 | 判定方式 | 提议动作 |
|---|---|---|
| **腐化** | 超 `reviewDueAt` 未更新 / 溯源的 Task 已删 / 引用的文档已变更 | 标「待更新」+ 指出哪段可能过期 |
| **重复** | 资产间向量相似度 > 阈值（现成 embedding） | 提议 merge，给出合并稿 |
| **矛盾** | 新资产结论与旧资产冲突（LLM 判定） | 高亮冲突段落，要人工裁决 |
| **孤岛** | 无入链无出链、未挂域 | 提议挂域 + 建议关联对象 |
| **空洞** | Outline 有主题但无资产覆盖 | 转 Gap |

产出「**知识库健康周报**」：覆盖率 / 腐化率 / 孤岛率 / 本周新增 / 本周被复用 Top5。

> 这一环对应大厂的文档 review 机制，也是**个人知识库与团队知识库的真正差距所在**——个人库通常只有"堆"没有"养"。

## 闭环 ④ Reuse：复用 → 证明价值（**留存的关键**）

沉淀若不被使用，用户三周内必然放弃。所以必须**主动把资产推到用眼前**：

| 时机 | 动作 | 实现接入点 |
|---|---|---|
| 新建任务/目标时 | 「你上次做过类似的 X，有 1 份 SOP + 2 条踩坑」 | Task/Goal 创建事件 |
| Agent 规划时 | 自有 SOP/CHECKLIST 优先注入规划上下文 | `PlannerAgentService` |
| 对话回答时 | 自有资产优先于通用知识，并标注 `[[资产标题]]` | 已有 CRAG 排序加权 |
| 轮次收尾时 | 「这次的解法要不要沉淀？」 | 已有 `TurnStoppingAdvisor` ★ |

★ 现有 `ProactiveFollowUpAdvisor` 的钩子机制**天生就是为这个场景准备的**，接入成本几乎为零。

每次命中并被引用 → `reuseCount++` → 直接支撑北极星指标。

# 四、Agent 侧扩展（全部复用现有机制）

## 4.1 新增子代理角色（`SubAgentRole` 加枚举即可）

| 角色 | 职责 | 工具 tag | 步数 |
|---|---|---|---|
| `HARVESTER` 收割专家 | 从执行轨迹/复盘/会话炼制资产草稿 | `task,goal,note,kb,asset` | 8 |
| `CURATOR` 策展专家 | 巡检腐化/重复/孤岛/空洞，提议 merge 与挂域 | `asset,domain,kb` | 8 |
| `SYNTHESIZER` 综述专家 | 多篇资产 → 一篇 DIGEST（**仓库→体系的关键动作**） | `asset,domain,kb` | 10 |
| `EXAMINER` 考官 | 按 CONCEPT 出题、判分、更新掌握度 | `asset,mastery` | 6 |

## 4.2 新增 AgentMode

`CURATE`（策展模式）：`allow={asset,domain,kb,note,read,write,subagent}`，`deny={task,goal}`
—— 整理知识时不该动任务，避免误操作。正好验证方案 K 的 deny 语义。

## 4.3 新增工具族

```
asset.*    draft / commit / update / get / search / link / merge
           / promote(推进成熟度) / deprecate / list_stale
domain.*   tree / create / assign / outline_generate / coverage
gap.*      list / upsert / close / to_learning_plan
mastery.*  exam_generate / exam_grade / due_queue
harvest.*  inbox / adopt / discard
```

写类工具全部 `requiresConfirm=true`；`asset.commit` 不允许直接写入 `REVIEWED+`（执行层强制，非提示层约束——延续方案 D/K 的立场）。

## 4.4 与既有能力的接缝

| 既有能力 | 在本方案中的新用途 |
|---|---|
| Hybrid 检索 + CRAG | 资产检索主通路；**degraded 信号转 Gap**（信号复用） |
| `note_embedding` | 加 `source='ASSET'` 即支持资产检索，无需新索引 |
| `Link` 表 | 资产 ↔ 任务/目标/笔记的弱关联 |
| `MarkdownRenderer` + `[[双链]]` | 资产正文渲染与互链，零改动 |
| `LongTermMemoryService` | AGENT_MEMO 是**未结构化的**长期记忆，可作 Harvest 原料 |
| MCP 文档直读 | 外部资料 → 资产的摄取通路 |
| 事件总线 | Harvest 触发器，core 层不反向依赖 |
| `TurnStoppingAdvisor` | 主动追问「要不要沉淀」 |
| insight 得分 | 扩展维度：从"规划得分"到"**知识资产得分**" |
| 评测体系（方案 A） | 新增收割/策展轨迹用例，防 prompt 改动导致沉淀质量退化 |

**这张表是本方案成本可控的根本原因：新增的是语义层与闭环，管道全部现成。**

# 五、数据模型（新增表）

```
knowledge_domain
  id, user_id, parent_id, name, path(物化路径), outline_json, sort, created_at

knowledge_asset
  id, user_id, domain_id, type(AssetType), title, summary, content(MEDIUMTEXT),
  maturity, owner, version, source_kind(AGENT_HARVEST/MANUAL/IMPORT),
  review_due_at, staleness_score, reuse_count, adopted_at,
  created_at, updated_at, deprecated_at
  ├ FULLTEXT ngram (title, summary, content)   ← 与 note 同构
  └ INDEX (user_id, domain_id, maturity)

asset_provenance
  id, asset_id, source_type, source_id, locator, excerpt(TEXT), created_at

asset_revision
  id, asset_id, version, content, change_note, editor(USER/AGENT), created_at

asset_relation                                  ← 资产间语义关联（体系的"键"）
  id, asset_id, target_asset_id, relation(PREREQ/EXTENDS/CONTRADICTS/SEE_ALSO)

knowledge_gap
  id, user_id, question, norm_question, domain_id, hit_grade, ask_count,
  first_asked_at, last_asked_at, status(OPEN/PLANNED/CLOSED/IGNORED),
  closed_by_asset_id, learning_goal_id

asset_mastery
  id, asset_id, level(0-5), last_examined_at, next_review_at, ease_factor

harvest_candidate                               ← 收集箱（与 asset 分离，防污染主库）
  id, user_id, trigger_type, trigger_ref_id, suggested_type, suggested_domain_id,
  draft_title, draft_content, confidence, status(PENDING/ADOPTED/DISCARDED),
  discard_reason, created_at
```

复用改造：`note_embedding.source` 增加 `ASSET` 取值；`Link.LinkTargetType` 增加 `ASSET`。

> `harvest_candidate` 与 `knowledge_asset` **必须分表**：草稿是机器产物、可能被大量丢弃，混在主表里会让"我的知识库有多少资产"这个数字失去意义，也会污染检索。

# 六、界面形态（务实版，沿用 Thymeleaf + 原生 JS）

| 页面 | 内容 | 优先级 |
|---|---|---|
| **收割收集箱** | 草稿卡片流，采纳/编辑/丢弃，支持批量 —— **日常主入口** | P1 |
| **知识库首页** | 左域树 + 右健康仪表盘（覆盖率/腐化/孤岛/待收割/开放缺口） | P0 |
| **资产详情** | Markdown 正文 + 模板槽位缺失提示 + 溯源侧栏 + 反链 + 版本 + review 状态条 | P0 |
| **缺口看板** | 按 askCount 排序，一键转学习计划 | P2 |
| **健康周报** | 策展巡检结果 + 待处理提议（merge/挂域/更新） | P3 |
| **知识地图** | 域树 + 资产关系图（先做「树 + 关联列表」，图可视化后置） | P4 |
| **掌握度视图** | 域 × 掌握度热力图 + 今日复习队列 | P5 |
| Agent 面板 | 增加 `CURATE` 模式入口 + 「沉淀这段对话」按钮 | P1 |

UI 原则：**收集箱做到 3 秒决策，资产详情做到能看清出处，其余都可以简陋。** 不做通用富文本编辑器（那是 Notion 的战场，打不赢也不必打）。

# 七、度量体系

**北极星指标：知识复用率** = `被自有资产回答的提问数 / 总知识型提问数`

选它的理由：它是唯一无法靠"多写文档"刷上去的指标，必须**沉淀对 + 检索准 + 内容有用**三者同时成立。且它**用现有 CRAG grade 统计即可算出**，无需新埋点。

| 维度 | 指标 | 健康信号 |
|---|---|---|
| 沉淀 | 草稿采纳率、资产净增、平均编辑成本 | 采纳率 > 40%（过低说明起草质量差；过高说明预筛太保守） |
| 结构 | 域覆盖率、孤岛率、平均入链数 | 孤岛率下降 |
| 质量 | 模板完整率、溯源完整率、腐化率 | 腐化率 < 20% |
| 价值 | **复用次数**、缺口关闭率、**degraded 率趋势** | degraded 率随时间**单调下降** ← 体系真在长 |
| 学习 | 掌握度分布、复习按时率 | —— |

全部并入现有 `/api/observability/stats`，遵守项目既有约束「没有消费方的指标等于没有指标」。

# 八、分期路线

| 期 | 主题 | 交付 | 验收 |
|---|---|---|---|
| **P0** | 地基 | domain/asset/provenance/revision 表；`asset.*` `domain.*` 基础工具；资产详情页 + 域树；接入 `note_embedding` | 能手动建资产、挂域、被 `kb.semantic_search` 检索到 |
| **P1** | 自动收割 | 事件触发 + 规则预筛 + `HARVESTER` + `harvest_candidate` + 收集箱 UI + 模板校验 | 完成一个跨天任务后，收集箱出现可用草稿 |
| **P2** | 缺口闭环 | `knowledge_gap` + CRAG 信号接线 + 语义聚类 + `gap.to_learning_plan` | degraded 提问自动进缺口，可一键转目标 |
| **P3** | 策展保鲜 | `CURATOR` + 五类巡检 + merge/挂域提议 + 健康周报 | 能查出重复/腐化/孤岛资产并给出提议 |
| **P4** | 体系化 | `outline_generate` + 覆盖率 + `SYNTHESIZER` DIGEST + `asset_relation` + 知识地图 | 能对某域输出覆盖率与综述 |
| **P5** | 掌握度 | `EXAMINER` + SM-2 + 掌握度视图 + 接入 insight 得分 | 能出题、判分、生成复习队列 |

**最小可信路径 = P0 + P1 + P2**：这三期就已构成完整故事「工作产生知识 → 知识补全缺口 → 缺口驱动学习」，且每期独立可用。P3~P5 是纵深。

# 九、风险与反模式（必须防的六条）

| # | 反模式 | 后果 | 对策 |
|---|---|---|---|
| 1 | Agent 自动 commit 正式资产 | **知识库信任崩塌**，产品价值归零 | 草稿态 + 人工采纳；`REVIEWED+` 执行层禁止 Agent 写入 |
| 2 | 模板过重 | 沉淀成本高 → 收集箱被弃用 | 模板只校验不强制；SEED 允许只有一句话；缺槽位只提示不拦截 |
| 3 | 做成"又一个 Notion" | 在编辑器体验上必败 | 坚持工作流原料驱动；编辑体验够用即止 |
| 4 | 指标虚高（资产数刷满但没人用） | 自欺 | 北极星是**复用率**不是数量；资产数只作辅助指标 |
| 5 | 知识图谱可视化先行 | 投入大、收益低、易烂尾 | 后置到 P4；先「域树 + 关联列表」 |
| 6 | Note/Asset 二分让用户困惑 | 不知道该写哪边 | 心智统一为「收集箱 → 资产库」；Note **不迁移不改动**，只做原料 |

技术边界（要主动说清，别夸大）：
- 单用户量级下，MySQL + 内存向量比对足够，**不引入 pgvector/ES**；量级上万 chunk 后再谈。
- 腐化检测是启发式（时间 + 溯源变更 + LLM 判定），**不是形式化验证**，会有漏判。
- 语义聚类合并 Gap 依赖 embedding 阈值，会有误合，需支持人工拆分。

前瞻设计（刻意留的）：`owner` / `version` / `review` / `maturity` 这几个字段本质是**团队语义**。个人版用不满，但将来做「多人共享知识库」时**数据模型无需改动**，只需加权限层。这是有意为之，不是过度设计。

# 十、对项目叙事的增益

| 原叙事 | 升级后 |
|---|---|
| 「我做了个带 AI 的任务管理器」 | 「我做了个**个人知识运营系统**，Agent 负责从工作流自动炼制并维护知识资产」 |
| Agent 是**对话式助手** | Agent 是**有主动职责的常驻角色**（收割/策展/考官），且有明确的产出物与度量 |
| RAG 是**检索问答** | RAG 是**知识资产的生产-消费闭环**，检索失败会反向驱动生产 |
| 指标是工程指标 | 指标是**产品指标**（复用率、覆盖率、腐化率），能讲清"怎么证明这东西有用" |

顺带能回答几个有区分度的问题：
- 「怎么防 Agent 写脏你的数据？」→ 草稿态隔离 + 分表 + 执行层禁止越级 commit
- 「Agent 主动性怎么落地而不烦人？」→ 事件触发 + 规则预筛 + 收集箱异步决策（不打断当前工作）
- 「怎么衡量知识库有没有用？」→ 北极星复用率 + degraded 率单调下降
- 「LLM 起草的内容怎么保证不是幻觉？」→ 强制溯源 + excerpt 快照 + 成熟度门禁
