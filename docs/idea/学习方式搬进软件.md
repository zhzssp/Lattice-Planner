# Idea · 把自创学习方式搬进软件：从原始资料收敛成知识体系

| 项 | 内容 |
|---|---|
| 性质 | **Idea**。写清预期，不是现状，也不是实施计划 |
| 日期 | 2026-09-16 |
| 一句话 | 在已有的目标–任务规划之外，软件要能执行我自创的学习方式：读我列出的原始资料 → 抽出路径和要点 → 变成可执行的任务 → 在与 Agent 的问答里不断纠正 → 把认可的知识沉成笔记 → 直到整套体系像函数一样收敛；**全部资产以 Git 为权威源**，别处改了 `pull` 进来，软件里展示的内容跟着变 |
| 对照 | 现状能力包见 [P-KB-001](../problems/知识沉淀体系-用户功能与未合拢.md)；仓库形态设计见 [Codex V2](../design/知识资产沉淀-Git仓库形态产品方案V2.md)；缺口与方案见 [学习体系收敛-缺口分析与设计.md](../design/学习体系收敛-缺口分析与设计.md) |

V2 把方法论形式化成「源 → 蒸 → 线 → 做 → 验 → 沉 → 收」，实施时却落成：**对一份已经写好的 Git 仓库做索引、体检、检验面板**。那是执行器，不是我要的东西。我要的是软件**从资料把体系长出来**，并且和原来的规划能力接在同一条链上。

---

## 1. 软件里本来有什么，还缺什么

Lattice 早期已经能做一件事：**目标–任务规划管理**（拆目标、排任务、执行/学习/规划三种密度）。

还缺的是第二件事：我有自己的学习方式，现在主要靠仓库纪律和对话里手搓。我希望软件把这套方式接进来，而不是另开一个「知识库 App」、也不是在 Dashboard 旁边挂五张运维页。

两件事的关系：

```
原始学习资料
    → 学习路径 + 路径上的要点          ← 知识体系（要长出来、要可改）
    → 对应的目标 / 任务                 ← 已有规划能力（被路径驱动，不是平行宇宙）
    → 学的过程中与 Agent 问答
    → 纠正路径 / 要点，沉淀认可的笔记
    → 再规划、再学、再改
    → 收敛
```

规划不是知识体系外面的工具；**由路径长出来的任务，本身就是知识体系的一部分**——它回答「接下来具体干什么」，和「这条路上要掌握什么」是同一套状态。

## 2. 要搬进软件的学习方式

### 2.1 起点：人列出原始资料

学习不从空白笔记开始，从**我指定的原料**开始：论文 PDF、官方文档、仓库里的源码/指南、我扔进 Git 的任何原文。

软件的第一职责是**读这些东西**（不是让我先手写一本教材再来「接入」）。人决定学什么、原料在哪；机器负责从原料里提出可讨论的结构。

### 2.2 抽出学习路径，以及路径上的要点

读完原料之后，要得到两样结构化的东西：

| 产物 | 回答的问题 | 不是什么 |
|---|---|---|
| **学习路径** | 先读什么、再做什么、中间怎么串 | 不是书签列表，不是按文件名排序 |
| **学习要点** | 这一步必须抓住什么、什么可以先跳过 | 不是全文摘要，不是把 PDF 再抄一遍 |

路径是顺序和依赖；要点是每一站的掌握标准。没有这两样，后面的任务规划没有依据，Agent 问答也没有可改的对象。

第一版路径和要点**允许是错的、粗的**。软件的价值不在一次蒸馏完美，在于它们是显式状态，后面每一轮对话都能改。

### 2.3 据此做任务规划

路径和要点要落到 Lattice 里已有的目标/任务上：这一周读哪一节、做哪一个实验、完成哪一条掌握标准。

这不是「知识页上按个按钮，往任务列表里丢一条备忘」。任务必须能指回路径上的某一站、某一个要点。改路径时，过时的任务要能被看出来；完成任务时，要点的状态要能往前走。

### 2.4 学的过程：和 Agent 问答

真正的学习发生在对话里：

- 问不懂的地方，从原料和已有笔记里拿证据回答
- 发现路径走不通、顺序反了、某要点其实不该现在学 → **改路径、改要点**
- 发现原料里没写清、或我形成了自己的理解 → **把我认可的那一段沉淀成笔记**

Agent 是迭代算子，不是百科。问答的目的有三件，缺一不可：**获取知识、纠正体系、沉淀认可**。聊完若不改路径/要点、不落笔记，这一轮对体系没有贡献。

### 2.5 认可才进体系

对话默认是过程，不是资产。只有我点头的内容才成为笔记、才有资格改路径和要点。

未认可的草稿可以留在分支或对话里，但不能冒充体系。这一点和「Agent 不许直接改权威源」是同一条纪律。

## 3. 「函数收敛」指什么

把某一时刻 Git 里的知识体系叫做 \(x\)：路径、要点、笔记，以及由它们驱动的任务关联。

一轮交互是一个算子 \(T\)：读原料（若有新的）→ 问答 → 人认可 → 写回 Git。

> 预期：反复做 \(x_{n+1} = T(x_n)\)，直到 \(T(x) \approx x\)。

收敛时的样子（人能感觉到，不是覆盖率仪表盘假绿）：

- 新问题大多能在现有路径和笔记里答上，不再倒逼大改路线
- 要点稳定：必须掌握的还在，该跳过的真的可以跳过，不会每周重写一遍
- 任务和路径对齐：Dashboard 上的下一件事就是路径上的下一站
- 整份材料**流畅**：能当一份体系来读，而不是论文堆 + 聊天记录 + 互不相干的备忘

不收敛的样子：

- 每次打开都在重新发明「我该干什么」
- 笔记和路径各写各的
- 任务是规划模式里随手加的，和学习要点对不上
- 蒸馏出一篇草稿就当「体系完成了」

**收敛是过程的固定点，不是一次 LLM 调用的输出。** 所以产品中心是这条回路，不是某一张「体系仪表盘」页面。

## 4. 知识体系里有哪些资产（全部进 Git）

下列都是知识体系的一部分，**全部要和同一个 Git 仓库绑在一起**，在 Git 上持久化：

| 资产 | 谁产生 | 存在哪 |
|---|---|---|
| 原始资料（或资料的指针与快照） | 人列入 | 仓库里的 `paper/`、文档、链接清单 |
| 学习路径 | 人 + Agent 提议，人认可 | 仓库里的路线文件（阶段表 / 优先级 / 周次） |
| 学习要点 | 同上 | 挂在路径各站上：必学 / 先跳过 / 掌握标准 |
| 由路径长出的任务与目标 | 规划能力，但要能指回路径 | 规划数据要能关联到仓库里的站与要点；不能只活在软件私有库里却和 Git 失联 |
| 认可后的笔记 | 对话里搞懂、人点头 | 仓库里的 notes，并回挂到路径/要点 |
| 蒸馏出的可读材料（若有） | Agent 起草，人核对 | 仓库里的 guide / paper-notes |

软件里的数据库最多是**可扔掉的索引和展示缓存**。删掉索引、从 Git 再拉再编，展示应能恢复。人离开 Lattice，用 IDE / Obsidian 打开同一仓库，路径、要点、笔记都还在。

### Git 同步是产品行为，不是备份口号

- 在软件里认可并写入 → commit 进该仓库（工作分支、人看 diff，这些是护栏，不改变「权威在 Git」）
- 在别处改了同一仓库（另一台电脑、GitHub、编辑器）→ `git pull` → **软件当前展示的路径、要点、笔记、由它们派生的视图必须更新**
- 展示与仓库打架时，以仓库为准，而不是以上次打开软件时的内存为准

做不到 pull 即更新，就只是「软件里另存了一份」，和这则 Idea 相反。

## 5. 和今天已有能力的关系（预期，不是验收）

| 已有 | 在这则 Idea 里应扮演的角色 |
|---|---|
| 三模式 Dashboard（执行 / 学习 / 规划） | 学的时候看任务与笔记密度；**不是**知识体系的容器 |
| 目标–任务 | 路径的下游执行面；任务应能追溯到要点 |
| Agent 对话 | 迭代算子：问答、提议改路径、起草笔记 |
| 「我的笔记」（MySQL PKM） | 随手记可以继续存在；**一经认可进入知识体系，就应落进 Git 仓库**，不能永远停在软件私有库 |
| Codex 五页（接入 / 定线 / 检验 / 策展 / 缺口） | 至多是回路上的工具面；**不能代替「从资料长出路径再收敛」这条主路径** |
| Git 接入与索引 | 必要底座：没有权威源就没有 pull 更新 |

今天最容易走偏的三点：

1. **把「接入已有仓库 + 健康度」当成产品本身**——那是第 0 步，不是学习方式。
2. **把「蒸馏 PDF → 一篇 guide 草稿」当成体系已经长出来**——那只是 \(T\) 的一次提议。
3. **路径、笔记、任务三套状态互不引用**——收敛无从发生。

## 6. 怎样才算这则 Idea 被产品接住

不要求一次做完 V2 里所有检验/CI。最低要能走通下面这条故事：

1. 我在仓库里放入（或列出）若干论文/文档。
2. 软件读它们，给出一版学习路径和各站要点，我能改、能认可、能写进 Git。
3. 认可后的路径能生成（或更新）Dashboard 上的目标/任务，且任务能点回那一站要点。
4. 我与 Agent 针对某一要点问答；我认可的回答成为仓库里的笔记，并挂回该要点。
5. 问答若证明顺序错了，路径被改一版，过时任务能被看出来。
6. 我在仓库外改了同一文件并 `pull`，软件里看到的路径/要点/笔记随之变化。
7. 重复 4～6，路径的改动逐渐变小——这就是在收敛。

做不到第 2、3、4、6 条，就还是「规划软件 + 一个索引了 Git 的附属页」，不是这则 Idea。

---

## 7. 本文不写什么

不写表结构、开关名、页面线框、P0–P7 排期。那些属于 `docs/design/`，且必须**先承认主路径是「资料 → 路径/要点 → 任务 → 问答迭代 → Git」**，再决定哪一期做检验、哪一期做 CI。

检验、止损线、示例不可砍，仍然可以是方法论里的硬约束；它们是收敛之后用来**防止假懂**的，不能反客为主，变成软件唯一可见的「知识功能」。
