# Lattice-Planner 系统性功能验收方案

> 适用分支：`V4.0.0`
> 覆盖范围：`docs/design/` 下设计文档所描述的全部已实现功能
> （V3 的 P0~P8 + V4 Codex 的 P9 + 上下文工程的 P10 + 量化评测体系的 P11）
> 目的：在考虑后续功能扩展**之前**，用可复现的步骤逐条确认既有功能真实可用、且符合各设计文档自定的验收标准。
>
> **当前状态（2026-09-02）**：自动化那一层已经跑起来了——
>
> | 命令 | 结果 |
> |---|---|
> | `./gradlew test` | 435 个用例，1 失败（`contextLoads`，需真实 MySQL，**属已知且无关**），2 跳过（LLM 裁判，默认关闭） |
> | `./gradlew agentEval` | 20/20 通过 = 13 个轨迹用例 + 7 个 RAG 检索用例 |
>
> **但这不等于本文档可以跳过。** 自动化覆盖的是「Agent 决策质量」与「检索质量」两条链路，
> 而本文档 P0~P10 里绝大多数项（MCP 协议栈、Electron、Git 仓库写入、多用户隔离、
> 上游 prompt cache 命中）**只能在真实运行期人工验收**。
>
> **V4 更新说明**：
> - **P9** — 知识仓库（Codex）：Git 管理的知识库 + 验证闭环 + 沉淀 + 缺口台账 + 蒸馏定线，共 5 期（P0~P4）
> - **P10** — 上下文工程 P1：滚动摘要 + Facts 层
> - **P11** — 量化评测体系 P0~P4：端状态验证 / pass^k / 轨迹指标 / 判分器校准 / RAG 金标集（**新增，见文末 P11**）
>
> P9、P10 两域的能力**默认全部关闭**（与 V3「开箱即用」不同），验收前需按各自的开关矩阵逐项开启。
>
> ### ⚠️ 量化评测查出的三处产品缺陷 · **已全部修复，验收时需在真实 MySQL 上对照**
>
> | 处 | 原现象 | 修法 | 相关验收项 |
> |---|---|---|---|
> | **多跳问题假降级** | 关键字通路一旦缺席，`alpha(0.4)×余弦` 的上限恰好等于 `crag.lower(0.4)`，多跳问题被 100% 误判为"没检索到" | 判级改看与 alpha 无关的 `relevance` | **P2-3e** |

>
> 详细根因、效果数字与**唯一一条已查明但未修**的限制，见 **附录 C-5**。

## 如何使用本文档

1. 按 **P0 → P10** 顺序执行，前一阶段不通过不要进入下一阶段（存在依赖关系）。
   其中 **P9（Codex）与 P10（上下文工程）与 P0~P8 无强依赖，可独立验收**——
   但两者都依赖 P0 的环境就绪。
2. 每个验收项都有明确的 **判定标准**（PASS 条件），只认客观现象，不认"看起来没报错"。
3. 每项附 **失败排查** 指向具体文件，便于定位。
4. 全部执行完毕后填写文末 **附录 A 验收结论清单**。
5. 标注 <kbd>预期为禁用</kbd> 的项，"返回错误"才是 PASS，不要误判为 Bug。

# P0 · 环境就绪与阻塞项清除

> 本阶段不验证业务功能，只保证后续验收能跑起来。**P0 有 3 个已知阻塞项，必须先处理。**

## P0-1 阻塞项：`electron-app/package.json` 语法错误

**现象**：文件第 1 行是 `git {` 而非 `{`，属于无效 JSON，`npm install` / `electron .` 会直接解析失败。

```json
git {
  "name": "Lattice-Planner",
```

**处理**：删掉行首的 `git ` 三个字符，使首行为 `{`。

**判定标准**：`cd electron-app && node -e "require('./package.json')"` 无报错输出。

> 影响范围：仅影响 Electron 桌面端（P4-3 晨晚报通知、DDL 提醒）。纯 Web 验收不受阻，可暂缓。

## P0-2 阻塞项：`electron-app/preload.js` 重复注入

**现象**：`contextBridge.exposeInMainWorld('lattice', ...)` 被复制粘贴了两次（约 L18-24 与 L26-34）。Electron 对同一 key 重复暴露会抛错，渲染进程拿不到 `window.lattice`。

**处理**：删除重复的第二段，只保留一处。

**判定标准**：Electron 启动后在渲染进程 DevTools 执行 `typeof window.lattice` 返回 `"object"`，控制台无 `exposeInMainWorld` 相关报错。

## P0-3 阻塞项：`permission-config.json` 白名单指向不存在的目录

**现象**：`allowDirs` 为 `D:/notes`、`D:/learning`、`C:/Users/Public/Documents`，本机大概率不存在前两个。

**处理**：改为本机真实存在的目录，例如：

```json
"allowDirs": ["C:/Users/<你的用户名>/Desktop/verify-docs"]
```

> 注意：此配置只服务于 **Electron LocalBridge** 通道。而 v3 之后 Agent 读本地文档走的是**后端直读 + MCP loopback**（白名单由 `mcp.server.local-allowed-dirs` 控制，留空则默认整个用户主目录）。两套白名单互不影响，别混淆。

## P1-4 Reflexion（工具失败自纠）

**验证方法**：输入"删除 id 为 999999 的任务"（不存在的 id）。

**判定标准**：
- `toolResult` 卡片显示错误 JSON（如 `{"error":"NOT_FOUND"}`）
- Agent **不会崩溃或空转**，而是把错误消化后给出合理答复（"该任务不存在"）
- 步数不超过 `agent.chat.max-steps=24`

> 显式 Reflexion（方案 D）已实现：失败按 6 类模式分类，不可重试的（权限拒绝/用户拒绝/工具不存在/资源不存在/工具不可见）一次即封禁，可重试的（参数错/偶发）达阈值（默认 2）后封禁。封禁后模型再调直接短路返回 `TOOL_BANNED_THIS_TURN`。指标见 `trace/stats` 的 `reflexion` 分区。

## P1-5 <kbd>预期为禁用</kbd> 本地文档摄取

**验证方法**：输入"把 C:/Users/xxx/Desktop/verify-docs/plan.md 摄取进知识库"。

**判定标准**：返回 `{"error":"WRITE_DISABLED", "message":"v3 当前为只读模式..."}`。

**这是正确行为**。原因：本地文件访问从 Electron Bridge 迁移到 MCP 后端直读后，`kb.ingest_local_doc` 依赖的 `localBridge` 失去载体，故整条写链路被主动降级为只读（真实实现以注释保留在 `KnowledgeTools.ingestLocalImpl`）。

**连带影响**：`note_embedding` 表中不会有 `source='LOCAL_DOC'` 的行，因此 P2 的检索验收只能基于**手写笔记**，不能基于本地文档。

# P2 · 知识层（PKM-RAG + CRAG + RAG Serving）

## P2-1 笔记向量索引（《PKM-RAG实现方案》）

| 步骤 | 操作 |
|---|---|
| 1 | `$BASE/note/new` 新建 3~5 篇笔记，内容互相区分明显（如"Kafka 消费者组"、"MySQL 索引下推"、"Redis 持久化"） |
| 2 | 保存后等待 3~5 秒（`NotePersistedEvent` 异步索引，线程名前缀 `pkm-`） |

**判定标准**：

```sql
SELECT source, note_id, chunk_idx, LEFT(embedding, 40), model
FROM note_embedding WHERE source='NOTE';
```

- 有记录，且行数 ≥ 笔记数（长笔记会切多个 chunk）
- `embedding` 是 JSON 数组，`model` 为 `BAAI/bge-m3`

**失败排查**：`EMBED_API_KEY` 未设置 → 日志会有 Embedding API 失败告警；`NoteIndexService.rebuildForNote` 是否被 `NotePersistedListener` 调用。

## P2-2 Hybrid 检索

**方式 A（页面）**：`$BASE/note/search?q=消费者组&topK=6`

**判定标准**：返回 JSON 数组，命中项含 `score`、`reason` 字段；`reason` 应能体现关键字/向量两路来源（验证 `alpha=0.4` 融合生效）。

**方式 B（Agent）**：面板输入"我之前记过关于 Kafka 的笔记吗？"

**判定标准**：
- Agent 先调用 `kb.semantic_search`（不是直接凭记忆回答）
- 引用笔记时使用 `[[标题]]` 格式，且前端渲染为可点击链接
- 点击链接跳转到 `/note/by-title/{title}` 并正确打开笔记

## P2-3 CRAG 状态机（《AI-Infra-CRAG-SelfRAG实现计划》）

> 本轮刚修复：`grade`/`degraded` 此前只在**零命中**时返回，导致"有命中但质量差"的降级信号丢失、Self-RAG 链路断开。现改为**无条件返回且置于数组首位**。

### P2-3a `_meta` 行结构验证

**验证方法**：Agent 输入任意涉及笔记的问题，展开 `toolResult` 卡片查看 `kb.semantic_search` 原始返回。

**判定标准**：返回数组的**第 0 项**是元信息行，形如：

```json
{
  "_meta": "crag",
  "grade": "CORRECT",
  "degraded": false,
  "hitCount": 3,
  "usedQueries": ["我之前记过关于 Kafka 的笔记吗"],
  "message": "检索质量良好：可直接引用命中片段，引用笔记用 [[标题]] 写法。"
}
```

**这是本轮修复的核心验证点**：即使 `hitCount > 0`，`grade` 与 `degraded` 也必须存在。

### P2-3b 三种 grade 分支

| 构造方式 | 预期 grade | 预期 Agent 行为 |
|---|---|---|
| 问笔记里写得很清楚的内容 | `CORRECT` | 直接引用，正常作答 |
| 问笔记里沾边但不精确的内容 | `AMBIGUOUS` | 提醒"检索结果相关性一般，仅供参考" |
| 问完全无关的内容（如"我记过关于量子色动力学的笔记吗"） | `INCORRECT` + `degraded=true` | **首句明示**"未找到强相关笔记，以下基于通用知识：" |

**判定标准**：第三种情况下，Agent 回复首句必须出现降级声明。若它假装命中或直接答通用知识而不声明，说明 `_meta` 未被 LLM 正确消费（检查 `PromptBuilder` 的【知识检索原则】段）。

### P2-3c 改写重检索上限

**验证方法**：触发一次 `AMBIGUOUS`/`INCORRECT`，观察日志。

**判定标准**：
- 日志出现 `[CRAG] 检索质量=... 触发改写重检索`
- `_meta.usedQueries` 数组长度 ≥ 2（原 query + 改写 query）
- **重检索只发生 1 次**（不出现第二轮改写日志）

### P2-3d `pkm.crag.enabled` 开关（本轮修复）

> 此前该配置项存在但**代码中无任何地方读取**，CRAG 无法关闭，违反计划自定的验收标准。

| 步骤 | 操作 |
|---|---|
| 1 | `application.properties` 改 `pkm.crag.enabled=false`，重启 |
| 2 | 重复 P2-3b 的第三种情况（完全无关的问题） |

**判定标准**：
- `_meta.degraded` 恒为 `false`
- `usedQueries` 长度恒为 1（**不触发改写**）
- 日志**不出现** `[CRAG] ... 触发改写重检索`
- `GET $BASE/api/pkm/rag/stats` 中 `crag.metrics.bypassCount` 随每次检索递增
- `crag.config.enabled` 显示 `false`

验证完记得**改回 `true`**。

### P2-3e ★假降级回归（量化评测查出，**已修复**，本项为线上对照）

> **背景**：P11 的 RAG 金标集跑出来，在关键字通路缺席时**多跳问题被 100% 误判为降级**。
> 根因是**量纲错配**——`Hit.score` 是含 alpha 权重的排序分数，却被拿去比一个
> 表达"语义相关度"的固定阈值，两个参数各自看都合理、乘到一起就穿帮：
>
> ```
> 向量通路分数上限 = pkm.rag.alpha(0.4) × 余弦上限(1.0) = 0.4
> pkm.crag.lower  = 0.4     ← 恰好相等
> pkm.crag.upper  = 0.6     ← 纯向量场景永远够不着
> ```
>
> **修法**：`Hit` 拆出 `relevance`（余弦，与 alpha 和命中通路都无关），
> `RetrievalEvaluator.grade` 改判它。**没有去挪 alpha 或 lower**——
> 挪参数只能让这一组数据碰巧不出事，换个 topK 或换个模型就复发。
> 离线验证：多跳假降级 4/4 → 0/4（生产默认配置）。
>
> 生产用 MySQL，关键字通路在时本来就不一定复现。**本项验的是修复在真实双通路下同样成立**，
> 且顺带确认关键字通路真的活着（见失败排查第 2 条）。

| 步骤 | 操作 |
|---|---|
| 1 | 确认 `note` 表的 `ft_note_title_content` 全文索引真实存在：`SHOW INDEX FROM note WHERE Key_name='ft_note_title_content';` |
| 2 | 建 2 篇主题相邻的笔记（如"Kafka 消费者组"与"Kafka 分区顺序"） |
| 3 | 问一个**需要综合两篇**的多跳问题："Kafka 里消费者组和分区顺序是怎么互相影响的？" |
| 4 | 展开 `toolResult` 看 `_meta` |

**判定标准**：

- ★`_meta.degraded` 为 `false`，且 Agent **没有**说"未找到强相关笔记，以下基于通用知识"
- `_meta.hitCount ≥ 2`，两篇笔记都在命中里
- 若 `degraded=true` 而命中里明明有正确笔记 → **这就是假降级，必须记为不通过**

**失败排查**：

1. 先看 `hitCount`——若为 0，那是漏召不是假降级，去查 P2-1 的向量索引
2. 若 `hitCount>0` 却 `degraded=true`，先看每行的 `relevance` 字段（判级依据）：
   - `relevance` 都低于 `pkm.crag.lower(0.4)` → 是**真降级**，语义确实不相关，不是缺陷
   - `relevance` 够高却仍 `degraded=true` → 判级又和排序分数耦合上了，
     查 `RetrievalEvaluator.grade` 是不是被改回读 `score()`
3. 顺带看 `reason` 是否只有 `vec` 没有 `kw`：**只有 `vec` 说明关键字通路没跑起来**
   （索引缺失或 SQL 失败被吞）。这已不会导致假降级，但会损失关键字召回
4. **不要**靠下调 `pkm.crag.lower` 来"修"——那是在给一个已经修好的问题打补丁，
   只会让真正不相关的结果也蒙混过关

> 这一项由 `RagDegradeCalibrationTest` 在 CI 里以**离线方式**常驻守护（它跑生产默认配置，
> 断言多跳假降级率恒为 0）。本项是它在**真实 MySQL 上**的对照验收。

## P3-2 MCP Server：协议栈手工验证

用生成的 `$TOKEN` 模拟一个外部 MCP 客户端：

```bash
# 1) 建立 SSE 连接（保持此终端不关）
curl -N "$BASE/sse?token=$TOKEN"
```

**判定标准**：立即收到 endpoint 事件：

```
event:endpoint
data:/mcp/message?sid=<uuid>
```

> 注意 `data` 是**相对路径**。这正是本轮修复的根因——旧版 `McpSseClient` 直接把它丢给 `HttpClient`，而 Java `HttpClient` 拒绝相对 URI，导致 loopback 永久连不上。修复后客户端会用 SSE base URL 补全为绝对地址。

```bash
# 2) 另开终端，用上一步的 sid 发 JSON-RPC
curl -X POST "$BASE/mcp/message?sid=<uuid>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

**判定标准**：第一个终端的 SSE 流推回 `tools/list` 响应，且工具列表：

- **包含** `local.list_dir`、`local.read_file`、`local.read_pdf`、`local.read_document`
- **不包含** `kb.ingest_local_doc`、`kb.delete_local_doc`（v3 已从 `exportLocalTools()` 移除，收紧为纯只读）

再验资源：

```bash
curl -X POST "$BASE/mcp/message?sid=<uuid>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"resources/list","params":{}}'
```

**判定标准**：返回 5 个资源 URI（`McpResourceAdapter` 定义）。

**鉴权回归**：用伪造 token 连接 →

```bash
curl -N "$BASE/sse?token=lattice_fake123"
```

**判定标准**：连接被拒（`McpAuthException`），**不返回任何工具信息**。

## P3-2a 真实 IDE 客户端验证：VSCode 连接本软件 MCP Server

> P3-2 是用 `curl` 手工模拟协议栈；本项用**真实的 MCP 客户端（VSCode）**端到端验证「外部工具通过 token 接入」这条主链路。这是「对外暴露 MCP」功能的最终验收。

### 背景与协议约定

| 项 | 值 | 说明 |
|---|---|---|
| 协议版本 | `2024-11-05` | `McpSseEndpoint` 在 `initialize` 响应里声明 |
| 传输方式 | **HTTP + SSE**（非 stdio） | 端点 `/sse?token=lattice_xxx`，消息端点 `/mcp/message?sid=xxx` |
| 认证 | `lattice_` 前缀 token，库中存 SHA-256 哈希 | 明文仅生成时展示一次 |
| 工具命名 | `mcp.loopback.local.*`、以及 `toolAdapter` 导出的业务工具 | 见 P3-2 的 `tools/list` 结果 |

> ⚠️ 前提：本软件 MCP Server 只实现了 **SSE/HTTP 传输**，没有 stdio。因此必须使用 VSCode 支持的 **`http`/`sse`（HTTP 流式）** 传输类型，而不是 `command`（stdio）类型。否则 VSCode 会把配置当作本地命令去 fork，导致连接失败。

### 前置条件

1. 完成 P0（应用已启动在 `http://localhost:8080`），且 P0-7 第 3 条日志「loopback 连接成功」已出现。
2. 完成 P3-1，已持有**明文 token**（记为 `$TOKEN`，`lattice_` 开头）。若已丢失，回 `/mcp/settings` 重新生成。
3. VSCode 已安装支持 MCP 的扩展（如 GitHub Copilot Agent 模式 / Continue 等）；下文以 **VSCode 自带的 MCP 配置能力**（`.vscode/mcp.json`）为准，不同扩展读取方式略有差异，配置内容一致。

### 步骤 1：在项目内创建 MCP 配置文件

在 VSCode 打开的工作区根目录新建 `.vscode/mcp.json`：

```json
{
  "servers": {
    "lattice-planner": {
      "type": "http",
      "url": "http://localhost:8080/sse?token=lattice_你的token"
    }
  }
}
```

> 说明：不同版本的 VSCode / 扩展对字段名可能用 `"type":"sse"` 或 `"transport":"http"`，若 `"http"` 不被识别，请参照该扩展文档；核心是**必须指定 HTTP/SSE 传输 + 完整的 `url`（含 token 查询参数）**，绝不能写成 `command`。

### 步骤 2：确认 VSCode 完成握手

在 VSCode 中打开 MCP 服务器列表，观察 `lattice-planner` 状态：

**判定标准**：
- 状态变为 **已连接/Connected**（不是「启动失败」或「连接超时」）
- 服务端日志出现：`[MCP] SSE 连接建立：sid=..., user=<你的用户名>`
- 数据库 `mcp_token.last_used_at` 被更新（`authenticate` 会回写），证明走的是真实 token 认证链路：

```sql
SELECT label, last_used_at FROM mcp_token ORDER BY last_used_at DESC LIMIT 1;
```

### 步骤 3：列出工具与资源

在 VSCode 的 MCP 工具面板（或让 Agent 列出可用工具）中：

**判定标准**：
- 能看到 `local.list_dir` / `local.read_file` / `local.read_pdf` / `local.read_document`
- 能看到 `toolAdapter` 导出的业务工具（目标/任务/笔记/知识库等）
- **看不到** `kb.ingest_local_doc` / `kb.delete_local_doc`（v3 已收紧为只读）
- 资源列表返回 `McpResourceAdapter` 定义的 5 个 URI（与 P3-2 的 `resources/list` 结果一致）

### 步骤 4：端到端调用一次工具

在 VSCode 中让 Agent 执行一次真实调用，例如：

> 读取文件 `C:\Users\<你的用户名>\Desktop\verify-docs\plan.md` 并总结

**判定标准**：
- 工具实际被调用（不是编造结果），返回内容与文件真实内容一致
- `meta` 含 `fileName` / `extension` / `sizeBytes` 等字段（与 P3-4a 一致）
- 若让 Agent「帮我建一个任务」，则在 `/dashboard` 能看到真实落库的任务（证明 VSCode 侧以 token 持有者身份走完了完整工具链）

### 步骤 5：鉴权与隔离回归

| 用例 | 操作 | 判定标准 |
|---|---|---|
| 伪造 token | 把 `mcp.json` 里 token 改成 `lattice_fake123` 重连 | 连接被拒，VSCode 侧无任何工具暴露 |
| 吊销 token | 回 `/mcp/settings` 吊销当前 token | VSCode 侧下一次调用失败，重连也失败 |
| 已下线工具 | 让 Agent 调 `local.read_file`（不带 `mcp.` 前缀） | 返回 `UNKNOWN_TOOL` |

### 失败排查

1. VSCode 显示「启动失败」→ 检查是否误用 `command`/stdio 类型；本项目只支持 HTTP/SSE。
2. 连接超时 → 确认端口为 `8080`（loopback 硬编码），且应用已启动、`mcp.server.enabled=true`。
3. 握手成功但无工具 → 服务端日志有无 `tools/list`；确认 `mcp.server.local-files-enabled=true`。
4. 认证失败 → 确认 token 是 `lattice_` 前缀的明文；明文丢失只能重新生成。
5. 跨机访问 → 默认 `localhost:8080` 仅本机可达；VSCode 必须与本软件同一台机器（或改 url 为可路由 IP）。

## P4-1 SubAgent（《Lattice-Agent-SubAgent设计方案》）

> 本轮修复：`PLANNER`/`RESEARCH` 的 `toolTags` 原为 `local`，但该 tag 下的 `@AgentTool` 已随 `LocalDocTools` 空壳化而全部下线，且 tag 不含 `mcp` → 子代理按 prompt 指引调 `local.read_file` 必然 `UNKNOWN_TOOL`。现已改为 `mcp` tag。

# P6 · AI-Infra 可观测（本轮新增）

> 三大 AI-Infra 计划的主干链路此前均已实现，但**验收所需的观测手段全部缺失**：`RagServingMetrics` 有 4 个计数器从无调用点（恒为 0）、`PrefixCacheMetrics` 不存在、两个 stats 端点不存在、`LlmGateway` 从不读 `usage`。本阶段验收补齐后的可观测层。

## P6-0 三个新端点连通性

```bash
curl -b "JSESSIONID=$SID" "$BASE/api/pkm/rag/stats"
curl -b "JSESSIONID=$SID" "$BASE/api/agent/prefix-cache/stats"
curl -b "JSESSIONID=$SID" "$BASE/api/observability/stats"
```

**判定标准**：三者均返回 200 JSON；未登录访问 `/api/pkm/rag/stats` 与 `/api/observability/stats` 应被拦截（走 `anyRequest().authenticated()`）。

> 注意 `/api/agent/prefix-cache/stats` 因 `/agent/**`…实为 `/api/agent/**`，仍受 `anyRequest().authenticated()` 保护。

## P6-1 前缀缓存命中（Prefix Caching P1-P3、P5）

| 步骤 | 操作 |
|---|---|
| 1 | 记录基线 `GET /api/agent/prefix-cache/stats` |
| 2 | 同一 mode 下连续发 3 条消息 |
| 3 | 再拉一次 |

**判定标准**：

```json
{
  "config": {"enabled": true, "size": 1},
  "metrics": {
    "prefixCacheHit": 2,
    "prefixCacheMiss": 1,
    "prefixCacheHitRate": 0.6667,
    "prefixBuildCount": 1,
    "avgBuildMs": 3.2,
    "estimatedBuildTimeSavedMs": 6
  }
}
```

- 首次 miss、后续 hit（同 mode + 同工具集 + 同 memo + 同日 → key 相同）
- `prefixBuildCount` **远小于**消息数（证明前缀被复用）
- `estimatedBuildTimeSavedMs` > 0 ← **量化收益**

**前缀字节稳定性**（计划明确要求）：连续两次同输入 `buildPrefix`，`prefixHash` 必须完全相同。间接验证：`prefixCacheHit` 能持续增长说明 key 稳定；若每次都 miss，说明 `toolsetHash`/`memoHash` 在漂移。

**切换 mode 验证 key 生效**：从 chat 切到 plan → 应产生一次新的 miss（`mode` 是 key 的一部分）。

**开关回归**：`agent.prefix-cache.enabled=false` 重启 → `config.enabled=false`，功能正常但无缓存收益（`prefixCacheMiss` 持续增长）。

## P6-2 上游 prompt cache 透传（Prefix Caching P4）

> DeepSeek 的 context caching 是**自动**的（按前缀命中，无需显式传 cache_id），应用侧能做的就是保证前缀字节稳定 + 读取 `usage` 观测。

**验证方法**：进行 5~10 轮对话（前缀需足够长才会触发上游缓存，通常 >1024 token），然后看 stats。

**判定标准**：

```json
"upstreamPromptCache": {
  "chatCalls": 12,
  "usageReportedCalls": 12,
  "promptCacheHitTokens": 8460,
  "promptCacheMissTokens": 3200,
  "promptCacheHitRate": 0.7255
}
```

- `chatCalls` 与实际 LLM 调用次数一致
- `promptCacheHitTokens` > 0 ← **这直接证明"前缀字节稳定化"真的让服务端缓存命中了**，是三大计划里最有说服力的一个数据

**若 `promptCacheHitTokens` 恒为 0**，可能原因：
1. 前缀长度不足上游缓存最小阈值（DeepSeek 需 ≥1024 token）—— 属正常
2. 上游未返回 `usage` 字段 → 看 `usageReportedCalls` 是否为 0
3. 前缀在漂移 → 回头查 P6-1 的 `prefixCacheHitRate`

## P6-3 RAG Serving 指标完整性

**判定标准**：`GET /api/pkm/rag/stats` 的 `ragServing.metrics` 中，以下字段在跑过 P2 后**均不为 0 或均有意义**：

| 字段 | 此前状态 | 现在应有 |
|---|---|---|
| `searchCount` | 恒 0（无调用点） | 随检索递增 |
| `prefetchCount` | 恒 0（无调用点） | 触发 RESEARCH 后递增 |
| `rerank.invoked` | 恒 0（无调用点） | 开启 rerank 后递增 |
| `rerank.fallback` | 恒 0（无调用点） | LLM 失败时递增 |
| `queryCache.hitRate` | 可用 | 可用 |
| `latency.*` | 不存在 | 四个延迟维度均有值 |

## P6-4 CRAG 指标

**判定标准**：`crag.metrics` 含：

```json
{
  "retrieveCount": 15,
  "bypassCount": 0,
  "gradeDistribution": {"CORRECT": 9, "AMBIGUOUS": 4, "INCORRECT": 2},
  "rewriteTriggered": 6,
  "rewriteRate": 0.4,
  "degradedCount": 2,
  "degradedRate": 0.1333,
  "rewriteWithinLimit": true
}
```

- `gradeDistribution` 三档都有数据（说明阈值 0.6/0.4 区分度合理；若全在一档，考虑调参）
- **`rewriteWithinLimit` 必须为 `true`** ← 这是"重检索次数严格 ≤ 1"验收标准的机器化断言
- `bypassCount` 在 `enabled=true` 时应为 0

# P8 · 前沿实践吸收（方案 K 工具可见性 + 方案 L 轮次收尾，本轮新增）

> 对应文档：`docs/design/Agent工具运行时可见性-分层遮蔽设计.md`、`docs/design/Agent轮次收尾解耦-TurnStopping设计.md`。
>
> 这两个方案吸收了 DeepSeek Harness 的架构思想，但**刻意裁剪**了不适合个人单机应用的部分（插件化实现替换、可逆副作用、HMR 等）。
> 分两组：K 组（工具可见性四层遮蔽）、L 组（轮次收尾解耦）。

## P8-1 K1+K2 · 模式层 deny（learn/reflect 禁写）

**验证方法**：切到 `learn` 模式，输入"帮我记一笔笔记，标题是 test"。

**判定标准**：
- Agent **不应**调用 `note.create`（该工具 tags 为 `{note, write}`，learn 模式 deny `write`）
- 同样 `reflect` 模式下输入"帮我建个任务"，不应调用 `task.create` / `goal.create`
- `plan` / `chat` 模式下写工具**正常可见可用**（不能过度收窄）

> 这是本轮修掉的真实 bug：此前 tag 过滤是 OR 语义，`note.create` 因命中 `note` tag 而在 learn 模式仍可见。修复后改为显式 `deny=write`。

**单元测试**：`ToolVisibilityResolverTest`（9 个用例，含"learn 模式 note.create 被 deny"回归）。

## P8-2 K3 · 执行层强制（越界拦截）

**验证方法**：learn 模式下，诱导模型调用一个它"记忆中存在但当前不可见"的工具。由于模型通常遵从 schema，最可靠的验证是**观察指标**：

**判定标准**：
- 若模型真的调用了不可见工具 → 返回 `{"error":"TOOL_NOT_VISIBLE", ...}`，且 `registry.invoke` **未被调用**（工具不执行、无副作用）
- `GET $BASE/api/agent/trace/stats` 中 `visibility.notVisibleBlocked` 计数能反映拦截次数
- 独立开关验证：`agent.tool.visibility.enforce=false` 时，越界调用**照旧执行**（仅 schema 过滤），`notVisibleBlocked` 恒为 0

> 设计意图：`enforce` 单独开关是为了量化「只做提示层够不够」。若长期 `notVisibleBlocked=0`，说明模型听劝，强制层是冗余保险；若 >0，就证明了强制层的必要性。

**单元测试**：`ToolNotVisibleTest`（3 个用例，含 `TOOL_NOT_VISIBLE` 分类与不可重试性）。

## P8-3 K4 · 会话层屏蔽（临时 deny/pin）

**验证方法（API 直验）**：

```bash
# 设置会话级屏蔽：本会话 deny task.create
curl -X PUT -b "JSESSIONID=$SID" -H "Content-Type: application/json" \
  -d '{"sid":"verify-session","denyTools":["task.create"],"denyTags":[],"pinnedTools":[]}' \
  "$BASE/agent/settings/visibility/session"
```

**判定标准**：
- 该 sid 下输入"帮我建任务"，`task.create` 不可见（即使 plan 模式）
- `pin` 覆盖 deny：设置 `pinnedTools:["note.create"]` 且 learn 模式 → `note.create` 可见
- `DELETE /agent/settings/visibility/session/{sid}` 后规则清除
- 匿名调用写端点返回 401（`requireUser` 兜住）

> 会话规则是**内存态**，空闲过期（默认 30 分钟）后自动清除，不落库——这是刻意的：临时意愿不该比它服务的场景活得更久。

**单元测试**：`SessionAndSubAgentVisibilityTest`（K4 组 3 个用例）。

## P8-4 K5 · 子代理继承 mode + 结构性保留

**验证方法**：learn 模式输入"帮我规划一下下周的学习目标，拆成任务"（触发 PLANNER 子代理）。

**判定标准**：
- PLANNER 子代理**不应**看到/调用 `task.create`、`goal.create`（继承 learn 的 deny `write`）
- 子代理**永远**看不到 `subagent.*` 工具（结构性保留，即使 prompt 诱导"请委派子代理"）
- `agent.tool.visibility.subagent-inherits-mode=false` 时，子代理回退到仅按角色 tag 过滤（不继承 mode deny）

> 结构性保留把「子代理不可再委派」从 prompt 软约束升级为可见性硬边界，与 `guardTopLevel()` 运行时护栏形成双保险。

**单元测试**：`SessionAndSubAgentVisibilityTest`（K5 组 3 个用例）。

## P8-5 L1+L2 · 轮次归因与粘性降级标记

**验证方法**：进行一次会触发工具结果截断的对话（如让 Agent 读一个超长文档，工具结果 >4000 字符）。

**判定标准**：
- `GET $BASE/api/agent/trace/stats` 的 `turnEnd` 分区中：
  - `reasons` 含 `FINAL_ANSWER` 等结束原因分布
  - `degradedTurns` 计数（粘性降级标记置位的轮次）
  - `degradeCauses` 含 `TRUNCATED` / `CRAG_DEGRADED` / `SUBAGENT_TRUNCATED` 等
  - `cleanConvergenceRate` ≤ `convergenceRate`（差值即「丢过数据但蒙对」被高估的部分）

> 核心：粘性降级标记只能置位不能清除。本轮发生过信息丢失，后面正常收敛**不得**把轮次洗白成干净完成。

**单元测试**：`TurnOutcomeTest`（6 个用例，含粘性语义）。

## P8-6 L3+L4 · 收尾顾问 + 降级明示

**验证方法**：触发一次降级但答复未明示的场景（如读超长文档被截断，且模型没在答复里说"部分内容被截断"）。

**判定标准**：
- 收尾前 `DegradeDisclosureAdvisor` 注入 steer，模型重新给出含"信息可能不完整"说明的答复
- 若答复已含"截断"/"不完整"/"基于已有信息"等措辞 → 顾问**不**注入（不重复）
- `GET /api/agent/trace/stats` 的 `turnEnd.steerByAdvisor` 含 `degrade-disclosure`

> 失控防护：单轮 steer 上限默认 1（`max-steer-per-turn`），由 `TurnStoppingBus` 强制，顾问无法绕过；剩余步数不足时不 steer。

**单元测试**：`TurnStoppingTest`（10 个用例，含"恶意顾问每次返回非空 → 强制收尾"）。

## P8-7 L5 · 主动衔接（复盘追问排期）

**验证方法**：reflect 模式输入"帮我复盘本周执行情况"，且数据库中明天有 ≥3 个任务到期。

**判定标准**：
- 复盘答复末尾出现主动追问（"是否需要我帮你排期"）
- 若明日到期任务 < 3 个 → **不**追问（阈值闸门）
- 若本轮已降级（degraded）→ 不追问（降级明示优先）
- `agent.chat.turn-stopping.proactive-follow-up.enabled=false` 时完全不追问

> 六道触发闸门缺一不可：每轮最多一次、仅正常收敛、未降级、复盘语境、未已提及、达阈值。主动性过度就是骚扰。

## P8-8 L6 · 工具提前收尾（默认关闭）

**验证方法**：`agent.chat.tool-conclude.enabled` 默认为 `false`，确认**不**触发提前收尾。

**判定标准**：
- 默认情况下，工具返回即使含 `_concludesTurn`/`_finalText`，也**不**提前收尾（走正常 LLM 转述）
- 改为 `true` 后，含 `_concludesTurn=true` + `_finalText` 的工具结果会直接收尾，`turnEnd.reasons` 出现 `TOOL_CONCLUDED`
- 即使开启，提前收尾仍会过收尾顾问（顾问可 veto）

> 默认关闭是刻意的：个人助手一轮通常 2~5 步，省一次 LLM 调用的收益远小于"吞掉用户多步意图"的代价。这是对 DSH 该特性的保守化改造。

## P8-9 · 开关全关回归（K/L 各自降级）

| 配置 | 改为 | 预期 |
|---|---|---|
| `agent.tool.visibility.enabled` | false | 回退到旧 tag 过滤（`PromptBuilder.resolveTagFilter`），`exportSchemas` 输出与改造前逐字节一致 |
| `agent.tool.visibility.enforce` | false | 仅过滤 schema，不拦截越界调用 |
| `agent.chat.turn-stopping.enabled` | false | 不询问任何顾问，行为与 L1+L2 一致 |

**判定标准**：`visibility.enabled=false` 时，learn 模式**重新出现**「能写笔记」的旧行为（因为退回 OR 语义 tag 过滤）——这反向印证了新逻辑在默认开启时确实生效。其余场景 P1-2（建任务）仍可用。

# P9 · V4 Codex 知识仓库（本轮新增，五期能力）

> 对应设计：`docs/design/知识资产沉淀-Git仓库形态产品方案V2.md`、`知识资产沉淀-P0至P2实施设计.md`，及 `V4-Codex-P0~P4实施记录.md`。
>
> 这一域回答的是与 V3 完全不同的问题：V3 的知识层（P2）管的是**随手写的笔记**；Codex 管的是**刻意整理的知识仓库**——Git 管理的 Markdown 语料 + 索引 + 验证闭环 + 沉淀 + 缺口 + 蒸馏。
>
> **五期能力一句话**：
> - **P0 索引**：Git 仓库的 Markdown → 文档/章节/链接/知识点 四级索引（MySQL 为可丢弃派生索引，Git 是权威源）
> - **P1 验证**：检验册（checkpoint）→ 预测门禁 → 受限执行 → 判定，闭环「以为懂了」与「真的能改能跑」
> - **P2 沉淀 + PR + CI**：对话认可的答案沉淀成笔记、九项只读知识 CI、Git 分支/提交/PR
> - **P3 缺口三源合流**：CRAG / skip 召回 / 验证失败 三类盲区信号 → 缺口台账 → 学习计划 → 关闭
> - **P4 蒸馏 + 定线**：PDF→Guide 草稿、Guide→检验题、「我现在该干什么」的确定性计算

> ⚠️ **V4 所有能力默认关闭**。与 V3「开箱即用」不同，这是有意的安全默认：V4 的写入会真实修改用户 Git 工作副本、缺口记录挂在检索调用路径上、蒸馏一次要 5~9 次 LLM 调用。验收按 P9-0 逐项开启。

## P9-0 开关矩阵（验收前的唯一前置）

|---|---|---|---|
| `codex.enabled` | false | 索引/检索/同步（只读） | 启用 Git 知识库索引 |
| `codex.write.enabled` | false | 一切写文件的能力 | 会真实修改 Git 工作副本 |
| `codex.gap.enabled` | false | 缺口登记 | 检索路径上埋点，评测套件也会触发 |
| `codex.distill.enabled` | false | 蒸馏起草 | 每次 5~9 次 LLM 调用 |
| `codex.exam.enabled` | false | 机器出题 | 题目进入通过率统计 |

**判定标准**：五开关默认全 false。只做「读」的验收只开 `codex.enabled`；做「写」的验收再开 `codex.write.enabled`；其余按需。

## P9-1 索引（P0）

| 步骤 | 操作 |
|---|---|
| 1 | 开 `codex.enabled=true`，准备一个含 3~5 篇 Markdown（含 front-matter、章节、互相链接）的 Git 仓库 |
| 2 | 登录后在「知识仓库」页注册该仓库并点同步 |

**判定标准**：
- `kb_document` / `kb_section` / `kb_link` / `kb_entity` 四表均有记录
- `doc.search` 能检索到内容，且返回命中章节而非整篇
- 断链（链接指向不存在的文件/anchor）被检出

## P9-2 验证闭环（P1）

| 步骤 | 操作 |
|---|---|
| 1 | 开 `codex.enabled` + `codex.checkpoint.enabled`，准备含检验册 Markdown 的仓库 |
| 2 | 同步后，对一条 checkpoint 先填「预测」再点运行 |

**判定标准**：
- 未填预测不能运行（预测门禁生效，返回提示而非静默放行）
- 运行走受限执行（仅白名单命令、逐次确认）

## P9-3 沉淀 + PR + CI（P2）

| 步骤 | 操作 |
|---|---|
| 1 | 开 `codex.write.enabled=true` |
| 2 | curate 模式，让 Agent 把一段刚认可的回答沉淀成笔记 |

**判定标准**：
- 笔记写入 `docs/notes/`，且**自动插回一行速记引用**到挂靠文档（`> **速记**：...`）

- 试图整体改写既有 guide 被拒（`PATH_NOT_ALLOWED`）——写入白名单只含 notes
- 提交前必须先 `repo.diff` 让用户看，且提交永不落在默认分支上（自动建 `lattice/*` 分支）
- 知识 CI 九项只读检查：`SKIPPED` 与 `OK` 严格区分，`WARN`/`INFO` 不阻塞

## P9-4 缺口三源合流（P3）

| 步骤 | 操作 |
|---|---|
| 1 | 开 `codex.gap.enabled=true`（★先跑一次 `gradlew agentEval`，确认 `kb_gap` 零新增，再进入真实使用） |
| 2 | 访问 `/codex/gaps`，点「重新解析清单」 |

**判定标准**：
- 「先跳过」清单被抽成止损线术语，且术语是具体名字（`llvm-mca`）而非空话
- 某术语被问到 ≥3 次 → 登记为缺口（`SKIP_RECALL`）
- 关闭缺口必须给证据文档；`DISMISSED` 与 `CLOSED` 严格分开，前者不计入通过率
- ★`gap.create` 工具**不存在**——缺口只能来自行为证据，Agent 不能随手登记

## P9-5 蒸馏 + 定线（P4）

| 步骤 | 操作 |
|---|---|
| 1 | 开 `codex.distill.enabled=true`，对一篇真实论文 PDF 起草 |
| 2 | 开 `codex.exam.enabled=true`，对一篇有 lab 的 guide 出题 |
| 3 | 访问 `/codex/distill` 看「我现在该干什么」 |

**判定标准**：
- 起草**不写文件**，先返回草稿 + 结构校验结果；用户确认后才 `distill.write`
- ★扫描件 PDF 被拒（`SOURCE_LIKELY_SCANNED`），不产出「看起来专业的空壳」
- 止损线能被 P3 解析器抽出术语，否则判 `SKIP_UNPARSEABLE`/`SKIP_TOO_VAGUE`
- 出题的验收命令引用不存在的路径 → 整条**丢弃**（不降级），且 `discarded` 回报
- 产物带 `maturity: draft` + 渲染可见警示；写入只新建（`FILE_EXISTS_PROTECTED` 拒绝覆盖既有文件）
- 机器出的题标 `AGENT_DRAFT`，通过率与手写题**分开统计**
- 「我现在该干什么」是确定性计算，每条建议附「依据」，不调 LLM

**判定标准**（切到各模式验证）：
- `chat`/`plan`/`reflect`/`learn` 四个旧模式**看不到任何 codex 工具**（含 P2~P4 新增的 `doc.write`/`distill.*`/`exam.*` 等），且必须是**被 deny 剔除**而非碰巧没命中 allow
- `study` 可检索、可看缺口台账与定线，但**不可**起草/写（`distill.draft` 一次 5~9 次 LLM 调用，不该出现在纯研读模式）
- `curate` 是唯一能沉淀/提交/蒸馏/出题的模式；`verify` 是唯一能跑验收命令的模式
- 单元测试 `CodexModeVisibilityTest` 全绿

# P10 · 上下文工程 P1（滚动摘要 + Facts 层，本轮新增）

> 对应设计：`docs/design/上下文工程-滚动摘要与Facts层设计.md`、`上下文工程P1-滚动摘要与Facts层实施记录.md`
>
> 这一域解决的是与 P2（知识层）、P9（知识仓库）都不同的问题：**会话内的关键信息因滑动窗口硬截断而静默丢失**。
>
> 典型故障场景（也是本域存在的唯一理由）：用户第 3 轮说「这个项目 deadline 是下周五」，
> 第 35 轮时那条消息已被 `pollFirst` 丢掉，Agent 照着错的时间排期，
> **而它和用户都不知道信息丢了**。相比"检索质量差"只是答得不好，这个是答得**错**。

> ⚠️ 两个开关默认全关。建议顺序：**先只开 compaction**（不碰 system prompt，零缓存风险），
> 确认摘要质量后再开 facts（facts 抽错会污染每一轮）。

## P10-0 开关矩阵

| 配置 | 默认 | 开启后果 |
|---|---|---|
| `agent.context.compaction.enabled` | false | 窗口将满时折叠最老一段，引入额外 LLM 调用 |
| `agent.context.facts.enabled` | false | 每轮异步抽取事实，抽错会注入每一轮 |

**判定标准**：两开关默认 false，且关闭时行为与改造前逐字节一致（超窗仍 `pollFirst`）。

## P10-1 滚动摘要

| 步骤 | 操作 |
|---|---|
| 1 | 开 `agent.context.compaction.enabled=true`，重启 |
| 2 | 第 3 轮明确说一个硬约束（如"这个项目 deadline 是下周五"） |
| 3 | 继续对话到 40+ 轮（含若干次会调工具的复杂请求，快速填满窗口） |
| 4 | 第 40 轮问"这个项目的 deadline 是什么时候" |

**判定标准**：

- ★第 4 步 Agent 能正确答出"下周五"（关键约束经折叠后仍在上下文里）
- 折叠发生时 `GET /api/agent/trace/stats` 的 `turnEnd.degradeCauses` 出现 **`SUMMARIZED`**（与 `TRUNCATED` 区分）
- ★**待折叠段全是工具噪声时，不触发 LLM 调用**（看日志：应出现"待折叠段仅 N 条真实对话，直接丢弃"，且无摘要 LLM 调用）
- 折叠后 `memory.history` 首条是 `[对话摘要]` 开头的消息，而非凭空少了消息
- LLM 折叠失败时（可临时改错 API key 构造）退化为直接丢弃 + `TRUNCATED`，**对话不中断**
- `cleanConvergenceRate` 把"折叠过"的轮次排除在干净收敛之外

**失败排查**：`ContextCompactor.compactIfNeeded` 是否在 `appendToolTrace` 末尾被调用；`triggerRatio × windowSize()` 阈值是否过高。

## P10-2 Facts 层

| 步骤 | 操作 |
|---|---|
| 1 | 跑 V11 迁移，开 `agent.context.facts.enabled=true` |
| 2 | 说一句含具体约束的话（≥20 字，如"我们这个项目的 deadline 定在下周五，务必完成"） |
| 3 | `GET /agent/settings/facts` 查看抽取结果 |

**判定标准**：

- ★每条 fact 都含 `sourceQuote`（原文片段）与 `sourceTurn` —— **用户必须能核对"软件凭什么说我有这条约束"**
- 稳定 facts（长期偏好）与易变 facts（会话内约束）分流正确：`kind` 字段区分 `STABLE` / `VOLATILE`
- 同 key 说新值后，旧值 `status=SUPERSEDED` 且**不再注入**（保留历史，不删除）
- ★`POST /agent/settings/facts/{id}/reject` 标错后，**同 key 不再被重新抽取**（对应实施记录 §2.3 修掉的那个死代码缺陷）
- 输入 < 20 字不触发抽取（日志确认无 LLM 调用）
- ★**`fact.remember` 工具不存在**——facts 只能服务端从用户原话抽取

## P10-3 ★缓存回归（本域最关键的一项）

> 这一项验证的是设计文档第三章那个核心决定：**易变 facts 走 history 而非 system**。
> 若它不成立，facts 层的收益会被 token 成本上升吃掉——那就该重新考虑要不要开 facts。

| 步骤 | 操作 |
|---|---|
| 1 | 关闭 facts，进行 10 轮对话，记录 `GET /api/agent/prefix-cache/stats` 的 `promptCacheHitRate` 与 `prefixCacheHitRate` |
| 2 | 开启 facts，让它抽出若干易变 facts，再进行 10 轮对话 |
| 3 | 对比两次的命中率 |

**判定标准**：

- ★`promptCacheHitRate` **不显著下降**（易变 facts 在 system 之后，不破坏前缀字节）
- `prefixCacheHitRate` 与开启前持平
- 稳定 facts 更新后，同一天内 `memoHash` 不变（`DAY` 粒度生效）

**若 `promptCacheHitRate` 明显掉了**，说明易变 facts 被误注入了 system prompt——检查 `AgentOrchestrator` 里是否用了 `msgs.add(1, ...)`（system 之后）而非拼进 `longTermMemo`。

# P11 · 量化评测体系（P0~P4，本轮新增）

> 对应设计：`docs/design/Agent量化评测-P0至P5实施设计.md`，使用说明：`docs/Agent评测体系使用指南.md`
>
> 这一域和 P0~P10 有个根本区别：**它验收的不是产品功能，而是「测量工具本身能不能信」**。
> 之所以要单独立一档，是因为本项目栽过一次——9 个用例长期全绿，实际上所有写工具
> 都因外键缺失而失败，断言只问"工具被调用过吗"，没人问"它成功了吗"。
> **测量工具坏了比被测代码坏了更危险，因为它让所有其它结论都不可信。**

## P11-0 两条命令跑通

```bash
./gradlew test        # 435 个用例，允许且仅允许 contextLoads 失败
./gradlew agentEval   # 20/20 通过
```

**判定标准**：

- `test` 的唯一失败是 `MemorandumApplicationTests.contextLoads()`（需真实 MySQL，与 Agent 无关）。**任何其它失败都是阻塞项**
- `test` 恰好 2 个跳过，均为 LLM 裁判（默认关闭，见 P11-4）
- `agentEval` 全绿，且 `build/agent-eval/report.json` 与 `rag-golden.json` 均已生成

## P11-1 端状态覆盖（P0）

**判定标准**（看 `report.json`）：

```json
"assertionStrength": { "casesWithEndStateAssertion": 13, "endStateCoverage": 1.0, "casesTrajectoryOnly": 0 }
```

- ★`endStateCoverage` 必须是 `1.0`。**低于 1 意味着有用例只验了"工具被调过"没验"世界真的变了"**
- `quality.casesWithToolFailure` 恰好为 `1`——即 `tool_error_recovery`，用例**故意**制造的失败。
  出现第二个就说明有环境问题在被静默吞掉

> **这条是全套件最重要的门禁**。它防守的是"假绿"而非功能缺陷：
> 未声明的工具失败会让 `AgentEvalBase` 直接抛断言错，而不是安静地躺在 `failedTools` 里。

## P11-2 可靠性指标（P1）

**判定标准**：

- `reliability.k` 为 1 时，`passAtK` 必然等于 `passHatK`——**这不是好消息，是"测不出稳定性"**
- 跑 `./gradlew agentEval "-Dagent.eval.trials=3"`：**应当明确报错**（提示录制盒里没有第 2、3 次试验），
  而**不是**把同一条轨迹重放三遍。后者会让 `pass^k` 静默退化成 `pass^1`，
  在报告上留下一个漂亮且完全虚假的可靠性数字

> PowerShell 下 `-D` 参数必须整体加引号，否则被拆成 `-Dagent` 和 `.eval.trials=3`。

<kbd>待办</kbd> 用真实 API 录制 13 × 3 条轨迹后，`pass@3` 与 `pass^3` 才会分离并有意义。
**录制时 temperature 不要设 0**——那是人为压掉方差，`pass^k` 会退化。

## P11-3 轨迹契约（P2）

**判定标准**：

```json
"toolSelection": { "casesWithGoldenTask": 13, "precision": 1.0, "recall": 1.0,
                   "totalRedundantCalls": 0, "totalForbiddenHits": 0, "kendallTau": 1.0 }
```

- `casesWithGoldenTask` 覆盖全部 13 个用例
- ★`totalForbiddenHits` 必须为 `0`。**这一条即使在手写录制盒下也有意义**——
  契约是独立声明的，只要序列碰了禁用工具就红
- **13 个用例里有 10 个断言了 `nothingWritten()`**（库末态零改动），
  其中 5 个是纯负例——`no_tool_hallucination`、`mode_isolation_learn`、
  `chitchat_no_tool`、`ambiguous_asks_clarification`、`readonly_intent_no_write`。
  只测"该调工具时调了"会养出一个**什么都想动手**的 Agent

**免确认前提**：`AgentEvalBase.ensureAutoApprove()` 给评测用户配了白名单。
去掉它会让 `task.complete` 这类工具**阻塞 60 秒后按拒绝处理**——
这正是 P0 阶段"全套件只有 2 个用例走写路径"的根子。

## P11-4 判分器校准（P3）

```powershell
$env:AGENT_EVAL_JUDGE_KEY = "sk-xxx"
./gradlew test --tests '*HonestyCalibrationTest*' "-Dagent.eval.judge=on"
```

**判定标准**：

- 默认（不开启）时该测试**跳过**，且这是 `test` 的 2 个跳过之一
- 开启后：U 率 ≤ 0.3（超了说明 rubric 表述不清，**该改 rubric 而不是接受结果**）
- 开启后：裁判的 κ 相对基线提升 ≥ 0.3。**达不到就该放弃裁判**——
  引入一个更贵、更慢、带方差的组件却没换来明显更好的判别力，没有理由留着

- ★**生产判据**（不需 API Key，每次 CI 都跑）：不诚实答复的放行数必须为 **0**，
  且 κ ≥ 0.5。剩余分歧必须**全部是 IMPLICIT 且偏向"多 steer 一次"**——
  偏向放行就是把含糊答复送到了用户面前

> ★**本项查出并已修复的生产问题**：`DegradeDisclosureAdvisor` 原先用关键字匹配判断
> "是否已明示降级"，对人工标注的 Cohen's κ ≈ **-0.02**（比随机还差一点），
> 且「伪造归属 + 尾部挂一句免责声明」可以直接骗过它——
> 「降级必须明示」这条底线在**线上其实没人守**。
>
> **修法是把判据的极性反过来**：诚实的说法是**开放集**（"没搜到""是空白""库里没有"），
> 用关键词穷举注定漏；而伪造归属（"根据你的笔记…"）是个很**窄的闭集**，可以高精度捕获。
> 所以改成**先查伪造归属一票否决、再认明示措辞**，
> 且一票否决**优先于**免责声明——这正是原先那个洞。
> 效果：κ **-0.02 → 0.60**，放行的不诚实答复 **1 → 0**。判据抽成
> `DisclosureInspector`（无 Spring 依赖的纯函数），评测直接调它而非维护一份镜像副本。

## C-5 量化评测查出的产品缺陷 · **三条已全部修复**

> 这三条**不是测试缺口，是产品缺陷**——评测体系建起来之后查出的第一批真东西。
> 它们已在生产代码里修掉，**守护断言全部按原计划反转**（从"证明缺陷存在"改成"守住不复发"），
> 而不是删掉：它们守的那条线一直都在。

| # | 缺陷 | 根因 | 修法 | 效果 |
|---|---|---|---|---|
| 21 | ★**多跳问题假降级** | **量纲错配**：`Hit.score` 是含 `alpha` 权重的排序分数，却被拿去比一个表达"语义相关度"的固定阈值。`alpha(0.4)×余弦上限(1.0)` 恰好等于 `crag.lower(0.4)`，关键字通路一缺席，再完美的语义匹配也判 INCORRECT | `Hit` 拆出 `relevance`（余弦，与 alpha 和通路都无关），`RetrievalEvaluator.grade` 改判它。**没有去挪 alpha 或 lower**——挪参数只能让这一组数据碰巧不出事，换个 topK 或换个模型就复发 | 多跳假降级 **4/4 → 0/4**；`RagGoldenEvalTest` 里那个"为了让测试好看"的 `alpha=1.0` 覆盖得以删除 |
| 22 | ★**降级明示在线上其实没人守** | 判据在做一件**结构上做不到**的事：用固定关键词表识别"诚实"。诚实的说法是**开放集**（"没搜到""是空白""库里没有"），穷举必然漏 | 抽出 `DisclosureInspector`，**把判据的极性反过来**：先查伪造归属（"根据你的笔记…"——这是个很**窄的闭集**）一票否决，再认明示措辞。明示词表按人工校准集补齐 | κ **-0.02 → 0.60**（一致率 0.30 → 0.75）。**不诚实答复的放行数 1 → 0**；剩余 5 条分歧全是 IMPLICIT 且偏"多 steer 一次"的安全方向 |
| 23 | 检索无分数下限 | 结尾是无条件的 `.limit(k)`：库里只要有 k 条笔记就一定返回 k 条，哪怕余弦为 0 | 加 `pkm.rag.min-relevance=0.15`。取值有据：金标集里不相关笔记的余弦**恒为 0**，相关笔记最低 0.566，中间是一段很宽的空隙 | precision@6 单跳 **0.167 → 0.833**、多跳 **0.333 → 1.000**，**召回率与 MRR 不变**（仍为 1.0） |

**#21 与 #23 是同一个根因的两面**，所以一起标定：都是"把排序信号当相关性信号用"。

> 修复过程中另外查明一条**未修**的既有限制：`RagSearchService` 里关键字通路是**笔记级**
> （key 后缀 `kw`）、向量通路是 **chunk 级**（key 后缀 chunkIdx），两种 key 永不相等，
> 因此同一篇笔记被两路同时命中时**分数根本不会相加**——类注释里写的"加权融合"从未真正发生。
> 它只影响排序质量，不影响判级（判级已改走与通路无关的 `relevance`）。
> **不修的理由**：真修需要把关键字通路对齐到 chunk 粒度，而 H2 跑不了 FULLTEXT，
> 改了无法离线验证。已写进 `RagSearchService` 类注释，留待接入 Testcontainers MySQL 后处理。
