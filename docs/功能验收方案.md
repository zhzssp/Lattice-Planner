# Lattice-Planner 系统性功能验收方案

> 适用分支：`V3.0.0`
> 覆盖范围：`docs/design/` 下 16 份设计文档所描述的全部已实现功能
> 目的：在考虑后续功能扩展**之前**，用可复现的步骤逐条确认既有功能真实可用、且符合各设计文档自定的验收标准。

---

## 如何使用本文档

1. 按 **P0 → P7** 顺序执行，前一阶段不通过不要进入下一阶段（存在依赖关系）。
2. 每个验收项都有明确的 **判定标准**（PASS 条件），只认客观现象，不认"看起来没报错"。
3. 每项附 **失败排查** 指向具体文件，便于定位。
4. 全部执行完毕后填写文末 **附录 A 验收结论清单**。
5. 标注 <kbd>预期为禁用</kbd> 的项，"返回错误"才是 PASS，不要误判为 Bug。

### 术语约定

| 记号 | 含义 |
|---|---|
| `$BASE` | `http://localhost:8080` |
| `$SID` | 浏览器登录后的 `JSESSIONID` Cookie 值 |
| `$TOKEN` | MCP Token 明文（`lattice_` 开头，仅生成时展示一次） |
| <kbd>预期为禁用</kbd> | 该能力被主动禁用，返回错误即为正确 |

# P0 · 环境就绪与阻塞项清除

> 本阶段不验证业务功能，只保证后续验收能跑起来。**P0 有 3 个已知阻塞项，必须先处理。**

## P0-1 阻塞项：`electron-app/package.json` 语法错误

**现象**：文件第 1 行是 `git {` 而非 `{`，属于无效 JSON，`npm install` / `electron .` 会直接解析失败。

```json
git {
  "name": "Lattice-Planner",
```

**处理**：删掉行首的 `git ` 三个字符，使首行为 `{`。

**判定标准**：`cd electron-app && node -e "require('./package.json')"` 无报错输出。

> 影响范围：仅影响 Electron 桌面端（P4-3 晨晚报通知、DDL 提醒）。纯 Web 验收不受阻，可暂缓。

## P0-2 阻塞项：`electron-app/preload.js` 重复注入

**现象**：`contextBridge.exposeInMainWorld('lattice', ...)` 被复制粘贴了两次（约 L18-24 与 L26-34）。Electron 对同一 key 重复暴露会抛错，渲染进程拿不到 `window.lattice`。

**处理**：删除重复的第二段，只保留一处。

**判定标准**：Electron 启动后在渲染进程 DevTools 执行 `typeof window.lattice` 返回 `"object"`，控制台无 `exposeInMainWorld` 相关报错。

## P0-3 阻塞项：`permission-config.json` 白名单指向不存在的目录

**现象**：`allowDirs` 为 `D:/notes`、`D:/learning`、`C:/Users/Public/Documents`，本机大概率不存在前两个。

**处理**：改为本机真实存在的目录，例如：

```json
"allowDirs": ["C:/Users/<你的用户名>/Desktop/verify-docs"]
```

> 注意：此配置只服务于 **Electron LocalBridge** 通道。而 v3 之后 Agent 读本地文档走的是**后端直读 + MCP loopback**（白名单由 `mcp.server.local-allowed-dirs` 控制，留空则默认整个用户主目录）。两套白名单互不影响，别混淆。

## P0-5 环境变量

| 变量 | 必需性 | 缺失后果 |
|---|---|---|
| `DEEPSEEK_API_KEY` | **必需** | Agent 对话全链路不可用（P1 起全部失败） |
| `EMBED_API_KEY` | **RAG 必需** | 向量检索降级为纯关键字，P2 大部分项无法验收 |


启动日志中**必须**出现以下 4 条，缺一即为 P0 不通过：

|---|---|---|---|
| 1 | `[Agent] Registered N local tools:` | 工具注册表扫描完成 | `ToolRegistry.scan()` 未触发 |

# P1 · Agent 内核（对应《Agent实现方案》）

## P1-1 页面注入与面板可用

| 步骤 | 操作 |
|---|---|
| 1 | 访问 `$BASE/register` 注册用户（密码 ≥5 位） |
| 2 | `$BASE/login` 登录 → 自动跳转 `/select-features` |
| 3 | 选择思维模式 → 进入 `/dashboard` |

**判定标准**：以下 4 个页面右侧均出现 Lattice-Agent 面板（含模式下拉、模型下拉、⚙设置、关闭按钮）：

- `/dashboard`
- `/memo/add`
- `/preference/settings`
- `/select-features`

**失败排查**：检查对应 `templates/*.html` 是否 `th:replace` 引入了 `fragments/agent-panel.html`。

## P1-2 WebSocket 建连与 ReAct 循环

**端点**：`ws://localhost:8080/ws/agent/{sessionId}`（同源握手自动带 `JSESSIONID`，Spring Security 注入 Principal）

| 步骤 | 操作 | 预期 |
|---|---|---|
| 1 | 打开面板，DevTools → Network → WS | 连接状态 101 Switching Protocols |
| 2 | 输入"帮我建一个任务：周五前写完验收文档" | 依次出现 `toolStart` → `toolResult` 卡片 → 最终自然语言回复 |
| 3 | 刷新 `/dashboard` | 任务真实落库并显示 |

**判定标准**：
- 工具调用卡片显示的工具名为 `task.create`（不是编造的名字）
- 任务在数据库 `task` 表中真实存在
- 最终回复是中文自然语言，**不含裸露的 JSON**（验证 `ToolCallParser.cleanForDisplay` 生效）

**失败排查**：
- 无 WS 连接 → `AgentWebSocketConfig` 路径 / `WebSecurityConfig` 的 `/ws/agent/**` CSRF 豁免
- 回复里有 JSON 残留 → `ToolCallParser.cleanForDisplay` 的正则

## P1-3 四种模式的工具隔离

`PromptBuilder.resolveTagFilter` 按 mode 过滤工具集：

| mode | 应可见 tag |
|---|---|
| chat | 全部（无过滤） |
| plan | task, goal, planner, kb, read, write, subagent, mcp |
| reflect | task, goal, insight, note, kb, read, subagent, mcp |
| learn | kb, note, read, subagent, mcp |

**验证方法**：切到 `learn` 模式，输入"帮我建一个任务" →

**判定标准**：Agent **不应**成功调用 `task.create`（该工具在 learn 模式下不可见），而应回复"当前模式不支持"或改用检索类工具。若它仍成功建了任务，说明 tag 过滤失效。

## P1-4 Reflexion（工具失败自纠）

**验证方法**：输入"删除 id 为 999999 的任务"（不存在的 id）。

**判定标准**：
- `toolResult` 卡片显示错误 JSON（如 `{"error":"NOT_FOUND"}`）
- Agent **不会崩溃或空转**，而是把错误消化后给出合理答复（"该任务不存在"）
- 步数不超过 `agent.chat.max-steps=24`

> <kbd>已知缺口</kbd>《Agent实现方案》V3 Day3-4 规划的**显式** Reflexion（"连续 2 次同名工具失败则强制换工具"）**未实现**，当前只有隐式的错误回灌。本项只验收隐式行为。

## P1-5 <kbd>预期为禁用</kbd> 本地文档摄取

**验证方法**：输入"把 C:/Users/xxx/Desktop/verify-docs/plan.md 摄取进知识库"。

**判定标准**：返回 `{"error":"WRITE_DISABLED", "message":"v3 当前为只读模式..."}`。

**这是正确行为**。原因：本地文件访问从 Electron Bridge 迁移到 MCP 后端直读后，`kb.ingest_local_doc` 依赖的 `localBridge` 失去载体，故整条写链路被主动降级为只读（真实实现以注释保留在 `KnowledgeTools.ingestLocalImpl`）。

**连带影响**：`note_embedding` 表中不会有 `source='LOCAL_DOC'` 的行，因此 P2 的检索验收只能基于**手写笔记**，不能基于本地文档。

# P2 · 知识层（PKM-RAG + CRAG + RAG Serving）

## P2-1 笔记向量索引（《PKM-RAG实现方案》）

| 步骤 | 操作 |
|---|---|
| 1 | `$BASE/note/new` 新建 3~5 篇笔记，内容互相区分明显（如"Kafka 消费者组"、"MySQL 索引下推"、"Redis 持久化"） |
| 2 | 保存后等待 3~5 秒（`NotePersistedEvent` 异步索引，线程名前缀 `pkm-`） |

**判定标准**：

```sql
SELECT source, note_id, chunk_idx, LEFT(embedding, 40), model
FROM note_embedding WHERE source='NOTE';
```

- 有记录，且行数 ≥ 笔记数（长笔记会切多个 chunk）
- `embedding` 是 JSON 数组，`model` 为 `BAAI/bge-m3`

**失败排查**：`EMBED_API_KEY` 未设置 → 日志会有 Embedding API 失败告警；`NoteIndexService.rebuildForNote` 是否被 `NotePersistedListener` 调用。

## P2-2 Hybrid 检索

**方式 A（页面）**：`$BASE/note/search?q=消费者组&topK=6`

**判定标准**：返回 JSON 数组，命中项含 `score`、`reason` 字段；`reason` 应能体现关键字/向量两路来源（验证 `alpha=0.4` 融合生效）。

**方式 B（Agent）**：面板输入"我之前记过关于 Kafka 的笔记吗？"

**判定标准**：
- Agent 先调用 `kb.semantic_search`（不是直接凭记忆回答）
- 引用笔记时使用 `[[标题]]` 格式，且前端渲染为可点击链接
- 点击链接跳转到 `/note/by-title/{title}` 并正确打开笔记

## P2-3 CRAG 状态机（《AI-Infra-CRAG-SelfRAG实现计划》）

> 本轮刚修复：`grade`/`degraded` 此前只在**零命中**时返回，导致"有命中但质量差"的降级信号丢失、Self-RAG 链路断开。现改为**无条件返回且置于数组首位**。

### P2-3a `_meta` 行结构验证

**验证方法**：Agent 输入任意涉及笔记的问题，展开 `toolResult` 卡片查看 `kb.semantic_search` 原始返回。

**判定标准**：返回数组的**第 0 项**是元信息行，形如：

```json
{
  "_meta": "crag",
  "grade": "CORRECT",
  "degraded": false,
  "hitCount": 3,
  "usedQueries": ["我之前记过关于 Kafka 的笔记吗"],
  "message": "检索质量良好：可直接引用命中片段，引用笔记用 [[标题]] 写法。"
}
```

**这是本轮修复的核心验证点**：即使 `hitCount > 0`，`grade` 与 `degraded` 也必须存在。

### P2-3b 三种 grade 分支

| 构造方式 | 预期 grade | 预期 Agent 行为 |
|---|---|---|
| 问笔记里写得很清楚的内容 | `CORRECT` | 直接引用，正常作答 |
| 问笔记里沾边但不精确的内容 | `AMBIGUOUS` | 提醒"检索结果相关性一般，仅供参考" |
| 问完全无关的内容（如"我记过关于量子色动力学的笔记吗"） | `INCORRECT` + `degraded=true` | **首句明示**"未找到强相关笔记，以下基于通用知识：" |

**判定标准**：第三种情况下，Agent 回复首句必须出现降级声明。若它假装命中或直接答通用知识而不声明，说明 `_meta` 未被 LLM 正确消费（检查 `PromptBuilder` 的【知识检索原则】段）。

### P2-3c 改写重检索上限

**验证方法**：触发一次 `AMBIGUOUS`/`INCORRECT`，观察日志。

**判定标准**：
- 日志出现 `[CRAG] 检索质量=... 触发改写重检索`
- `_meta.usedQueries` 数组长度 ≥ 2（原 query + 改写 query）
- **重检索只发生 1 次**（不出现第二轮改写日志）

### P2-3d `pkm.crag.enabled` 开关（本轮修复）

> 此前该配置项存在但**代码中无任何地方读取**，CRAG 无法关闭，违反计划自定的验收标准。

| 步骤 | 操作 |
|---|---|
| 1 | `application.properties` 改 `pkm.crag.enabled=false`，重启 |
| 2 | 重复 P2-3b 的第三种情况（完全无关的问题） |

**判定标准**：
- `_meta.degraded` 恒为 `false`
- `usedQueries` 长度恒为 1（**不触发改写**）
- 日志**不出现** `[CRAG] ... 触发改写重检索`
- `GET $BASE/api/pkm/rag/stats` 中 `crag.metrics.bypassCount` 随每次检索递增
- `crag.config.enabled` 显示 `false`

验证完记得**改回 `true`**。

## P2-4 RAG Serving（《AI-Infra-RAG-Serving-System实现计划》）

### P2-4a 语义查询缓存（R1）

| 步骤 | 操作 |
|---|---|
| 1 | 先 `GET $BASE/api/pkm/rag/stats` 记下 `ragServing.metrics.queryCache` 基线 |
| 2 | Agent 问同一个问题**两次**（第二次可换个说法但语义相同，如"Kafka 消费者组是什么" / "跟我说说 Kafka 的消费者组"） |
| 3 | 再拉一次 stats |

**判定标准**：
- `queryCache.hit` 增加了 1（语义命中，阈值 `0.93`）
- `latency.avgCacheHitMs` **明显小于** `latency.avgCacheMissMs`
- `latency.avgSavedPerHitMs` > 0 ← **这就是"你怎么证明有效"的量化答案**

### P2-4b 写失效

| 步骤 | 操作 |
|---|---|
| 1 | 命中缓存后，去 `/note/{id}/edit` 修改任意一篇笔记并保存 |
| 2 | 再问同一个问题 |

**判定标准**：`queryCache.miss` 增加（缓存已被 `NoteIndexService` 主动失效），而非继续命中陈旧结果。

### P2-4c 二阶段 Rerank（R2，默认关闭）

| 步骤 | 操作 |
|---|---|
| 1 | 确认默认 `pkm.rag.serving.rerank.enabled=false` → stats 中 `rerank.invoked` 与 `fallback` 均为 0 |
| 2 | 改为 `true` 重启，问一个能召回 >6 条候选的宽泛问题 |

**判定标准**：
- `rerank.invoked` 或 `rerank.fallback` 至少一个递增（证明埋点生效——此前这两个计数器**从无调用点，恒为 0**）
- **关键**：即使 `fallback` 递增（LLM 超时/解析失败），检索结果仍正常返回、**不劣化**（验证"尽力而为"语义）
- `rerank.fallbackRate` 可见

### P2-4d 预取（R3）

**验证方法**：Agent 输入"帮我深入研究一下我笔记里关于消息队列的所有内容"（触发 RESEARCH 子代理）。

**判定标准**：stats 中 `prefetchCount` 递增（`SubAgentRunner` 在 RESEARCH 启动前调用了 `prefetch`）。

# P3 · MCP 双向能力

## P3-1 MCP Server：Token 管理（《Lattice-MCP-Server设计方案》）

> ⚠️ `/mcp/settings` 落在 `permitAll` 分支，但 Controller 用 `@AuthenticationPrincipal` 直取 `getUsername()`，**匿名访问会 NPE**。必须先登录。

| 步骤 | 操作 |
|---|---|
| 1 | 登录后访问 `$BASE/mcp/settings` |
| 2 | 生成一个 Token，label 填 `verify-external` |
| 3 | **立即复制明文**（`lattice_` 开头，仅展示一次） |

**判定标准**：
- 页面列出 Token（只显示 label / 创建时间 / 最近使用，**不显示明文**）
- 数据库 `mcp_token.token_hash` 存的是 SHA-256，**不是明文**

## P3-2 MCP Server：协议栈手工验证

用生成的 `$TOKEN` 模拟一个外部 MCP 客户端：

```bash
# 1) 建立 SSE 连接（保持此终端不关）
curl -N "$BASE/sse?token=$TOKEN"
```

**判定标准**：立即收到 endpoint 事件：

```
event:endpoint
data:/mcp/message?sid=<uuid>
```

> 注意 `data` 是**相对路径**。这正是本轮修复的根因——旧版 `McpSseClient` 直接把它丢给 `HttpClient`，而 Java `HttpClient` 拒绝相对 URI，导致 loopback 永久连不上。修复后客户端会用 SSE base URL 补全为绝对地址。

```bash
# 2) 另开终端，用上一步的 sid 发 JSON-RPC
curl -X POST "$BASE/mcp/message?sid=<uuid>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

**判定标准**：第一个终端的 SSE 流推回 `tools/list` 响应，且工具列表：

- **包含** `local.list_dir`、`local.read_file`、`local.read_pdf`、`local.read_document`
- **不包含** `kb.ingest_local_doc`、`kb.delete_local_doc`（v3 已从 `exportLocalTools()` 移除，收紧为纯只读）

再验资源：

```bash
curl -X POST "$BASE/mcp/message?sid=<uuid>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"resources/list","params":{}}'
```

**判定标准**：返回 5 个资源 URI（`McpResourceAdapter` 定义）。

**鉴权回归**：用伪造 token 连接 →

```bash

```

**判定标准**：连接被拒（`McpAuthException`），**不返回任何工具信息**。

## P3-3 MCP Client：loopback 连接（本轮核心修复）

**验证方法**：

```bash
curl -b "JSESSIONID=$SID" "$BASE/api/mcp/client/servers"
```

**判定标准**：

```json
{
  "enabled": true,
  "servers": [{
    "name": "loopback",
    "url": "http://localhost:8080/sse",
    "connected": true,          // ← 必须为 true
    "toolCount": 20,            // ← 业务工具 + 4 个 local.*
    "tools": [
      {"name": "mcp.loopback.local.read_document", "...": "..."}
    ]
  }]
}
```

**这是本轮修复的最终验收点**。修复前此处必然是 `"connected": false, "toolCount": 0`。

**失败排查**（按顺序）：
1. 日志有无 `[MCP Client] loopback 连接成功` → 无则看下一条
2. 日志有无 `[MCP Client] 收到 endpoint 事件：http://localhost:8080/mcp/message?sid=...` → 若打印的是 `/mcp/message?sid=...`（无 host），说明 `McpSseClient.resolveAbsoluteUrl` 未生效
3. `mcp.client.servers.loopback.url` 端口是否与实际端口一致（硬编码 8080）
4. 数据库有无用户 → `McpClientManager.autoWireLoopbackToken` 需要至少一个 User 才能自动签发 token
5. 手动重连：`curl -X POST -b "JSESSIONID=$SID" "$BASE/api/mcp/client/servers/loopback/reconnect"`

## P6-1 前缀缓存命中（Prefix Caching P1-P3、P5）

| 步骤 | 操作 |
|---|---|
| 1 | 记录基线 `GET /api/agent/prefix-cache/stats` |
| 2 | 同一 mode 下连续发 3 条消息 |
| 3 | 再拉一次 |

**判定标准**：

```json
{
  "config": {"enabled": true, "size": 1},
  "metrics": {
    "prefixCacheHit": 2,
    "prefixCacheMiss": 1,
    "prefixCacheHitRate": 0.6667,
    "prefixBuildCount": 1,
    "avgBuildMs": 3.2,
    "estimatedBuildTimeSavedMs": 6
  }
}
```

- 首次 miss、后续 hit（同 mode + 同工具集 + 同 memo + 同日 → key 相同）
- `prefixBuildCount` **远小于**消息数（证明前缀被复用）
- `estimatedBuildTimeSavedMs` > 0 ← **量化收益**

**前缀字节稳定性**（计划明确要求）：连续两次同输入 `buildPrefix`，`prefixHash` 必须完全相同。间接验证：`prefixCacheHit` 能持续增长说明 key 稳定；若每次都 miss，说明 `toolsetHash`/`memoHash` 在漂移。

**切换 mode 验证 key 生效**：从 chat 切到 plan → 应产生一次新的 miss（`mode` 是 key 的一部分）。

**开关回归**：`agent.prefix-cache.enabled=false` 重启 → `config.enabled=false`，功能正常但无缓存收益（`prefixCacheMiss` 持续增长）。

## P6-2 上游 prompt cache 透传（Prefix Caching P4）

> DeepSeek 的 context caching 是**自动**的（按前缀命中，无需显式传 cache_id），应用侧能做的就是保证前缀字节稳定 + 读取 `usage` 观测。

**验证方法**：进行 5~10 轮对话（前缀需足够长才会触发上游缓存，通常 >1024 token），然后看 stats。

**判定标准**：

```json
"upstreamPromptCache": {
  "chatCalls": 12,
  "usageReportedCalls": 12,
  "promptCacheHitTokens": 8460,
  "promptCacheMissTokens": 3200,
  "promptCacheHitRate": 0.7255
}
```

- `chatCalls` 与实际 LLM 调用次数一致
- `promptCacheHitTokens` > 0 ← **这直接证明"前缀字节稳定化"真的让服务端缓存命中了**，是三大计划里最有说服力的一个数据

**若 `promptCacheHitTokens` 恒为 0**，可能原因：
1. 前缀长度不足上游缓存最小阈值（DeepSeek 需 ≥1024 token）—— 属正常
2. 上游未返回 `usage` 字段 → 看 `usageReportedCalls` 是否为 0
3. 前缀在漂移 → 回头查 P6-1 的 `prefixCacheHitRate`
