## 三、逐页内容

### 第 1 页 · 封面

**放**：项目名 `Lattice-Planner`、一句话定位、姓名/专业。

**定位语（背熟）**：

> 一个面向个人的目标管理应用，我给它内置了一个**从零手写的 Agent 运行时**——不依赖 LangChain / Spring AI，自己实现了 ReAct 循环、工具系统、子代理、检索闭环、上下文工程和可观测层。

**副标题**：把「读我的资料、帮我规划」从想法落地成一个**可工程化**的 Agent 系统

**封面要传达的三个信号**：不是"调 API 做了个聊天框" / 自己实现了运行时关键机制 / 有评测、有指标、能证明有效。

---

### 第 2 页 · 项目是什么（产品视角）

**放**：左侧产品功能点，右侧一句"为什么会演进成 Agent"。

**讲**：

> 它本身是个人目标/任务/笔记管理工具。后来我想让它能"读我的资料、帮我规划"，就逐步演进成了一个内置 Agent 的系统。

**功能点（4~5 个）**：任务/目标/笔记管理 + 多思维模式 · 规划得分（三维 0~100）· 内置 Agent 对话 · 桌面端 + DDL 提醒

**承上启下**：

> 技术重点全在 Agent 这一块，其他是常规 CRUD，下面我主要讲 Agent 的运行时设计。

### 第 5 页 · 为什么自己写 Agent 内核 ⚡

**放**：三个"控制点" + 一句"我知道有框架"。

**讲**：

> 我知道有 LangChain、Spring AI。手写是因为要三个控制点，它们要么被框架封装掉、要么要 hack：
> 1. **步数上限**与耗尽后的降级措辞（给"请拆分任务"而非抛异常）
> 2. **工具按模式隔离**（学习模式不该看到写工具）
> 3. **确认策略能被用户运行时降权**（auto-approve 是用户级配置）

**收尾**：这让我真正理解 Agent 运行时的每个机制，而不是"调 API 做了个聊天框"。

### 第 6 页 · 亮点一：MCP loopback（调用链图）

**图结构**（纵向 6 节点链路）：

```
LLM 决定调 mcp.loopback.local.read_document
        ▼
ToolRegistry.invoke() 识别 "mcp." 前缀
        ▼
McpToolProxy 解析 serverName=loopback
        ▼
POST localhost:8080/mcp/message（JSON-RPC: tools/call）
        ▼
[同一 JVM] McpSseEndpoint 处理
        ▼
结果经 SSE 流式推回
```

**图上必须标注**：
- 中间虚线框：**"同一 JVM，仍走 HTTP + SSE + JSON-RPC"**
- 底部：**"多一次本机回环（<5ms），换来协议栈完整复用"**

---

### 第 7 页 · 亮点一：为什么绕这一下（三栏对照）

| 收益 | 说明 |
|---|---|
| ① 协议栈真通 | Server/Client 两套代码（SSE 建连、initialize 握手、tools/list 发现、tools/call 调用）都被真实验证，不是摆设 |
| ② 扩展零成本 | 接第三方 MCP Server 只需配置加一条，代码路径完全一样，工具自动以 `mcp.<server>.<tool>` 出现 |
| ③ 暴露真实 bug | 正因走真协议，才发现服务端返回 endpoint 是相对路径、Java HttpClient 不接受的 bug；走捷径会潜伏到接外部服务器那天 |

**底部结论**：

> 这是一个关于「抽象边界」的选择——宁愿多 5ms 回环，也要让协议栈真实可用。

---

### 第 8 页 · 亮点二：两类失败对照表

| 失败类型 | 现象 | 传统做法 | 我的机制 |
|---|---|---|---|
| 工具**坏了** | 抛异常/参数错/工具不存在 | 让 LLM 自己看错误重试 | **Reflexion**：按失败模式注入策略 + 超阈值强制封禁 |
| 工具**好了但没查到好东西** | 检索成功但质量差 | 提示词里写"质量差要说明" | **CRAG**：自评质量 → 改写重检索 → 结构化降级信号 |

**表格下必须加这一行**：

> 第二类比第一类更危险：检索返回低相关片段，LLM 会**编出看似有据的错误答案**，比明确说"我不知道"危险得多。

---

### 第 9 页 · 亮点二：两个机制的"硬闭环"本质

**左栏 · Reflexion 的深度**：
- 失败分 7 类：参数错 / 资源不存在 / 权限拒绝 / 用户拒绝 / 工具幻觉 / 偶发故障 / 工具不可见
- 分类主轴是**可重试性**：确定性失败**一次即封禁**，不浪费第二步去证明"权限拒绝还是会拒绝"
- 两层：建议层（注入策略提示）+ 执行层强制（封禁后再调直接短路，不真正执行）

**右栏 · CRAG 的深度**：
- 按融合分数分级：≥0.6 直接用 / 0.4~0.6 改写重检索 / <0.4 改写仍不行则降级
- 降级时塞一个**给 LLM 读的行动指令**（不是给人看的）
- 本质：**质量评估在服务端确定性完成，不赌模型自觉**

**底部结论**：把"提示词软约束"升级为"运行时硬闭环"。

### 第 10 页 · 亮点三：工具分层遮蔽

**四层图**（纵向堆叠）：

```
┌ GLOBAL  全局：全量工具注册表 ─────────────┐
├ MODE    模式：执行/学习/规划/复盘 的权限边界 │
├ ROLE    角色：规划/复盘/检索 子代理         │
└ SESSION 会话：用户临时意愿（pin/deny）      ┘
```

**必放的"bug 揭示"块（这是亮点，不是背景）**：

> 原做法是给工具打 tag 按模式过滤，但有两个问题：
> - `note.create` 同时带 `note` 和 `write` 两个 tag，学习模式放行了 `note`，它**照样能写笔记**（OR 语义只能"放行"不能"禁止"）
> - 更关键：过滤只影响给 LLM 的列表，**不影响执行**——模型凭记忆照样能调通

**方案两行**：支持显式 `deny` + `pin`，运行时实时计算可见集；每个工具都能给出**可解释的决策链**。

**底部金句**：

> 可见性决定"你本来能碰什么"，Reflexion 封禁决定"你这轮已经把什么碰坏了"——两层权限治理。

### 第 11 页 · 亮点三：TurnOutcome 粘性降级标记

**信号累积图**：

```
本轮任何一步发生：
  ├─ 工具结果超 4000 字符被截断 ──┐
  ├─ 检索质量差（CRAG 降级）    ──┼─→ degraded = true（粘性，不可清除）
  ├─ 子代理结论被截断          ──┤
  └─ 工具被封禁               ──┘
        ▼
轮次结束：若答复里没提"信息可能不完整"，强制补一句
```

**两个关键点**：
1. **粘性**：参考 DSH 的"max-tokens 状态粘性"——一旦发生过信息丢失，后面正常完成也不能覆盖回"干净完成"
2. **修正指标**：原收敛率把"中途丢过数据但最后蒙对了"也算正常收敛，偏乐观；现在多了 `cleanConvergenceRate`，差值就是被高估的部分

**"刻意裁剪"话术（上屏或备注）**：

> 我参考了 DeepSeek Harness，但**刻意裁剪**：它的分层遮蔽还解决"插件化实现替换"，而我的工具是注解扫描、一个名字唯一实现，硬做替换就是过度设计。所以只保留"收窄 + deny"。

**底部结论**：在还没能力"不丢信息"之前，先做到"不隐瞒信息丢失"。

### 第 12 页 · 亮点四：上下文工程（★唯一有 A/B 数字的一页）

**一句话核心**：

> 滑动窗口的问题不是"丢信息"，而是**静默地**丢——用户第 3 轮说的 deadline 在第 35 轮消失了，模型和用户都不知道，于是照着错的时间排期。

**两个机制**：
- **滚动摘要**：窗口将满时把最老一段折叠成摘要，而非无差别 `pollFirst` 丢弃
- **Facts 层**：从用户原话抽取硬约束，按变更频率分流注入（稳定→system，易变→history 首条，**不打穿前缀缓存**）

**视觉主体 —— 前后对比表**（可复现，命令见备注）：

| 场景 | compaction 关 | compaction 开 |
|---|---|---|
| 40 轮后约束留存（约束在第 1..5 轮） | **0 / 5** | **5 / 5** |
| 40 轮后约束留存（约束散布到第 17 轮） | — | 2 / 5 |
| 纯工具噪声段的摘要 LLM 调用 | — | 0 次（短路） |
| 一天内 system 段字节版本数 | IMMEDIATE 9 种 | DAY **1 种** |

**底部结论（务必保留这句，它比 100% 更有说服力）**：

> 那个 2/5 是我特意补的对照：折叠把最老一段压成一条**放回队头**，而截断从**尾部**切，所以越早说的约束越受保护。真实结论是「早期约束保得住、中段约束会衰减」，不是「开了就不丢信息」。

**备注（不上屏）**：`./gradlew test --tests '*ContextEngineeringBenchmark*'`，报告在 `build/agent-eval/context-engineering.md`。摘要器是抽取式桩，量的是机制而非模型质量——被问到要主动说。

### 第 14 页 · 亮点五：「约定 → 门禁」对照表 ⚡

| 原来的约定（prompt 里写） | 现在的门禁（执行层 / CI） |
|---|---|
| "请别删掉示例" | 源有代码块而正文删成摘要 → **拒绝写入**（`MISSING_EXAMPLES`） |
| "笔记记得挂回 guide" | 漏挂 → 知识 CI 报 ERROR；`doc.write` 自动插入速记引用 |
| "引用要写对" | CI 校验链接到 anchor 级，断链检出 |
| "改动要审阅" | 提交永不落默认分支；精确 add + 提交前自校验暂存区 |
| "止损线要有具体名字" | 判据是解析器**真能抽出术语**，抽不出即拒 |

**金句**：

> prompt 提醒失效时是静默的，门禁失效时会大声拒绝——前者让你很久以后才发现内容坏了，后者当场就拦住。

**主动划边界（防追问，务必留）**：

> 门禁只能挡"结构不合格"和"写空"，挡不住"写得通顺但内容错"。所以蒸馏产物一律 `maturity: draft` + 渲染可见警示，必须人工核对。**门禁保证产物值得被核对，不保证产物正确。**

### 第 15 页 · 亮点六：Agent 评测体系

**核心难点**：LLM 非确定，无法写传统断言。

**解法**：把可替换点设在 **HTTP 边界**（`LlmTransport`），录制真实响应，回放时固定"模型说了什么"，其余——ReAct 循环、工具反射、CRAG 分支、前缀缓存——**全部真实执行**。

**寻址策略（有区分度）**：主键按调用序号（稳定），同时记录请求指纹做漂移检测。改了 prompt 测试仍能跑，但报告会告诉你"有几个用例录制已过期"。

**指标**：收敛率 / 工具幻觉率 / 步数 P50-P95 / 平均 LLM 调用数。CI 完全离线、零成本。

**★如果时间够，讲这个（比讲"我写了测试"有力得多）**：

> 我的评测套件有段时间是**假绿**的：写工具因为外键约束一直执行失败，但断言只检查「工具被调用过」，所以 9 个用例全通过。是我去核对报告里 `failedTools` 字段才发现的。**断言的粒度决定测试的信息量**——「调用了」和「调用成功了」差一个数量级。

### 第 16 页 · 其他模块速览 ⚡

- **RAG Serving**：个人场景重复提问率高，做**语义查询缓存**（阈值 0.93，写失效兜底）
- **MCP Server 双向**：对外把系统能力暴露成 MCP Server，Claude Desktop 等可直接接入
- **多模型路由**：按用户偏好路由 provider/model + 加权轮询
- **主动式 Agent**：晨报/晚报定时推送

**讲**：一句带过——"这些是配套能力，重点是前面讲的 Agent 运行时设计。"

### 第 17 页 · 踩坑与反思

**挑 2~3 个讲，每个一行现象 + 一句根因**：

**坑 1 · MCP loopback 永远连不上（相对 URI）**
> 现象是 Agent 说"读不了本地文件"，但 curl 全对。根因是服务端返回的 endpoint 是**相对路径**，Java HttpClient 不接受，握手一直失败，而日志写的是"将重试"——**看起来会自愈其实不会**。这坑让我学会用 curl 分治定位是 Server 还是 Client 的问题。

**坑 2 · CRAG 链路"看起来通了其实断了"**
> 三个组件单测全对，但检索质量差时 Agent 还是编造。根因是降级信号只在零命中时返回，而"有命中但质量差"走不进那个分支。**每个组件单独都对，但组件间的信息传递断了**——单测的盲区。

**坑 3 · 评测套件假绿（★最新，最能体现自省）**
> 写工具因外键约束一直失败，但断言只看"工具被调用过"，9 个用例全绿。**测试本身坏了却报告自己是好的**，比被测代码有 bug 更危险，因为它让所有其它结论都不可信。

**收尾金句**：

> 这些坑教会我两件事：做了优化必须能证明有效；**以及要怀疑自己的测量工具**——没有消费方的指标恒为 0 也不会被发现，粒度太粗的断言会让失败看起来像成功。

### 第 19 页 · 未来方向 + 主动划边界

**主动划边界（比被问出来更成熟）**：

> 我清楚当前边界：会话状态在内存（生产要用工作流引擎）；向量检索是万级全表 cosine（十万级必须换向量库）；评测还没做 LLM-as-Judge 的答案质量评分；上下文折叠对中段约束的保护会衰减（实测 40%）；知识仓库的门禁挡不住"写得通顺但内容错"。

**未来方向**：

> 下一步两件事：一是知识仓库的"体系化"（SYNTHESIZER）——从语料里自动抽出 foundations / 同构表 / 断链表；二是把"主动式 Agent"从定时推送延伸到对话内。

**收尾**：

> 这个项目最大的收获是：Agent 的难点不在"能不能调用工具"，而在**上下文、质量、可控性**这三件事——这也是我接下来读研想深入研究的方向。

## 四、金句（可做成主题页或结尾页）

1. **定位**：我不是在"用" Agent 框架，而是在"实现" Agent 运行时的关键机制。
2. **方法论**：把"提示词软约束"升级为"运行时硬闭环"。
3. **治理观**：可见性决定"你本来能碰什么"，Reflexion 封禁决定"你这轮已经把什么碰坏了"。
4. **门禁观**：prompt 提醒失效时是静默的，门禁失效时会大声拒绝。
5. **诚实观**：在还没能力"不丢信息"之前，先做到"不隐瞒信息丢失"。
