## 第 1 页 · 项目一句话定位

> **一句话**：Lattice-Planner 是一款面向个人的任务 / 目标 / 笔记规划软件，我在其中从零实现了一套**内嵌的对话式 Agent 系统**（Lattice-Agent），让用户可以用自然语言读写自己的规划数据、驱动 RAG 检索、委派子代理协作。

**它解决什么问题**：把「手动点页面管理任务」升级为「用一句话让 Agent 替你拆目标、建任务、做复盘、查笔记」。

## 第 4 页 · 亮点 1：自研 ReAct + 双层 Reflexion（重点讲）

### 背景
未用 LangChain / Spring AI，**从零手写 ReAct 主循环**（`AgentOrchestrator`），单轮最多 N 步（默认 8），每步 LLM 输出要么是「工具调用 JSON」要么是「终态自然语言」。

### 关键设计：把「工具失败」从被动回灌升级为主动干预

**原始做法（隐式 Reflexion）的问题**：错误 JSON 原样喂回 LLM，指望它自己想明白。实际观察到两类退化：

1. **原地打转**：同一工具用同样的错参数反复调用，直到步数耗尽。
2. **误判可重试性**：权限拒绝这类「确定性失败」被反复重试；参数错误这类「本可修复」的失败反而被轻易放弃。

**我的解法（双层 Reflexion，`ReflexionAdvisor`）**：

```
┌─ 建议层：按失败模式注入差异化策略提示 ─────────────┐
│  6 类失败模式 → 6 套策略（可重试 / 换工具 / 别重试直接说明）│
│  例：INVALID_ARGUMENTS → "对照 expectedParams 修正后重试"  │
│      RESOURCE_NOT_FOUND → "先检索拿真实 id，别编造"        │
└──────────────────────────────────────────────┘
┌─ 执行层强制：同一工具本轮失败达阈值 → 进入 banned ─┐
│  模型若无视提示再次调用，Orchestrator 直接短路返回      │
│  TOOL_BANNED_THIS_TURN，工具根本不执行               │
└──────────────────────────────────────────────┘
```

### 设计深度（面试加分点）

- **失败模式按「可重试性」分类是主轴**：`DENIED / USER_REJECTED / UNKNOWN_TOOL / RESOURCE_NOT_FOUND` 这类确定性失败**一次即封禁**，不浪费第二步去证明「权限拒绝还是会拒绝」。
- **失败分类是字符串/字段级轻量识别**，不是统一异常体系——因为工具实现分散在多个模块，分类「够准到能选对策略」即可，这是有意识的取舍而非偷懒。
- **封禁是单轮作用域**，不跨轮：用户下一轮可能已补齐信息，继承封禁会误伤。
- **配指标自证必要性**：`bannedToolCallsBlocked` 这个指标若长期为 0，说明模型听劝、强制层是冗余保险；一旦非 0，就是「只做提示层不够」的实证。

> **口头金句**：「提示层是"劝"，执行层才是"强制"——只做提示层的话，模型完全可能无视你继续撞墙。」

## 第 5 页 · 亮点 2：多代理编排（Orchestrator-Worker + 上下文隔离）

### 为什么需要子代理
单 Agent + 单上下文有三大瓶颈：

| 瓶颈 | 场景 | 根因 |
|---|---|---|
| 上下文污染 / 爆 token | 读 PDF 全文 + 建 N 个任务的中间 JSON 全进主窗口 | 所有结果回灌同一个 `ConversationMemory` |
| 串行慢 / 易超步 | 「体检我所有目标进度」多目标串行，8 步就耗尽 | 单一 `maxSteps` |
| 浅检索 | 多跳检索的中间片段污染主上下文 | 单轮召回有限 |

### 解法：三层组合

1. **Orchestrator-Worker**：主 Agent 编排，子代理是 Worker。
2. **Agents-as-Tools（核心巧思）**：每个子代理包装成一个 `@AgentTool`（`subagent.plan / reflect / research / parallel_research`）。**主循环 `AgentOrchestrator` 零改动**——委派子代理对它而言只是「调了一个慢一点的工具」。
3. **Context Isolation**：子代理用独立局部上下文跑完整段多步推理，**只把压缩后的结论还给主 Agent**，中间过程全部丢弃。

### 三个专精子代理

| 角色 | 定位 | 工具子集（最小权限） |
|---|---|---|
| PLANNER 规划专家 | 读文档 → 拆目标 → 建任务落库 | local + kb + planner + task + goal |
| REFLECTION 复盘专家 | 聚合周期数据产出结构化复盘 | insight + task + goal + note + kb |
| RESEARCH 检索专家 | 多跳知识库 + 文档检索，给出有出处的答案 | kb + note + local |

### 并行 fan-out（亮点中的亮点）

`subagent.parallel_research` 可并行委派多个检索专家处理多个子问题，把「体检所有目标」从串行变并行：

- **ThreadLocal 跨线程显式传播**：worker 线程手动 set/clear 用户上下文（这是最容易踩坑、也最见功底的点）。
- 固定线程池 size=4 + `allOf().orTimeout(120s)` 超时降级 + `@PreDestroy` 关池。
- **并行 fan-out 仅绑定只读角色**（RESEARCH），避免并发写冲突。

### 防递归护栏

`AgentContext.depth` + 运行期双护栏：`guardTopLevel()` 在 `depth>0` 时抛错；子代理 system prompt 的工具子集本就不含 `subagent.*`，双重禁止子代理递归套娃。

> **口头金句**：「子代理的价值源于同一句话——它在自己的独立上下文里跑完多步推理，只把压缩后的结论还回来，主对话窗口因此保持干净。」

## 第 6 页 · 亮点 3：Hybrid RAG + CRAG 纠错检索

### 检索架构（四层能力叠加）

```
用户提问
  ▼
RagServingService（门面：缓存 / 精排 / 异步 / 指标）
  ▼
CorrectiveRetriever（CRAG 纠错检索）
  ├─ RetrievalEvaluator 分级：CORRECT(≥0.6) / AMBIGUOUS(≥0.4) / INCORRECT
  ├─ QueryRewriter 改写重检索（RRF 合并，最多 1 次）
  └─ 仍不达标 → degraded 提示走通用知识
  ▼
RagSearchService（Hybrid 双通路）
  ├─ 关键字：MySQL FULLTEXT ngram（RRF 1/(1+rank)）
  ├─ 向量：bge-m3 1024 维 cosine
  └─ 加权融合 alpha=0.4，任一通路异常自动降级另一路
```

### 关键设计决策

- **零外部向量组件**：MySQL JSON + 本地 Caffeine LRU，万级 chunk 全表余弦 ~10ms，单体部署形态不变。
- **Hybrid 优于纯向量**：关键字（精确 ID/标题）+ 向量（语义）互补，且**降级矩阵完整**——没配 `EMBED_API_KEY` 时自动退回纯关键字通路，功能不失效。
- **Self-RAG 元信息回传**：CRAG 分级结果回传给 LLM 自省，让它知道「这次检索质量如何，该不该信」。
- **语义查询缓存**：cosine≥0.93 命中，按用户 LRU，降低重复检索开销。
- **LLM 精排（Reranker）**：LLM-as-Ranker 对粗排 top-N 重排，异常回退融合序。

> 这一页展示的是「RAG 不是调个接口就完事，而是一套可降级、可观测、有纠错闭环的检索系统」。

## 第 7 页 · 亮点 4：Agent 评测体系（录制回放）—— 最有力的一张

### 核心难题
LLM 输出**非确定性**，无法写传统断言。改一行 prompt 或调一次工具描述，**完全不知道是否让效果变差了**。

### 解法：VCR（录制 / 回放）模式

```
1) 抽接口：LlmGateway → interface LlmClient
2) 录制模式：真实跑一遍，把每次 (messages_hash → response) 存成 JSON 落盘
3) 回放模式：测试时注入 ReplayLlmClient，按 hash 命中返回录制的响应
   → 整条 ReAct 链路、工具调用、CRAG 分支都真实执行，只有 LLM 被固定
4) 断言 DSL：
   assertTrajectory(sid)
       .calledTool("kb.semantic_search")
       .thenCalledTool("task.create")
       .stepsWithin(6)
       .finalAnswerContains("已创建")
       .cragGradeWas(INCORRECT)
       .degradedSignalReachedLlm(true);   ← 专门防"信息传递断裂"
```

### 要落的指标（跑一批用例后输出报告）

| 指标 | 含义 |
|---|---|
| 工具选择准确率 | 期望工具集 vs 实际调用工具集 |
| 步数分布 | P50/P95 步数，发现工具循环 |
| 任务完成率 | 端到端断言全通过的用例占比 |
| 幻觉率 | 编造不存在的 id / 工具名的次数 |
| 降级正确率 | 该降级时真的降级了的比例 |
| 自修复率 | 工具失败后重试并成功的比例 |

### 这套体系的价值（三条）

1. 它是**其他所有优化的度量衡**——做上下文压缩，怎么知道效果没退化？加参数校验，怎么证明自修复率提升了？都靠它。
2. 它能**反向发现存量 bug**——项目真实踩过两个「组件都对但集成断了」的坑（CRAG grade 信号丢失、指标恒为 0），有回归集会提前暴露。
3. 它是面试中**唯一能把项目从"做过"升级到"做好"的证明**。

> **口头金句**：「这回答了 Agent 面试的必问题——你怎么评估 Agent 效果？我的答案是：录制回放 + 分层断言 + 指标报告。」

## 第 8 页 · 亮点 5：工具权限治理（分层遮蔽）

### 现状痛点（真实 bug）
工具可见性靠 `PromptBuilder` 的 OR 语义 tag 白名单，有三个缺陷：

1. **只能放行不能禁止**：`learn` 模式放行了 `note` tag → **learn 模式下 Agent 依然能写笔记**（现存 bug）。
2. **只是提示层约束，不是执行层约束**：模型凭上下文记忆调用被过滤掉的工具，**能调通**。
3. **会话级临时屏蔽不存在**，子代理不受主对话模式约束。

### 解法：四层 scope 链

```
GLOBAL → MODE → ROLE → SESSION（运行时实时计算可见集）
```

- **allow（收窄）/ deny（累积剔除）/ pin（破例）/ 结构性保留**（不可被 pin 解除）。
- **执行层增加拦截**：不可见工具短路返回 `TOOL_NOT_VISIBLE`，且**一次即封禁**，不可重试。
- 与 Reflexion 的动态封禁形成**两层权限治理**：静态可见性决定「你本来能碰什么」，动态封禁决定「你这轮已经把什么碰坏了」。

### 顺带修掉的隐患

- **度量缺陷**：`hallucinationRate` 把「工具不存在」与「越界调用」混算 → 幻觉率被高估。
- **静默遮蔽**：本地与 MCP 同名工具 schema 重复导出，但 invoke 永远走本地。

> 这一页展示的是「为 LLM 设计的权限模型」，呼应亮点 1 的「提示层 + 执行层」双约束思想，形成方法论上的统一。

## 第 9 页 · 亮点 6：可观测与轮次归因（工程化收尾）

### 设计原则（血泪教训沉淀）
项目踩过的「坑 4」：**指标恒为 0**——因为指标写了但没有任何消费方去读它。教训沉淀为两条硬约束：

1. **可降级**：所有新能力必须有开关，关闭时行为与现状一致。
2. **可观测**：每个新能力必须有对应指标进 `/api/observability/stats`——**没有消费方的指标等于没有指标**。

### 指标体系（举例）

```json
{
  "argValidation": { "argumentsRejected": 12, "rejectionRate": 0.0857,
                     "topRejectedParams": {"task.create.title": 5} },
  "reflexion": { "repairAttempts": 12, "repairSuccesses": 10,
                 "selfRepairRate": 0.8333, "bannedToolCallsBlocked": 2,
                 "failureModes": {"INVALID_ARGUMENTS": 9} },
  "config": { "reflexionEnabled": true, "reflexionFailThreshold": 2 }
}
```

### 轮次收尾解耦（TurnOutcome）

- **粘性降级标记**：本轮发生截断 / CRAG degraded / 子代理截断 → 置位后**不可清除**。**在没能力不丢信息之前，先做到不隐瞒**。
- 所有结束路径（终态 / 步数耗尽 / LLM 失败 / 初始化失败）归一为统一收尾出口，保证埋点与 WebSocket 语义一致。
- `config` 分区刻意加入：看到 `selfRepairRate=0.83` 却不知道校验开没开，这个数字就没有解释力。

## 第 10 页 · 亮点 7：MCP 双向集成 + 反向通道（安全）

### 双向 MCP
- **Server 端**：以 SSE 把本地工具与资源暴露给外部 MCP 客户端（Claude Desktop、Cursor、Cline 等）。
- **Client 端**：连接远程 MCP Server，把远端工具代理为本地 `@AgentTool`，扩展 Agent 能力边界。

### 反向通道（安全亮点）
本地文件类工具走「反向 RPC」，敏感操作**不出用户机器**：

```
后端 LocalDocTools.readPdf
  → LocalBridgeProxy 通过 WS 推 localCall
  → Electron preload → ipcMain → fs/pdf-parse（白名单校验路径/扩展名/大小）
  → 原路返回（CompletableFuture，30s 超时）
```

**核心安全优势**：后端不知道用户磁盘结构，服务器无法代读本地文件——这是相对「服务器代读」架构的根本优势。

### 高危操作显式确认
所有写操作先弹确认气泡，用户点「允许」才真正落库，60s 超时默认拒绝。

## 第 10·5 页 · 亮点 8：知识仓库（把约定变门禁）★

### 一句话定位

> 这是 V4 最新五期的主线：把「学习一个技术体系」工程化。方法论一句话——**把靠人自觉的约定，逐条升级成机器门禁。**

### 五期能力时间线

| 期 | 能力 | 一句可讲的取舍 |
|---|---|---|
| P0 | Git 仓库四级索引 | MySQL 是**可丢弃的派生索引**，Git 是权威源 |
| P1 | 验证闭环（checkpoint） | **预测门禁**：先写预测再动手，"改完再解释"人会为结果编理由 |
| P2 | 沉淀 + PR + 知识 CI | 写入白名单只含 `docs/notes/`——改既有 guide 在结构上**不可能** |
| P3 | 缺口三源合流 | 缺口只能来自**行为证据**，刻意不提供 `gap.create` 工具 |
| P4 | 蒸馏 + 定线 | 蒸馏**先看后写**；定线一次 LLM 都不调（可核对 > 更聪明） |

### 展开一个门禁（口头，最有代表性）

> **示例门禁是执行层拒绝，不是提示词请求**：沉淀笔记时，问答原文里有代码块、而模型把笔记压缩成"见原文示例"，我直接拒绝写入。因为模型天然倾向把内容压缩得更"整洁"，被压掉的恰是半年后还能重新看懂的部分。这个门禁有指标自证——`exampleGateRejections` 一旦非 0，就直接证明"只靠 prompt 提醒不够"。

### 方法论金句

> prompt 提醒失效时是静默的，门禁失效时会大声拒绝——前者让你很久以后才发现内容坏了，后者当场就拦住。

### 主动划边界（防追问）

> 门禁只能挡"结构不合格"和"写空"，挡不住"写得通顺但内容错"。所以蒸馏产物一律 `maturity: draft` + 渲染可见警示，必须人工核对。**门禁保证产物值得被核对，不保证产物正确。**

## 第 12 页 · 技术难点与取舍（应对追问，最能拉开差距）

> 面试官最爱问「为什么这么做」，这一页是备好的答案库。

| 追问 | 我的答案 |
|---|---|
| 「为什么不用 LangChain / Spring AI？」 | 想搞清楚 Agent 底层机制，自研 ReAct 让我对每一步（提示构造、工具解析、错误回灌、上下文管理）有完全掌控，也避免了框架黑盒带来的排障困难。 |
| 「LLM 不确定性怎么测？」 | 录制回放 + 分层断言：回放固定 LLM，但整条 ReAct / 工具 / CRAG 分支真实执行。 |
| 「上下文满了怎么办？」 | 三级治理：隔离（子代理独立上下文）+ 复用（前缀缓存）+ 压缩（工具结果截断 + 分级）。 |
| 「Agent 卡住了怎么办？」 | 失败分类 + 失败计数 + 执行层强制换工具，而不是无脑重试。 |
| 「怎么防止 Agent 越权？」 | 分层遮蔽（静态可见性）+ 动态封禁（本轮失败状态）+ 高危确认（用户授权），三层。 |
| 「指标恒为 0 怎么办？」 | 每个指标必须有消费方，config 分区让数字有解释力。 |
| 「失败分类会不会误判？」 | 会，但分类只要「够准到能选对策略」，误判代价仅是给一条次优提示，不影响正确性——这是有意识的取舍。 |

## 附：PPT 制作建议（视觉与节奏）

1. **页数控制在 12~14 页**：第 3 页亮点总览是「目录」，第 4~10 页是正文，第 11 页能力背书，第 12 页可作备用页（不一定放映，但被追问时有料）。
2. **每页一个主题 + 一句金句**：金句用大字号单独框出，方便面试官抓重点。
3. **架构图用手绘风格重画**：别直接贴 ASCII 图，用 draw.io / PPT 自绘，突出「七层解耦」和「数据流」。
4. **Agent 页都用「痛点 → 解法 → 亮点」三段式**：这是最有说服力的叙事结构，也和面试官「你怎么解决 XX」的提问习惯对齐。
5. **准备一个 30 秒 live demo**：如果现场允许，跑「读 PDF → 拆目标 → 建任务」这条闭环，配合子代理卡片 + 高危确认弹窗，观感远胜纯讲 PPT。
6. **主动暴露已知边界**（加分项）：上下文是内存态未持久化、工具调用未并行、失败分类是轻量识别——主动说出来反而显得诚实且思考周全。
