## 二、三层讲解法（由粗到细）

### 第一层：一句话概括（30 秒）

> 我的主循环是一个手写的精简 ReAct：**「用户输入 → 反复 {问 LLM → 调工具 → 把结果喂回去} → 直到 LLM 不再调工具给出终态答复」**。
>
> 不用现成框架，是因为我要在循环里塞几个框架封装不掉的控制点：步数上限、工具可见性、授权确认、失败自纠、收尾时机。

### 第二层：三个关键结构（2 分钟，讲骨架）

**结构 1 · 循环体 = "一次一步"的 ReAct**

> 每一轮只调一个工具，拿到结果立刻回灌，再问下一轮。不做并行（除了子代理内部），因为工具之间常有依赖——`task.create` 需要 `goal.create` 返回的 id。

**结构 2 · 工具调用前的"三重闸门"（第 ⑤ 步）**

> 模型给出工具调用后，不是直接执行，而是过三道检查：
> 1. **存在吗**——不存在就回灌 `UNKNOWN_TOOL`（幻觉自纠）
> 2. **可见吗**——当前模式/会话不可见就回灌 `TOOL_NOT_VISIBLE`（越界拦截）
> 3. **封禁了吗**——本轮失败过就被 `ReflexionAdvisor` 封禁，短路返回
>
> 这三道闸门共同点是：**都是执行层强制，不是提示层劝告**——因为模型完全可能无视提示。

**结构 3 · 收尾时机可被外部干预（第 ④ 步）**

> 当 LLM 给出自然语言终态答复时，不是直接 `return`，而是先问一圈"收尾顾问"。顾问可以返回一条 steer 消息，让循环继续（比如"降级了但没明示，补一句"）。这样"什么时候算完"从循环内部解耦到外部。

### 第三层：子代理怎么开（重点展开）

> 子代理不是独立的循环，而是**被"工具"包装起来**的——`subagent.plan` / `subagent.reflect` / `subagent.research` 是三个 `@AgentTool`，主循环对它而言只是"调了一个慢一点的工具"。

```
主循环第 ⑦ 步调用 subagent.plan
        │
        ▼
SubAgentTools.plan()          ← 主循环视角：普通工具
        │ guardTopLevel() 检查 depth==0
        ▼
SubAgentRunner.run()          ← 开一个子代理
        │ AgentContext.enterSub()  depth++
        ▼
    ┌─────────────────────────────┐
    │  子代理自己的 ReAct 循环      │
    │  · 独立上下文（List，不碰主记忆）│
    │  · 独立步数预算（12 步）       │
    │  · 独立 Reflexion 状态        │
    │  · 工具集 = 角色最小子集       │
    └──────────────┬──────────────┘
                   │
                   ▼
    压缩结论（≤4000 字符）→ 作为工具结果回灌主循环
```

**子代理的三个关键设计（讲出隔离的价值）**：

1. **上下文隔离**：子代理用局部 `List`，绝不写主 `ConversationMemory`。主循环读 50 页 PDF，原文只在子代理上下文里，主循环只收到压缩结论——**防止长文档污染主对话**。

2. **递归防护**：`guardTopLevel()` 检查 `depth > 0` 抛异常 + 工具可见性层结构性保留 `subagent.*`，双保险防止子代理再开子代理。

3. **并行 fan-out**：`subagent.parallel_research` 把问题拆成多个子问题并发跑多个检索子代理，`allOf().orTimeout()` 超时降级不整体失败。仅用于只读角色（RESEARCH/REFLECTION），写角色（PLANNER）保持串行。

## 三、讲解节奏建议（画图顺序）

1. 先画**中间那一竖条**：`用户 → LLM → 工具 → 回灌 → 再问 LLM`，说"这是一个 ReAct 循环"
2. 再补**左边**（终态 → 收尾顾问），说"什么时候结束是可插拔的"
3. 再补**右边**（三重闸门 + 确认），说"工具调用前要过闸门"
4. 最后讲**子代理**：指着第 ⑦ 步说"subagent.* 不是特殊路径，就是一个慢一点的工具，内部再开一个隔离的循环"

## 四、三个必背金句（讲到对应节点时抛出）

1. **开场**：我不是在"用"Agent 框架，而是在"实现"Agent 运行时的关键机制。

2. **讲三重闸门时**：工具可见性决定"你本来能碰什么"，Reflexion 封禁决定"你这轮已经把什么碰坏了"——两层权限治理。

3. **讲收尾顾问时**：什么时候算一轮结束，从循环内部解耦到了外部——主循环不需要预先知道有多少种"还没完"的理由。

## 五、可能被追问的三个点（预案）

**Q：为什么一次只调一个工具，不做并行？**

> 因为工具间常有数据依赖——`task.create` 需要 `goal.create` 返回的 id。盲目并行会引入难查的时序 bug。真正的并行我只放在子代理内部（`parallel_research` 拆的是彼此独立的子问题）。

**Q：子代理和主循环的代码是不是重复的？**

> 是刻意的"相似而非统一"。两者都是 ReAct 循环，但关键差异是隔离：子代理用局部 `List`、独立 Reflexion、独立步数预算、角色最小工具集。合并成一个抽象类反而会破坏这些隔离边界。这是"显式重复优于错误抽象"的取舍。

**Q：循环怎么保证不会死循环？**

> 三道防线：① 步数上限 24；② Reflexion 封禁（同一工具失败达阈值就封禁，不再执行）；③ 收尾顾问的 steer 有单轮上限，防止"顾问一直说没完"。

**Q：第 ① 步那个"折叠"是什么？为什么不直接丢最老的消息？**

> 因为直接丢是**静默丢**。用户第 3 轮说"deadline 是下周五"，到第 35 轮这句随窗口滑出去了，模型不知道、用户也不知道，于是照着错的时间排期。
>
> 折叠是把最老一段压成一条摘要放回队头，而不是 `pollFirst` 扔掉。实测 40 轮对话下，关闭时早期约束留存 0/5，开启后 5/5。
>
> **两个细节值得说**：一是摘要只能放进 history、**不能放进 system**，否则每轮 system 字节都在变，上游 prompt cache 直接失效；二是待折叠段如果剔掉工具 trace 后没剩几条真实对话，就直接丢弃不调 LLM——不值得为一堆 `[tool_result ...]` 付摘要成本。
>
> **边界要主动说**：折叠放回队头、截断从尾部切，所以越早说的约束越受保护。同样 5 条约束散布到第 17 轮，留存就掉到 2/5。早期约束保得住，中段会衰减。

## 六、一页速记卡（面试前扫一眼）

```
主循环 = ReAct：用户 → {LLM → 工具 → 回灌} × N → 终态
控制点：步数上限 24 / 三重闸门 / 授权确认 / Reflexion / 收尾顾问
上下文：窗口 30，将满则折叠成摘要（不是丢弃），轮首 + 回灌后各判一次
子代理 = 被工具包装的隔离循环，12 步预算，只回压缩结论（≤4000 字）
核心哲学：执行层强制 > 提示层劝告
          上下文隔离 > 无脑共享
          静默丢失 > 一切（宁可折叠出错也不要悄悄丢）
```
